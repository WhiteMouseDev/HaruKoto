# 하루코토 학습 경험과 운영 안정성을 개선한 기록

일본어 학습 앱 하루코토를 개선하면서 처음 받은 요청은 학습 화면을 지하철 노선도처럼 표현해보자는 것이었다. 이후 실제 아이폰에서 학습을 반복하자 다른 문제가 보였다. 정답을 모두 맞혔는데 결과는 0점이었고, 한 문제를 저장한 이어 풀기 카드에는 0%가 표시됐다. 운영에서는 DB 접근 경고와 반복 오류, 날짜 비교 예외가 도착했다.

문제들은 서로 다른 계층에 있었지만 사용자에게는 같은 질문으로 돌아왔다. **앱이 내가 한 학습을 정확히 기억하고 있는가.** 화면의 의미, 서버의 저장 경계, 실제 DB의 상태를 함께 확인해야 답할 수 있었다.

이 기록은 2026년 9월 29일 이후 진행한 작업을 열다섯 사례로 정리한다. 운영 반영과 로컬 검증을 구분한다. 정기 점검·실제 알림 수신과 레슨 문항의 SRS 대상 수정은 운영에서 확인했다. 이번 오답 복습과 오류 화면은 아래 11번의 별도 구현 상태를 따른다. 연속 학습일의 영속 기록과 특수 모드 이어 풀기는 별도 후속 과제로 남아 있다.

## 1 지하철 노선도에서 자유로운 학습을 표현하기

### 문제와 원인

기존 챕터 목록은 학습 위치를 한눈에 파악하기 어려웠다. 참고 이미지의 굵은 노선, 역 번호판, 현재 역의 열차는 순서를 이해하기 쉬웠지만 그대로 적용하면 새로운 오해가 생겼다. 사용자가 1장을 건너뛰고 5장을 먼저 공부했을 때 선을 5장까지 채우면 앞의 장도 완료한 것처럼 보인다.

디자인 시안의 색을 가져오는 과정에서도 브랜드 핑크가 지나치게 넓게 쓰이면 눈에 부담을 줬다. 강도를 낮추다가 화면 전체를 어둡게 만들면 하루코토의 기존 인상과 멀어졌다. 정리된 디자인 시스템처럼 보이는 Stitch 산출물도 HTML과 설명의 토큰 값이 일치하지 않는 부분이 있었다.

### 설계와 수정

먼저 시각적 비유의 의미를 정했다. **노선은 커리큘럼 순서, 역은 챕터, 열차는 다음에 시작하거나 이어갈 추천 위치**다. 열차를 실제 최근 활동이나 학습 완료의 증거로 사용하지 않는다. API에 활동 시각이 없으므로 챕터 순서만으로 최근 학습 위치를 만들어내지도 않는다.

모든 역을 자유롭게 열 수 있게 두고 완료 상태는 역마다 독립적으로 계산했다. 노선 전체는 일정한 브랜드 색을 유지하며, 진행 여부는 역의 아이콘과 완료 수, 문구로 보여준다. 다른 역을 펼쳐보는 행동은 추천 위치나 학습 상태를 바꾸지 않는다.

처음 방문한 아이폰에서 열차가 보이지 않았던 피드백도 이 규칙으로 정리했다. 열차는 학습을 이미 시작했다는 표시가 아니므로 미시작 상태의 추천 역에도 보여야 한다. 대신 `이어할 역`과 `추천 역` 문구를 나눠 실제 상태를 정직하게 표현한다.

| 상황            | 표시 규칙                                                      |
| --------------- | -------------------------------------------------------------- |
| 처음 방문       | 첫 추천 역에 열차와 `추천 역`, 완료 수 0 표시                  |
| 5장을 먼저 시작 | 앞 장은 미학습 상태 유지, 기존 추천 규칙에 따라 이어갈 역 표시 |
| 5장만 완료      | 5장만 완료, 앞의 역으로 완료 상태가 전파되지 않음              |
| 다른 역 펼치기  | 탐색 상태만 변경, 추천과 학습 기록 유지                        |
| 전체 완료       | 완료 상태 유지, 활성 열차 대신 기존 복습 진입 사용             |

색상은 기존 `AppColors`를 기준으로 정리했다. 핑크는 노선과 열차, 역 테두리와 주요 행동에 사용하고, 넓은 배경은 따뜻한 중립색과 부드러운 Sakura 표면으로 낮췄다. 작은 흰 글자를 밝은 핑크 위에 놓는 조합도 그대로 채택하지 않았다. 브랜드 색을 유지하는 것과 모든 버튼을 같은 색으로 채우는 것은 다른 결정이었다.

사용자가 다시 제시한 휴대폰 이미지를 기준으로 교통 노선의 인상을 복원했다. 이후 열차는 40×50 크기로 줄이고, 역 번호판은 56×56을 기본으로 하는 정사각형으로 바꿨다. 글자 배율이나 세 자리 번호가 필요하면 가로와 세로를 함께 늘려 정사각형을 유지한다.

주변 카드도 의미를 명확히 했다. 복습 카드에는 실제 복습 대기 수와 하나의 시작 버튼을 두고, 근거가 없는 `어제 배운` 문구를 없앴다. 이어갈 레슨은 `Ch.1 · 4/5` 대신 `1번 역 · 4번째 레슨`처럼 위치와 순서를 풀어 썼다.

### 검증과 되돌리기

실제 Flutter 위젯으로 밝은 테마와 어두운 테마, 320px 화면과 2배 글자를 확인했다. 다른 역을 열어도 추천 위치가 바뀌지 않는지, 뒤의 장만 완료했을 때 앞 장이 미학습으로 남는지 테스트했다. 변경 단계별 전체 모바일 테스트 수는 달라졌으므로 이를 하나의 결과로 합산하지 않는다.

디자인 실험을 되돌릴 수 있도록 기존 목록을 보존하고 `studyMapEnabled` 소스 플래그로 분기했다. 이 플래그는 원격 설정이 아니라 앱을 다시 빌드해야 하는 스위치다. 두 화면은 같은 백엔드 식별자와 진도 데이터를 사용하므로 디자인을 되돌릴 때 학습 기록을 변환할 필요가 없다.

이 사례의 지하철·주변 카드 변경은 로컬 위젯과 시뮬레이터에서 검증한 작업이며, 이후 기존 변경을 보존한 아이폰 빌드에도 포함됐다. 전체 디자인 실험이 별도 PR로 병합됐다는 의미는 아니다.

학습 노선도 로컬 작업 기록: `docs/operations/plans/mobile-subway-learning-map-2026-09-29.md`.

## 2 연속 학습일은 화면보다 기록 기준이 먼저였다

### 문제와 원인

연속 학습일은 다음 날 다시 앱을 열게 하는 동기가 될 수 있다. 그래서 달력의 원을 예쁘게 만드는 것보다 어떤 행동을 하루 학습으로 인정할지 먼저 정해야 했다.

기존 데이터에서는 퀴즈를 시작하기만 해도 일일 행이 생길 수 있었고, 레슨을 다시 완료하면 최근 완료 시각이 덮어써질 수 있었다. 일일 행이 있다는 이유만으로 출석 처리하면 시작만 한 날을 학습일로 세게 된다. 최근 완료 시각만 이용하면 과거의 반복 학습일을 잃는다.

### 설계와 구현한 부분

날짜는 휴대폰 위치와 무관하게 한국 시간 자정부터 다음 자정까지로 정의했다. 학습 완료처럼 자격이 있는 행동만 하루에 한 번 인정하고, 같은 날의 재시도나 동시 완료는 추가 일수를 만들지 않게 하는 방향을 잡았다.

오늘 아직 학습하지 않았어도 어제까지 이어온 연속일은 계속할 수 있는 상태로 표현한다. 하루를 놓친 뒤 다음에 학습하면 1일부터 다시 시작한다. 출석을 위해 XP나 단어 수를 임의로 늘리는 방식은 사용하지 않는다.

모바일에는 한국 시간 기준 날짜 처리, 자정과 앱 복귀 시 새로고침, 실제 학습 성공 뒤 갱신, 달력 오류와 재시도 상태를 반영했다. 오늘의 테두리와 완료 표시를 구분하고 브랜드 핑크를 사용했다. API와 웹에는 날짜 계산과 공통 계산·잠금 보조 함수를 준비했다.

### 아직 남은 영속성 설계

확실한 학습일을 보존하려면 기존 사용자·날짜별 행에 명시적인 `has_studied` 기록이 필요하다. 완료 트랜잭션에서만 참으로 바꾸고, 같은 날 다시 쓰더라도 중복되지 않게 하는 설계다. 과거 데이터는 남아 있는 완료 증거로 확인할 수 있는 날짜만 복원해야 한다.

**이 스키마 변경과 모든 완료 경로의 영속 기록 전환은 승인 대기 상태다.** 현재 작업을 모든 학습 방식에서 연속일이 완전히 정확해졌다고 소개하면 안 된다. UI·날짜 처리 개선과 출석 데이터 모델 완성은 서로 다른 단계다.

9월 29일 검증에서는 모바일 595개 테스트가 통과했고 API는 578개 통과, 기존 스킵 13개였다. 이 숫자는 당시 변경의 로컬 검증 결과이며 영속 출석 기능의 운영 적용을 뜻하지 않는다.

연속 학습일 로컬 작업 기록: `docs/operations/plans/streak-attendance-integrity-2026-09-29.md`.

## 3 모두 맞힌 퀴즈가 0점이 된 이유

### 문제와 원인

10월 7일 실제 아이폰에서 오늘의 퀴즈를 모두 맞혔는데 정답률 0%, 정답 0/10, XP 0이 표시됐다. 결과 화면에서만 숫자를 고치면 저장되지 않은 답안과 통계는 그대로 남는다. 답안 제출부터 완료 집계까지 실제 PostgreSQL로 재현해야 했다.

복습 이벤트를 쓰는 테이블의 파티션 범위가 부족하면 이벤트 INSERT가 실패할 수 있었다. PostgreSQL에서는 문장 오류가 발생하면 해당 트랜잭션이 실패 상태가 된다. Python에서 예외만 잡아 무시해도 같은 트랜잭션이 정상으로 돌아오지 않는다. 부가 이벤트의 실패가 핵심 답안 저장까지 영향을 주던 경계가 문제였다.

### 설계와 수정

답안과 점수, 학습 진도를 핵심 저장 경로로 두고 부가 복습 이벤트는 SAVEPOINT 안에서 기록하도록 격리했다. 이벤트 INSERT가 실패하면 그 부분만 되돌리고 바깥 답안 트랜잭션은 유지한다. 실패는 경고로 남겨 이벤트 누락 자체를 숨기지 않는다.

```python
# 핵심 구조를 줄인 예시다. 실제 코드에는 진행 상태 갱신이 함께 있다.
try:
    async with db.begin_nested():
        await log_review_event(...)
except Exception:
    logger.warning("Quiz review event could not be recorded", exc_info=True)
```

재시도도 처리했다. 같은 세션의 답안 제출과 완료를 세션 행 잠금으로 직렬화하고, 같은 문제에 같은 답안을 다시 보내면 점수나 학습 진도를 한 번 더 올리지 않는다. 이미 제출한 답을 다른 답으로 바꾸려는 요청은 충돌로 처리한다. 결과 집계 역시 저장된 답안의 기준과 맞췄다.

이 방어는 파티션을 자동으로 복구하는 기능이 아니다. 먼저 정답 저장을 지키고, 이벤트 저장을 막는 운영 DB 문제는 별도로 해결하도록 분리한 것이다.

### 결과 화면과 피드백 정리

저장이 정상화된 뒤에도 결과 카드의 높이가 달랐다. XP 카드에만 다음 레벨 진행률이 들어 있어 세 개의 요약 카드가 맞지 않았다. 정답·획득 XP·오답 카드를 같은 구조로 맞추고, 다음 레벨 정보는 아래의 별도 영역으로 옮겼다. 좁은 화면이나 큰 글자에서는 세로 배치로 바꾼다.

과한 색종이 효과는 결과 화면에서 제거했다. 답안 피드백은 정답과 오답 두 소리로 통일하고, 연속 정답 수에 따라 다른 소리가 나오지 않게 했다. 사운드 파일이나 다른 모드의 모든 효과를 삭제한 변경은 아니다. 현재 답안 피드백 경로를 단순화한 것이다.

### 검증 결과

회귀 테스트는 10월 INSERT를 실패시키는 실제 파티션 구성을 만들었다. 일반 퀴즈와 스마트 퀴즈 모두 정답 10개가 별도 DB 세션에서 다시 읽히고, 완료 결과가 10/10·100%·100 XP인지 확인한다. 응답 유실을 가정한 같은 답안 재전송도 점수를 부풀리지 않아야 한다.

핵심 저장 수정은 [PR #174](https://github.com/WhiteMouseDev/HaruKoto/pull/174)로 병합됐다. 카드·색종이·사운드는 별도의 모바일 로컬 변경으로 검증하고 설치 빌드에서 보존했다. 저장 수정의 병합 상태와 모바일 디자인 변경의 상태를 섞지 않는다.

구현 근거: [이벤트 격리](../../apps/api/app/services/quiz_answer_progress.py), [실제 DB 답안 회귀](../../apps/api/tests/test_quiz_answer_persistence_postgres.py), [피드백 회귀](../../apps/mobile/test/features/study/providers/quiz_runtime_coordinators_test.dart). 결과 카드 회귀의 로컬 경로는 `apps/mobile/test/features/study/presentation/widgets/result_score_display_test.dart`다.

특수 모드인 매칭·문장 배열 퀴즈의 원래 모드를 이어 풀기에서 완전히 복원하는 계약은 별도 후속 과제로 남아 있다. 일반 퀴즈의 검증 결과를 모든 특수 모드로 확대하지 않는다.

## 4 Data API 경고를 접근 경로 분리로 해결하기

### 문제와 원인

10월 14일 Supabase에서 테이블과 민감 정보가 공개 접근 가능하다는 경고가 왔다. 실제 점검에서는 애플리케이션 테이블에 RLS가 켜져 있지 않았고 클라이언트 역할의 접근 권한도 넓었다.

하루코토의 학습 데이터는 FastAPI와 서버의 DB 연결을 통해 접근한다. 모바일에서 Data API로 애플리케이션 테이블에 직접 접근할 필요는 없었다. 따라서 필요한 서버 경로를 유지하면서 사용하지 않는 직접 접근 경로를 닫는 방향을 선택했다.

### 설계와 수정

플랫폼의 Data API를 끄고, 테이블·열 권한과 RLS를 함께 정리했다. 당시 42개 애플리케이션 테이블의 RLS를 활성화했고, 43개 공개 테이블·뷰 객체에서 일반 클라이언트의 유효한 DML 권한을 제거했다. 뷰는 호출자 권한으로 동작하게 하고, 시퀀스와 공개 루틴 접근도 함께 검토했다.

새 객체가 다시 넓은 권한을 갖지 않도록 기본 권한과 DDL 가드도 정리했다. Auth의 사용자 생성 트리거와 신뢰하는 서버 역할은 유지했다. RLS를 켰다는 사실 하나만으로 접근 제한 전체가 검증됐다고 판단하지 않고 실제 역할별 권한을 확인했다.

```sql
-- 접근 제한 방향을 설명하는 예시다. 운영 적용은 검토한 마이그레이션으로 한다.
ALTER TABLE public.example_table ENABLE ROW LEVEL SECURITY;
REVOKE ALL PRIVILEGES ON TABLE public.example_table
FROM PUBLIC, anon, authenticated;
```

### 검증과 운영 반영

실제 PostgreSQL에서 클라이언트 CRUD·열·뷰·파티션·루틴 접근 거부와 Auth 사용자 생성, 서버 학습 저장을 함께 테스트했다. 운영에서는 변경 전후 로그인과 학습 조회를 확인하고, 전용 테스트 계정의 퀴즈를 저장·복원·완료했다.

Security Advisor의 해당 ERROR 항목은 42개에서 0개가 됐다. 별도의 유출 비밀번호 보호 WARN은 다른 설정으로 남겼다. 보안 변경은 [PR #175](https://github.com/WhiteMouseDev/HaruKoto/pull/175)로 병합하고 서버 배포까지 완료했다. 접근 권한을 다시 여는 자동 downgrade는 거부한다.

10월 20일 받은 새 메일은 별개였다. 10월 30일부터 새 테이블에 Data API 권한을 자동 부여하지 않는다는 안내였다. 이미 차단한 경로를 다시 열 이유가 없으므로 메일의 GRANT 예시를 적용하지 않았다. 기존 테이블의 권한이나 학습 기록을 삭제한다는 안내도 아니었다. [Supabase 공식 공지](https://github.com/orgs/supabase/discussions/45329)는 직접 PostgreSQL 연결을 사용하는 앱은 이 변경의 영향을 받지 않는다고 구분한다. 정책 전환 뒤 핵심 기능 재확인은 후속 점검이다.

관련 기록: [Data API와 RLS 적용](../operations/plans/supabase-public-data-access-hardening-2026-10-14.md).

## 5 Disk IO 경고에서 확인한 사실만 고치기

### 문제와 조사

다음 날 Disk IO 예산 소진 안내가 왔다. 반복 오류와 비효율적인 조회가 함께 보였지만 그 메일의 원인을 하나로 확정할 수는 없었다. 짧게 관찰한 통계에서 디스크 블록 읽기나 임시 파일이 계속 증가하는 현상도 확인하지 못했다.

대신 확실한 두 문제를 분리했다. Data API를 껐을 때 없는 스키마를 찾는 오류가 약 32초마다 반복됐다. 스마트 퀴즈는 각 문항의 오답 선택지를 만들 때 같은 후보 집합과 이미 학습한 ID를 반복 조회했다.

### 설계와 수정

Data API는 계속 끈 채 비어 있고 클라이언트가 접근할 수 없는 PostgREST 대상 스키마를 설정했다. 스키마에 객체가 있거나 소유자가 예상과 다르면 적용을 중단하고, 일반 공개 테이블을 다시 노출하는 방식으로 오류를 없애지 않았다.

퀴즈에서는 사용자·유형·레벨 범위가 같은 후보 데이터와 학습한 ID를 요청당 한 번 읽어 재사용했다. 전역 캐시로 사용자 데이터를 섞지 않고, 한 퀴즈 생성 요청 안에서만 공유한다. 정답 제외, 오답 순위, 선택지 수 같은 기존 의미는 유지했다.

### 검증 결과와 해석

10문항 스마트 어휘 퀴즈에서 해당 후보·학습 ID SELECT는 **20회에서 2회**로 줄었다. 실제 DB 테스트로 2문항과 10문항 요청, 사용자 격리, 네 개의 서로 다른 선택지와 메타데이터를 확인했다.

운영 적용 후 관찰한 09:31:35–09:37:15 KST 구간에서 PostgreSQL·PostgREST 오류는 0건이었다. Data API는 계속 차단됐고 전용 테스트 계정의 퀴즈는 2/2·100%·20 XP로 저장됐다. [PR #176](https://github.com/WhiteMouseDev/HaruKoto/pull/176) 병합과 서버 배포도 완료했다.

이 결과는 반복 오류가 해당 관찰 구간에 없었고 특정 SELECT 수가 줄었다는 뜻이다. **전체 Disk IO가 90% 줄었다거나 경고의 근본 원인이 입증됐다는 수치는 아니다.**

관련 기록: [반복 로그와 퀴즈 중복 조회](../operations/plans/data-api-log-and-quiz-io-2026-10-15.md).

## 6 이어 풀기는 저장과 표시를 따로 검증했다

### 날짜 비교 예외

Sentry 주간 메일에 `offset-naive`와 `offset-aware` 날짜를 비교할 수 없다는 오류가 있었다. 실제 스택은 미완료 퀴즈 조회 경로를 가리켰다. 운영의 레거시 시작 시각은 시간대가 없는 PostgreSQL timestamp였고, 비교 기준은 시간대가 있는 UTC 시각이었다.

저장된 값이나 API 표현을 일괄 변경하는 대신 기존 UTC 해석 규칙에 따라 **비교할 로컬 값만 정규화**했다. 24시간 경계의 직전·정확히 경계·직후를 naive UTC, aware UTC, aware KST로 테스트했다. 실제 레거시 컬럼에서 다시 읽은 값으로 일반·스마트 퀴즈의 조회와 이어 풀기도 확인했다.

[PR #177](https://github.com/WhiteMouseDev/HaruKoto/pull/177) 배포 후 전용 계정으로 1/3 저장, 같은 세션 복원, 3/3·100%·30 XP 완료를 검증했다. 질문의 ID와 순서, 선택지, 이미 저장한 답안이 유지돼야 한다. 완료한 퀴즈는 미완료 조회에서 사라지고 다시 이어 풀 수 없어야 한다.

### 아이폰에 남은 0퍼센트

서버 이어 풀기가 정상화된 뒤에도 아이폰 카드에는 0%가 보였다. 이번에는 저장 실패가 아니었다. 원형 지표가 이번 퀴즈의 진행률이 아니라 해당 레벨의 숙련 단어 비율을 계산하고 있었다. 한 문제를 풀어도 숙련 단어가 늘지 않으면 0% 자체는 맞을 수 있지만 옆의 이어 풀기 행동과 의미가 어긋났다.

이어 풀 대상의 유형과 레벨이 맞을 때는 `저장한 답안 수 / 전체 문제 수`를 사용하고 `이번 퀴즈`와 저장 수를 함께 표시했다. 그 외에는 `N5 숙련도`처럼 지표 이름을 명확히 붙였다. 오답도 진행한 문제이므로 진행률에 포함한다. 로딩이나 오류를 거짓 0%로 바꾸지도 않는다.

화면을 나갈 때는 대기 중인 답안 저장이 끝나야 하고, 실패하면 오류와 재시도 경로를 제공한다. 홈과 앱 복귀 시 미완료 데이터를 갱신해 이전 값이 남지 않도록 했다.

### 실제 기기 검증

[PR #179](https://github.com/WhiteMouseDev/HaruKoto/pull/179)의 변경을 기존 로컬 UI 작업과 함께 보존해 아이폰에 업데이트했다. 앱을 지우거나 로그아웃시키지 않았다. 공식 Flutter 3.41.3으로 검증하고 CI도 같은 SDK를 사용하도록 고정했다.

실제 화면에서 한 문제 뒤 `1/20문제 저장됨 · 이번 퀴즈 · 5%`를 확인했다. 프로세스를 완전히 종료하고 다시 켠 화면에도 같은 수치가 남았다. 이후 사용자가 이어 풀기를 눌러 **2/20부터 시작한다**고 확인했다. 재시작 전후 카드 수치는 직접 화면 증거이고, 다음 문제 시작은 사용자의 실제 기기 확인이다.

이때 깨끗한 브랜치는 모바일 테스트 546개, 기존 변경을 보존한 설치 체크아웃은 649개가 통과했다. 차이는 포함된 로컬 변경 범위이므로 서로 같은 테스트 실행의 숫자로 합치지 않는다.

로컬 작업 기록 경로: 날짜 비교 수정은 `docs/operations/plans/incomplete-quiz-timezone-fix-2026-10-19.md`, 모바일 진행률과 재시작 검증은 `docs/operations/plans/mobile-resume-progress-2026-10-19.md`.

## 7 통과한 CI에서 실제 DB 테스트가 빠져 있었다

### 문제와 원인

로컬에서는 실제 PostgreSQL 회귀 테스트를 돌렸지만 CI에는 PostgreSQL 실행 파일이 없어 필요한 테스트가 스킵됐다. 테스트 명령이 성공했다는 사실과 중요한 DB 사례가 실행됐다는 사실이 달랐다.

당시 PR #177의 CI는 584개 통과·23개 스킵이었다. 같은 변경을 PostgreSQL이 있는 로컬에서 실행하면 594개 통과·기존 선택적 스킵 13개였다. 차이인 10개에 답안 영속성, 조회 재사용, 접근 제한 같은 핵심 DB 사례가 있었다.

### 설계와 수정

CI에서 실제 PostgreSQL을 준비하고 JUnit 결과를 검사하는 별도 가드를 추가했다. 필수 테스트의 정확한 식별자를 목록으로 관리해 누락·중복·스킵·실패·오류가 하나라도 있으면 가드가 실패한다. 이름만 비슷한 테스트나 전체 통과 개수로 대체하지 않는다.

[PR #178](https://github.com/WhiteMouseDev/HaruKoto/pull/178)에서는 10개를 필수로 지정했다. 이어 파티션 복구의 15개를 더해 총 25개로 늘렸다. 이후 파티션 복구 검증은 API 609개 통과·기존 선택적 AI 스킵 13개, **필수 PostgreSQL 25개 전부 실행·통과**였다.

테스트를 모두 스킵 불가로 바꾼 것은 아니다. 외부 AI 환경이 필요한 기존 선택적 테스트와, 반드시 실행해야 하는 데이터 안전성 회귀 테스트를 구분했다. 가드 자체에도 10개의 단위 테스트를 두었다. 10월 21일 검토 브랜치에서는 읽기 전용 검사 사례 27개를 더해 필수 PostgreSQL 목록을 52개로 확대했다.

이 사례에서 CI의 완료 기준은 녹색 표시를 넘어서, 이번 변경을 보호할 정확한 사례가 실제 환경에서 실행됐는지 확인하는 것으로 바뀌었다.

### CI가 발견한 테스트 실행 대상의 공유 문제

읽기 전용 검사 작업의 첫 원격 CI에서는 새 검사 사례가 모두 통과했지만 기존 파티션 복구의 동시 재적용 테스트 하나가 실패했다. 로컬 전체 결과는 669개 통과였고, 첫 원격 결과는 668개 통과·1개 실패였다. 같은 코드가 한 번 통과했다는 사실만으로 이 차이를 무시하지 않았다.

문제는 Alembic 테스트 도구의 공유 상태였다. `Operations.context`는 프로세스 전역 `alembic.op` 실행 대상을 바꾼다. 두 비동기 DB 작업이 번갈아 실행되면 한 작업의 시간대 설정이 다른 연결로 갈 수 있었다. 각 작업이 읽어 온 별도 migration 모듈에 자기 연결의 `Operations`를 직접 묶어 전역 대상을 공유하지 않게 했다.

실제 DB의 병렬 실행과 UTC·기존 기록 확인은 그대로 유지했다. 원래 PostgreSQL 복구 테스트 15개와 별도의 20회 병렬 반복, 총 40회 재적용이 통과했다. 운영 마이그레이션 SQL을 바꾸거나 실패한 테스트를 건너뛴 수정이 아니다. 이 보완은 [PR #181](https://github.com/WhiteMouseDev/HaruKoto/pull/181)에 포함된다.

## 8 파티션을 복구하고 다시 부족해지는 시점을 준비하기

### 운영에서 확인한 문제

10월 19일 읽기 전용 카탈로그 검사에서 복습 이벤트 테이블에 3월부터 6월까지 네 개의 파티션만 확인했다. 현재 월과 다음 월을 포함하는 파티션이 없고 DEFAULT 파티션도 없었다. 이름이나 코드에 유지보수 함수가 있다는 사실만으로 운영의 날짜 범위가 준비돼 있다고 볼 수 없었다.

SAVEPOINT 방어는 답안 저장을 지켰지만 이 이벤트 저장 문제를 해결하지는 않았다. 한편 별도의 레슨·SRS 경로는 원자적 트랜잭션을 사용하므로 퀴즈 한 경로의 방어만 보고 모든 학습이 안전하다고 확대할 수도 없었다.

### 적용 설계

자동 생성 엔드포인트를 즉석에서 호출하지 않고 Alembic 변경으로 2026년 7월부터 2027년 1월까지 일곱 개를 추가했다. 기존 3월부터 6월은 유지해 총 11개가 됐고, 준비된 범위의 끝은 **2027년 2월 1일 00:00 UTC 미포함**이다.

적용 전에는 부모 테이블과 RANGE 키, 소유자, 정확한 자식 범위, RLS와 권한, 인덱스 연결 상태를 검사했다. 이름이 같은 객체가 있다는 이유로 넘기지 않고 다른 부모·범위·소유자라면 중단한다. 잠금 대기는 2초, 문장 실행은 15초로 제한했다.

검토한 동일 SQL을 운영에서 먼저 실행하고 롤백했다. 원래 head와 네 개 파티션, 보호한 메타데이터가 그대로임을 확인한 뒤 같은 변경을 커밋했다. 보호한 관계 식별자와 파일 식별자, 소유권·권한·RLS·인덱스와 Auth·DDL 가드가 전후 동일한지도 확인했다.

기존 고객 행을 스캔하거나 재작성하지 않았고, 과거에 저장되지 못한 이벤트를 추정해 만들지도 않았다. 새 파티션에 학습 기록이 들어온 뒤 자동 downgrade로 삭제하면 데이터 손실이 되므로 파괴적 롤백은 거부한다. 앱을 롤백해도 추가한 파티션은 유지한다.

### 검증과 운영 결과

실제 PostgreSQL 테스트는 UTC 경계와 연말, 비 UTC 세션, 기존 행 유지, 충돌 객체·권한·인덱스 이상, 동시 실행과 잠금 시간 초과를 포함했다. 레슨 제출의 SRS·이벤트 원자 저장과 퀴즈 저장·이어 풀기·완료도 확인했다. 격리한 Prisma 동기화에서는 애플리케이션 스키마와 생성 클라이언트 메타데이터가 바뀌지 않았다.

운영 반영 후 전용 테스트 계정의 로그인과 학습·이어 풀기 검사 28개가 통과했다. 1/3 답안을 저장하고 재로그인해 같은 질문·선택지·답안을 복원한 뒤 3/3·30 XP로 완료했다. 생성한 이벤트 3건은 새 10월 파티션에 저장됐다.

기존 메타데이터와 접근 제한은 유지됐고 익명 Data API 요청도 계속 404로 차단됐다. [PR #180](https://github.com/WhiteMouseDev/HaruKoto/pull/180) 병합과 서버 배포 후 별도의 읽기 중심 검사 15개도 통과했다. DB 적용과 서버 배포는 별도 작업이며 배포 워크플로가 Alembic을 자동 실행한 것은 아니다.

### 10월 21일 구현한 읽기 전용 검사

복구는 완료됐지만 미래 날짜는 계속 다가온다. 다음 단계는 이번 달과 향후 세 달의 실제 범위와 연결 상태, 보안 설정을 읽기 전용으로 검사하는 코드와 회귀 테스트다. 가장 먼 종료일만 보면 중간 월 누락을 놓칠 수 있으므로 연속된 범위와 정확한 월 경계도 확인해야 한다.

검사는 별도 CLI와 내부 라이브러리로 구현했다. 기존 `DATABASE_URL`을 실행 환경에서 명시적으로 전달받고 `.env`나 애플리케이션 시작 설정을 자동으로 읽지 않는다. 실제 `READ ONLY`와 `REPEATABLE READ`, UTC 트랜잭션으로 카탈로그만 조회하고 연결·쿼리·잠금·정리 시간도 제한한다. DB 오류나 불완전한 정보는 정상으로 바꾸지 않고 `UNKNOWN`과 실패 종료 코드로 반환하며 접속 정보나 원본 예외를 출력하지 않는다.

새 단위 테스트 33개와 실제 PostgreSQL 사례 27개가 통과했다. 전체 API 테스트는 669개 통과·기존 선택적 AI 스킵 13개였고, CI 필수 PostgreSQL 사례는 기존 25개에 새 27개를 더해 52개가 됐다. 실제 CLI의 정상 종료와 JSON 출력, 최소 권한 역할의 검사 성공과 학습 행 조회·DDL 거부, 합성 학습 행과 보안 설정 보존도 확인했다. 이 수치는 로컬 폐기용 DB 검증 결과이며 운영에 새 역할을 만들거나 연결한 결과가 아니다.

정상적으로 더 먼 미래 파티션을 준비한 경우는 허용한다. 복구 후 구조를 재현한 로컬 DB 카탈로그를 11월 1일 기준으로 평가하면 2027년 2월이 부족하다는 사전 안내가 나온다. `--as-of`는 평가 날짜를 고정하는 테스트 옵션이며 과거 DB 상태를 조회하는 옵션은 아니다. 플랫폼 Data API 스위치는 DB 카탈로그로 증명할 수 없어 결과에도 `not_verified`로 표시한다.

첫 구현을 검증한 시점에는 정기 실행이나 이메일 알림을 활성화하지 않았다. 운영 DB 권한·계정과 클라우드 설정을 별도로 검토하도록 분리했고, 이후 승인과 운영 적용은 다음 사례에 기록했다. 읽기 전용 검사는 학습 기록과 Data API 설정을 바꾸지 않는다.

정기 운영안은 매일 실행, 부족한 미래 월의 사전 안내, 잔여 60·30·7일에 따른 위험도 상승, 현재 범위 누락의 즉시 경고, 실행 자체의 누락과 접속 실패 감지다. 검사 코드만으로 알림이 발송되지는 않는다. Cloud Scheduler·Cloud Run Job·Sentry 연결에는 별도의 운영 적용과 실제 수신 검증이 필요했다.

파티션 적용과 검증의 로컬 작업 기록: `docs/operations/plans/review-event-partition-repair-proposal-2026-10-19.md`.

## 9 읽기 전용 검사를 운영 점검과 실제 알림으로 연결하기

### 문제와 설계

검사 CLI와 CI가 통과해도 내일 점검이 실행되고 사람이 문제를 알게 되는 것은 별개다. 앱 서버의 강한 DB 계정을 그대로 쓰거나 Scheduler의 호출 성공만 확인하면 최소 권한과 실제 완료를 모두 놓칠 수 있었다.

운영 적용 승인을 받은 뒤 검사 전용 로그인 역할과 Cloud Run 실행 계정, Scheduler 호출 계정을 분리했다. DB 역할은 관리 권한·BYPASSRLS·역할 상속·학습 테이블 및 열·시퀀스·애플리케이션 함수 실행 권한 없이 카탈로그만 확인한다. 기존 PUBLIC 권한을 전역 회수하지 않았으며, 역할의 기본 READ ONLY 설정만으로 권한 부재를 증명했다고 주장하지도 않았다.

접속 문자열은 메모리에서 생성해 Secret Manager로 직접 전달했다. DB 연결, Sentry 전송, 공식 Supabase CA의 버전을 고정하고, Job은 검토한 이미지 digest에 고정했다. Scheduler는 해당 Job의 실행 권한만, 실행 계정은 필요한 Secret 읽기만 갖는다. 기존 API 서버의 DB Secret을 Job에 연결하지 않았다.

Job은 한 작업·자동 재시도 없음·120초 상한으로 설정했다. 내부 CLI는 60초 상한과 종료 신호 처리를 갖는다. DB 검사는 읽기 전용 트랜잭션을 사용하며 접속·SQL·정리 실패는 정상으로 바꾸지 않는다. Sentry에는 고객 데이터나 원본 예외 대신 시작과 종료 check-in만 보낸다. 두 HTTP 수락 응답을 확인한 뒤에도 실제 Sentry 기록과 이메일은 따로 확인한다.

### 연결과 검증 과정에서 확인한 것

DB 연결은 공식 대시보드에서 제공한 Supabase CA와 `verify-full`로 인증서와 호스트명까지 검증했다. 관리형 풀러와 호환되는 표준 SCRAM 설정을 사용했고, 기존 앱 계정 비밀번호나 전체 TLS 설정은 변경하지 않았다. 풀러 뒤의 `pg_stat_ssl`은 관리형 풀러에서 DB로 이어지는 구간을 나타내므로 검사 클라이언트의 TLS를 확인하는 지표로 사용하지 않았다.

권한 검증 쿼리도 수정했다. PostgreSQL은 WHERE 조건보다 타입별 권한 함수를 먼저 평가할 수 있다. 시퀀스 권한 함수를 테이블에 적용하는 오류를 권한 부족으로 오해하지 않도록 CASE로 객체 종류를 분리했다. 이 검증 도구의 수정에 DB 권한 추가는 필요하지 않았다.

전용 계정의 실제 검사와 학습 테이블 `LIMIT 0` 조회 거부를 확인했다. 보안 메타데이터는 적용 전후 같은 해시였고, 기존 역할·권한·RLS·보안 가드·파티션을 변경하지 않았다. 로그인·학습·미완료 퀴즈 조회 등 읽기 중심 검사는 적용 전후 각각 14개가 통과했다. 익명과 로그인 사용자 모두 Data API 요청이 404로 계속 차단됐고, 이 확인 과정의 학습 쓰기는 0건이었다.

### 알림 설정과 알림 수신은 다른 검증이었다

무료 Cron 모니터 한도가 하나여서 유료 예산을 켜지 않고 시험 슬롯과 운영 슬롯을 순차 사용했다. 시험에서는 실제 카탈로그를 11월 1일 기준으로 평가해 내년 2월 범위 부족을 경고로 만들었다. 실제 다음 실행을 생략해 missed check-in도 만들었으며, 정상 점검으로 복구되는 것과 복구 이메일 도착도 확인했다. DB를 손상시키거나 거짓 정상 결과를 보내는 시험은 하지 않았다.

Sentry의 알림 action이 실행돼도 이메일이 즉시 도착하지는 않았다. 프로젝트의 최대 digest 지연은 30분이었다. 다른 HaruKoto API 오류 메일에도 적용되는 설정임을 설명하고 명시적인 승인을 받은 뒤 최대 5분으로 줄였다. 이 값은 이메일 전달의 엄격한 SLA가 아니다. 빠르게 복구된 이슈가 지연 digest에서 제외될 수 있다는 공개 구현도 확인했으므로, 수신 시험은 실제 실패 상태를 유지한 채 진행했다.

오류·실행 누락·복구 이메일을 모두 실제 수신했다. 시험 모니터는 정상 복구한 뒤 비활성화했고, 운영 모니터와 매일 오전 9시 한국 시간 예약만 활성화했다. Scheduler 전용 계정의 수동 호출부터 Cloud Run 작업 완료와 Sentry의 같은 점검 ID가 정상인 것까지 대조했다. 첫 자연 정기 실행은 다음 날 오전 9시 예정으로, 이미 관찰한 수동 실행과 구분했다. 상세한 결과는 [운영 적용 기록](../operations/plans/partition-monitor-deployment-2026-10-21.md)에 남겼다. 설정 스크린샷이나 SDK 이벤트 ID를 실제 이메일 수신의 증거로 대체하지 않는다.

모니터 래퍼의 새 테스트 41개와 독립 검토가 통과했다. [PR #182](https://github.com/WhiteMouseDev/HaruKoto/pull/182)의 최종 CI는 API 710개 통과·기존 선택적 AI 스킵 13개였고, 필수 PostgreSQL 회귀 테스트 52개가 모두 실행됐다. [PR #181](https://github.com/WhiteMouseDev/HaruKoto/pull/181)과 함께 병합·서버 배포했다. 검사·알림 코드를 추가하면서 API 계약이나 마이그레이션은 바꾸지 않았다.

## 10 레슨의 문항 순서와 복습 대상 순서는 같지 않았다

### 문제와 원인

레슨 문항이 정답으로 처리돼도 복습 간격을 갱신하는 대상이 다른 단어나 문법이면 학습 기록의 의미가 달라진다. 이번 조사에서는 학생을 묻는 문항이 `私`의 SRS를 갱신하거나, 문법을 평가한 문항이 단어의 학습 진도로 연결될 수 있는 경로를 확인했다. SRS는 답안에 따라 다음 복습 시점을 계산하는 학습 상태다.

원인은 문항에 명시적인 대상이 없을 때 사용하던 위치 기반 fallback이었다. 문항의 표시 순서와 레슨의 `item_link` 순서가 같다고 가정했지만, 전자는 평가의 순서이고 후자는 소개할 단어·문법의 목록이다. 문항 유형도 하나의 정답 단어 또는 문법을 확정하는 식별자가 아니다. 같은 문법을 여러 유형으로 평가하거나 하나의 문항이 여러 표현을 함께 다룰 수도 있다.

### 표시 순서 대신 검토한 대상을 명시하기

원본 JSON의 각 문항에 검토한 어휘·문법 카탈로그의 순서 번호를 명시했다. 원본에는 환경마다 달라지는 DB UUID를 넣지 않는다. 시드가 레벨과 카탈로그 순서로 해당 환경의 UUID를 찾아 문항의 `vocabulary_id` 또는 `grammar_id`로 해석한다. 문항 표시 순서는 이 해석의 입력으로 쓰지 않는다.

원본 81개 레슨의 405개 문항에서 문구·정답·선택지는 보존하고 대상 메타데이터를 보완했다. 400개 문항에는 명시적인 복습 대상을 지정했다. 단일 대상에 귀속할 수 없는 다섯 문항에는 검토 이유인 `srs_skip_reason`을 두었다. 이 다섯 문항도 채점과 결과에는 포함하고 SRS 갱신에서만 제외한다. 메타데이터가 없다는 이유로 자동 제외하지 않는다.

서버는 모든 문항의 귀속을 먼저 검사한다. 대상 UUID는 같은 레슨의 항목 링크에 정확히 하나 연결돼 있어야 한다. 대상 누락, 어휘·문법의 동시 지정, 다른 레슨의 대상, 중복 링크, 대상과 제외 사유의 동시 지정은 409로 실패한다. 이 검사는 SRS 등록과 진도 쓰기 전에 끝나야 한다. 일부 문항만 갱신한 뒤 잘못된 매핑을 발견하는 순서는 허용하지 않는다.

기존 소개 목록에 없는 추가 문법 대상 17개는 `is_core=false` 링크로 보완했다. 기존 링크를 지우거나 순서를 바꾸지 않는 추가 방식이다. 다만 기존 소개 화면과 SRS 등록도 이 링크들을 사용하므로 non-core 표지만으로 화면과 등록에서 자동 제외되지는 않는다. 이 부수 효과를 승인 범위에 포함했고, 핵심 문법과 보조 항목의 시각적 구분은 별도 UX 검토로 남겼다.

### 현재 설계와 과거 기록을 구분하기

운영에서는 읽기 전용으로 복습 이벤트 94건을 확인했다. 범위는 계정 세 개와 레슨 열 개였고, 현재 어휘 진도 행은 62개였다. 94건 중 77건의 대상은 이번 검토안과 달랐고 17건은 일치했다.

이 차이를 **확정된 과거 오기록 77건**으로 표현하지 않는다. 이벤트에는 당시 문항 순서와 답안, 레슨 시도 ID, 콘텐츠 버전이 없어 어느 문항이 어느 버전에서 제출됐는지 정확히 재생할 수 없다. 현재의 검토안과 다르다는 사실과 당시 실제 정답 대상이 틀렸다는 증명은 구분해야 한다.

따라서 기존 이벤트 94건과 현재 진도 62개를 추정해 다시 쓰지 않고 보존했다. 기존 점수·XP·연속 학습일도 유지했다. 이미 남아 있는 데이터의 범위와 한계를 기록하고, 새 제출부터 대상이 명확한 경로를 사용하도록 전환했다.

### 회귀 테스트와 운영 전환 상태

전체 API 테스트는 757개 통과·기존 선택적 스킵 13개였다. 필수 PostgreSQL 회귀 테스트는 기존 52개에 새 아홉 개를 더한 61개가 스킵 없이 통과했고, 원본 콘텐츠 검증용 Node 테스트 여덟 개도 통과했다. 문항과 링크의 순서를 섞어도 같은 대상에 연결되는지, 잘못된 귀속이 모든 쓰기 전에 거부되는지, 405개 원본 문항이 환경별 식별자로 해석되는지 검증했다.

같은 문법을 평가하는 문항이 세 개이면 SRS를 세 번 갱신하는 기존 정책은 유지했다. 이번 변경의 목적은 대상 식별을 바로잡는 것이다. 문항별 갱신을 레슨당 한 번으로 합치는 정책 변경은 포함하지 않았다.

초기에는 코드와 원본 메타데이터만 준비하고 사전 검토를 기다렸다. 사용자 승인 후 [PR #184](https://github.com/WhiteMouseDev/HaruKoto/pull/184) 병합·서버 배포와 새 리비전 전환을 마쳤고, **10월 21일 13:19:55 KST에 운영 콘텐츠를 보정했다. 이후 실제 로그인·레슨·이어 풀기 검사 45개도 모두 통과했다.** 기존 서버의 제외 사유 미지원을 고려해 짧은 작업창을 사용했다. 전환과 보정 사이 미보정 제출은 409로 거절될 수 있어 무중단으로 안내하지 않았다. 전체 시드 재실행이나 과거 학습 기록 교정은 하지 않았다. [상세 적용 기록](../operations/plans/lesson-review-target-fix-2026-10-21.md)에 전환·보존·장애 처리와 실제 검증을 남겼다.

### 운영 적용 전에도 준비와 실제 전환을 구분했다

운영 전용 보정 도구는 폐기용 PostgreSQL 18에서 원자성, 60초 제한, 변경 전 상태 비교와 기존 기록 보존을 검증했다. 실제 운영 READ ONLY 사전 검사에서도 문항·링크·검토 원본과 기존 기록의 보존 조건이 일치했다. 이 확인은 콘텐츠를 쓴 결과가 아니라, 쓰기를 시작해도 되는 사전 조건을 확인한 결과다.

새 서버 health가 200이어도 기존 고정 트래픽은 자동으로 이동하지 않았다. 승인한 수동 전환으로 13:14:24 KST에 새 리비전 트래픽을 100%로 옮기고 기존 요청의 최대 300초보다 여유 있게 기다린 뒤 보정했다. 이후 기능 검증은 새 전용 QA 계정의 이메일·비밀번호 Auth와 공통 JWT/API 경로로 실행했다. 실제 아이폰 화면이나 SNS 제공자 UI 로그인 확인과는 구분한다.

연결 도구의 새 Python에서 공식 CA 검증이 거부됐을 때는 운영과 같은 Python 버전으로 실행해 CA·호스트명 검증을 유지했다. TLS 검증을 끄지 않았다. 공유 배포 워크플로 비활성화는 승인 검토에서 거절돼 실행하지 않았으며, 기존 자동 배포와 승인된 트래픽 전환 경로로 진행했다.

### 콘텐츠 반영과 기존 기록 보존

운영에서는 81개 레슨의 문항 대상 메타데이터와 링크 17개만 반영했다. 기존 링크 548개를 모두 보존해 총 565개가 됐고 문구·정답·보기·음성·공개 상태를 유지했다. 기존 기록 14개 테이블과 레슨 발생 이벤트 94건 범위의 보존 검사 15개는 트랜잭션 안과 커밋 뒤 별도 READ ONLY 감사에서 같은 개수와 SHA를 보였다. 레슨 이벤트 94건과 영향을 조사한 진도를 추정해 다시 쓰지 않았다.

RLS·권한 카탈로그 지문도 전후 같았다. 읽기 전용 재실행의 예정 변경은 레슨·링크 모두 0개여서 동일 보정을 반복할 필요가 없음을 확인했다. 사후 기능 검증 뒤에도 새 QA 활동만 제외한 기존 범위의 15개 개수·SHA가 최초 baseline과 모두 같았다. 새 계정과 활동은 감사 증거로 유지하고 기존 계정·세션은 수정하지 않았다.

[main CI](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/39542519102)의 일곱 잡과 [서버 배포](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/39542519133)가 성공했다. 운영 도구·QA 보조 코드의 회귀 23개도 같은 Python 환경에서 통과했다. 로컬 회귀와 실제 운영 기능 검증은 각각 수행한 결과로 기록한다.

### 틀린 답안을 다른 단어에 기록하지 않는지 실제로 확인하기

새 QA 계정으로 첫 레슨의 학생 문항만 의도적으로 틀려 4/5로 완료했다. DB를 읽기 전용으로 다시 확인하니 はじめまして에는 정답 한 번, 学生에는 오답 한 번, 평가한 문법에는 정답 세 번이 기록됐다. 私는 소개된 항목으로 등록됐지만 정답·오답과 FSRS 반복은 모두 0이었다. 점수만 정상인지 보는 데서 끝내지 않고 오답이 실제 학생 항목에 귀속되는지 확인한 것이다.

같은 계정에서 두 문항 퀴즈의 첫 답안을 저장해 1/2·50%를 확인했다. QA 세션만 로그아웃하고 새로 로그인한 뒤에도 같은 문제·선택지·답안이 복원됐고 첫 문제를 건너뛴 다음 문제부터 이어졌다. 반복 resume도 저장 답안을 바꾸지 않았다. 2/2·100%·20 XP로 완료한 뒤 통계와 프로필, 미완료 제안에서 사라진 상태까지 다시 읽었다.

계정 생성 1개·로그인과 조회 18개·레슨 제출 3개·정확한 DB 대상 확인 6개·이어 풀기 17개를 합친 45개 운영 검사가 모두 통과했다. Data API는 대시보드에서 비활성화를 재확인했고 익명·로그인 요청 모두 404였다. 보호 API의 익명 요청은 401로 거부됐다. 레슨 상세 응답에는 정답 키나 내부 대상 UUID가 노출되지 않았다.

13:27 KST의 사후 감사에서도 신규 QA 부분을 제외한 기존 기록은 모두 같았다. 새 리비전 전환 뒤 검사 시점까지 ERROR·HTTP 5xx 로그 조회 결과는 0건이었다. 검증용 임시 태그는 제거하고 최신 리비전 100%와 기존 배포 워크플로 활성 상태를 남겼다. 이 결과는 확인한 시간 구간과 공통 API 경로의 증거이며 모든 기기 화면이나 미래 오류 부재를 보장하지 않는다.

같은 문법 세 문항을 SRS 세 번으로 세는 기존 정책과, 문항·답안·콘텐츠 버전이 없어 정확히 재생할 수 없는 과거 기록은 후속 검토로 유지했다. 대상 식별을 고쳤다는 이유로 과거 상태를 추정해 다시 쓰거나 커리큘럼 정책까지 함께 바꾸지 않았다.

## 11 이번 오답 복습과 기한 복습의 약속을 구분하기

### 문제와 확인한 원인

결과 화면은 원본 퀴즈 ID로 오답 목록을 조회하지만 복습 버튼은 원본 ID 없이 일반 복습을 시작했다. 서버의 일반 복습은 복습 기한이 된 항목을 고르므로, 화면에 보인 이번 오답과 다음 퀴즈의 항목이 달라질 수 있었다. 저장된 학습 대상을 잘못 연결하던 10번 문제와는 다른 호출 범위 문제다.

기존 퀴즈 시작은 다른 미완료 세션을 자동 완료하고 XP를 반영하는 정책도 수행한다. 이 경로에 문항 필터만 추가하면 기존 기록을 보존하는 오답 전용 시작과 맞지 않는다. 현재 API에 원본 세션을 지정하는 계약이 없음을 확인한 뒤 사용자에게 전용 API 추가안을 먼저 제시했고, 명시적 승인 후 구현을 시작했다.

문법 오답에는 별도의 표시 문제도 있었다. 저장 스냅샷의 문법 표현은 `pattern`인데 오답 목록은 `word`만 읽었다. nullable 응답을 문자열로 읽는 앱에서는 목록 전체가 실패할 수 있었다. 같은 응답 키를 유지하며 문법 표현을 올바르게 채우고, 표시 목록과 실제 출제 대상의 판정도 맞췄다.

### 원본을 수정하지 않고 새 복습을 시작하기

새 API는 `sourceSessionId` 하나만 받는다. 서버가 본인 소유의 완료한 퀴즈와 문항별 최초 저장 답안을 확인하고 원본 스냅샷에 속한 오답만 선택한다. 임의 문항 ID·유형·레벨을 앱이 지정하지 않는다. 같은 원본의 복습이 진행 중이면 새로 만들지 않고 저장한 답안과 함께 그 복습을 반환한다.

새 복습 세션의 기존 JSON에만 원본 참조와 모드를 붙인다. 원본·다른 미완료 세션·원본 점수와 답안을 다시 쓰지 않고, 기존 시작의 자동 완료도 호출하지 않는다. 사용자가 새 복습을 실제로 푼 답안부터 기존 학습·XP 정책이 적용된다. 새 테이블·컬럼·권한·Data API 변경은 필요 없다.

중복 방지는 같은 복습이 미완료인 동안의 보장이다. 완료 또는 기존 정책에 따른 종료 후 다시 시작하면 새 시도이며 완료 후까지의 영구 멱등성으로 설명하지 않는다. 첫 지원은 단어·문법·한자·듣기의 정상 선택형이다. 저장 구조가 다른 가나·매칭·빈칸 특수 모드·배열을 일반 문제로 바꿔 내지 않는다.

### 오류를 콘텐츠 없음으로 바꾸지 않기

초기 퀴즈 요청 실패를 빈 문항 상태로 바꾸던 처리를 분리한다. 기존 세션 복구와 오답 목록은 같은 대상을 다시 조회할 수 있게 하고, 생성 여부가 불확실한 일반 퀴즈 시작 요청은 자동 재전송하지 않는다. 세션별 목록 상태와 비동기 작업의 수명을 분리해 뒤늦게 도착한 다른 퀴즈의 응답이 현재 목록을 덮지 않게 한다.

신규 오답 API는 진행 중 복습 재사용을 전제로 같은 원본으로 재시도할 수 있다. 네트워크 오류·실제 오답 없음·미지원 유형은 서로 다른 상태로 안내하며 실패를 일반 기한 복습으로 우회하지 않는다.

### 검증 결과와 출시 범위

승인한 API·모바일 소비자·회귀 구현을 완료했다. API 전체 810개 통과·기존 선택적 AI 13개 스킵, 새 PostgreSQL 24개와 완료 시 stageId 차단 후 관련 77개가 통과했다. 기존 61개와 새 24개를 합한 필수 PostgreSQL 85개는 CI에서 누락·스킵·실패를 허용하지 않는다. 게이트 자체 테스트 10개도 통과했다.

모바일 최초 구현 전체 580개 테스트와 정적 분석이 통과했다. 출시 통합 중 320px·글자 200%에서 오답 제목이 넘치는 문제가 드러나 네 개의 접근성 회귀를 추가했다. 최종 CI는 모바일 584개와 Android 빌드를 포함해 일곱 잡 모두 통과했다. 실제 CTA에서 원본 오답만 복습하고 새 시도에만 답안을 저장한 뒤 원래 결과의 점수와 목록으로 돌아오는 통합 흐름도 확인했다. 첫 문제부터 연속되지 않은 저장 답안은 ID로 구분하고, 모두 저장된 세션은 답안을 다시 내지 않고 결과 저장만 재시도한다.

기존 모든 OpenAPI path·schema는 그대로이며 새 path·요청 schema 각 하나와 생성 타입 58줄만 추가됐다. Admin의 실제 타입 소비와 production build, Web 타입 검사도 통과했다. 명세를 처음 생성할 때 원본 venv가 다른 작업 폴더를 import한 문제는 구조 비교가 검출했다. 관리 작업 트리를 명시해 재생성한 최종 결과에는 무관한 API 변경이 없다.

위 구현 검증과 별도로 사용자가 출시를 승인했고, [PR #186](https://github.com/WhiteMouseDev/HaruKoto/pull/186)을 10월 21일 14:56:40 KST에 병합했다. 정규 서버 배포가 성공한 뒤 새 리비전의 실제 트래픽 100%, health 200, 이미지 외 런타임 설정 보존을 확인했다. 기존 학습 기록의 15개 범위와 권한·RLS 정책의 배포 전후 집계 해시도 모두 같았다. Data API는 계속 차단됐다.

새 QA 두 계정으로 운영 기능 검사 85개와 오류 응답 재확인 1개가 통과했다. 단어 원본의 오답 2개와 스마트 문법 원본의 오답 1개만 각각 복습됐고 다른 퀴즈나 정답 문항은 섞이지 않았다. 동시 시작 네 요청과 성공 응답의 클라이언트 폐기 후 재시도가 같은 복습을 재사용했다. 1/2·50%에서 QA 로그아웃·재로그인한 뒤 다음 문제부터 풀어 2/2·20 XP로 완료했으며 반복 완료의 추가 XP는 0이었다. 원본 점수와 다른 일반 미완료 퀴즈도 유지됐다. 검증 후 새 QA 두 계정만 제외한 기존 기록·권한·RLS 집계 해시는 여전히 같았다.

운영 검증 도구에도 잘못된 가정이 있었다. 정상 401 응답을 FastAPI 기본 `detail` 형식으로 검사했지만 제품은 기존 공통 오류 핸들러의 `error/code/message/details`를 사용했다. 제품을 도구에 맞춰 바꾸지 않고 실제 핸들러·TestClient로 계약을 확인해 도구를 수정했다. 초기 실패 증거와 요청 표식을 보존하고 거부된 무인증 요청만 명시 재확인했으며 정상 계정 생성·학습 요청은 반복하지 않았다. 실제 서버 장애를 주입하거나 이 도구의 오판을 제품 장애로 보고하지 않았다.

아이폰 빌드는 기존에 승인했지만 아직 별도 커밋으로 정리하지 않은 UI·답안 저장 개선과 이번 변경을 함께 보존해야 했다. 깨끗한 main만 빌드하면 답안 저장 대기열·완료 재시도나 줄여둔 효과가 되돌아갈 수 있었다. 원본 파일 해시와 3way diff를 남겨 이번 기능 범위만 통합했고, 독립 검토와 통합본 전체 687개 테스트·정적 분석·release 서명 검증을 통과했다. 최초 설치는 기기 잠금에 따른 개발 디스크 마운트 오류로 막혔지만, 사용자가 홈 화면을 켜둔 뒤 15:10:37 KST에 업데이트가 성공했다. 앱 실행·화면 캡처와 기존 로그인 홈 유지도 확인했다. 아이폰 확인 범위는 업데이트·실행·기존 로그인 유지까지다. 이후 사용자가 테스트 계정으로 로그인하고 Simulator에서 대신 풀어 달라고 요청해 오답 복습·오류 재시도·앱 재실행 복원 세 항목을 그 환경에서 완료했다. 아이폰 실기기 터치를 완료한 것으로 서술하지 않는다. [상세 설계와 적용 기록](../operations/plans/session-wrong-answer-review-2026-10-21.md)에 현재 상태를 남겼다.

### Simulator에서 실제 실패와 프로세스 재시작까지 확인하기

사용자가 로그인한 테스트 계정으로 열 문제를 풀어 8/10·80%·80 XP를 기록했다. 오답은 もう와 先였다. 실행 중인 앱의 Dio API 주소만 닫힌 loopback HTTPS로 일시 변경해 오류·재시도 화면을 확인했고, 공식 주소 복원 뒤 같은 ‘다시 불러오기’로 정확한 두 오답이 원본 순서대로 출제됐다. 복습 세션은 하나였다. OS·TLS·아이폰·서버 설정은 바꾸지 않았다.

오류 화면에서는 진단용 Dio 영문이 그대로 노출되는 문제를 발견했다. 전송 실패의 사용자 안내를 한국어로 매핑하는 모바일 네 파일의 보완을 준비하고 실제 hot reload 화면에서 ‘서버 응답이 늦어지고 있어요. 잠시 후 다시 시도해 주세요.’를 확인했다. 새 회귀 13개를 포함한 관련 53개, 깨끗한 체크아웃 전체 597개와 기존 개선을 보존한 통합본 전체 700개 테스트, 분석·포맷이 통과했다. 로컬 실패 주입을 실제 서버 장애로 보고하지 않았다. 당시 별도 변경으로 준비한 [PR #188](https://github.com/WhiteMouseDev/HaruKoto/pull/188)은 이후 사용자 승인으로 병합하고 아이폰에 반영했다.

한 문제를 맞힌 뒤 홈의 1/2·50%를 확인하고 실제 `simctl terminate`·`launch`로 새 프로세스를 실행했다. 재설치·로그아웃 없이 로그인과 같은 진행률이 유지됐고 안내의 1/2에서 2/2의 先부터 이어 2/2·100%·20 XP로 완료했다. 원본 스냅샷과 이후 다섯 차례 SELECT 전용 감사에서 부분 저장·재실행 답안 해시는 같았고 원본 전체 행·답안 해시와 8/10 결과도 유지됐다. 새 답안과 XP는 정상 학습 활동이므로 모든 과거 학습 상태가 불변이었다고 확대하지 않는다.

화면 문구 후속도 남았다. 결과의 ‘홈으로 돌아가기’는 원래 퀴즈 탭으로 돌아가 하단 홈 탭을 추가로 눌렀고, 재실행 뒤 오답 복습 헤더는 ‘N5 단어 퀴즈’로 표시됐다. 실제 先 대상과 저장은 정확했으며 이 두 탐색·제목 문구는 별도 UX 범위다. 앞선 아이폰 설치, Simulator의 세 항목 조작 검증, 이후 한국어 안내를 포함한 아이폰 업데이트와 실제 로그인 홈 확인을 구분한다.

### 한국어 안내를 포함한 아이폰 업데이트

사용자 승인 후 문서의 [PR #187](https://github.com/WhiteMouseDev/HaruKoto/pull/187)과 한국어 안내의 [PR #188](https://github.com/WhiteMouseDev/HaruKoto/pull/188)을 각각 17:23:43·17:25:38 KST에 병합했다. 안내 수정의 CI는 모바일 597개와 Android APK를 포함해 통과했고 [병합 후 main CI](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/39569180047)도 성공했다. 기존 개선을 보존한 통합본의 700개 테스트와 소스·설정 해시를 유지하고, 실제 release AOT 산출물에 한국어 안내가 포함됨을 확인했다.

잠금 해제 뒤 17:32경 같은 앱을 업데이트하고 17:32:25 실행 이후 실제 아이폰 홈의 기존 로그인과 N5 숙련도 2%를 확인했다. 앱을 지우거나 로그아웃하지 않았다. 이번 폰에서 고의 오류나 새 퀴즈를 실행한 것은 아니며, 한국어 안내의 실제 오류 화면과 복습 재개 조작은 앞선 Simulator 증거다.

업데이트 전후에는 QA 제외 없이 전체 계정의 15개 기존 범위 개수·전체 행 SHA와 권한·RLS 지문이 같았다. 이 비교는 Simulator에서 정상 학습한 이후의 별도 기준선이다. 익명 Data API는 계속 404였고 기존 서버 리비전과 health도 유지했다. 모바일 안내 수정만을 위해 서버를 다시 배포하거나 DB·설정을 변경하지 않았다.

## 12 가나 조회 실패를 학습 화면 전체의 실패로 만들지 않기

### 문제와 재현

학습 탭은 가나 진행률에 사용하는 대시보드의 첫 로딩에서 화면 전체를 먼저 반환해 별도 챕터·복습 조회의 시작을 늦췄다. 가나 표시가 켜진 사용자의 최초 대시보드 요청이 실패하면, 값이 없는 상태를 가나 미완료처럼 처리하고 `dashboard!`를 읽어 null 예외도 발생했다. 서로 다른 데이터 영역을 하나의 조회 성공 여부에 묶은 결과였다.

수정 전 위젯 회귀 두 개로 이를 재현했다. 하나는 null 확인 예외로 실패했고, 다른 하나는 대시보드 대기 중 기대한 챕터 조회 한 번이 실제로는 0번인 것을 확인했다. 정상적인 실패 상태를 보여주는 것과 다른 학습 영역이 실제로 동작하는 것을 함께 검증해야 했다.

### 독립된 상태와 재시도

StudyPage와 분리한 가나 영역의 두 화면 소스에서 로딩·오류·정상·정보 없음 상태를 따로 처리하고, 레슨·복습·챕터는 각자의 조회 상태로 사용할 수 있게 했다. 실패하거나 아직 모르는 진도를 0/0이나 0%로 추측하지 않는다. 회귀의 합성 정상 응답 0/92와 12/92는 표시하고, HTTP 200이어도 진도 정보가 없으면 조회 실패와 다른 ‘정보 없음’으로 안내한다. 가나의 재시도는 대시보드만 다시 조회하며, 다른 영역의 재조회나 답안 저장 요청을 유발하지 않게 한다. 기존 `/study/kana` 진입과 로컬 가나 표시 설정도 유지한다.

### 검증 범위와 적용 상태

Dio의 인위적 타임아웃과 합성 저장소로 새 회귀 20개와 기존 StudyPage 회귀 네 개, 관련 24개가 통과했다. 실제 챕터의 레슨 행과 추천 배너에서 GoRouter·레슨 화면·상세 GET으로 이동하고 기존 가나 열기도 확인했다. 이전 완료·미완료 데이터를 가진 재조회 대기와 실패·성공, 320px 화면·200% 글자·두 테마·48px 터치와 접근성 의미도 검사했다. 인증 provider 접근 시 실패, SharedPreferences 표식 보존과 GET 외 요청 거부로 로그인·설정·쓰기 경로를 건드리지 않는지 확인했다. 최종 fixture로 깨끗한 체크아웃의 관련 24개·전체 617개와 기존 UI 개선을 보존한 원본 통합본의 관련 32개·전체 720개 테스트가 모두 통과했다. 원본 관련 32개는 신규 20개·기존 여덟 개·접근성 네 개다. 두 체크아웃 모두 정적 분석 오류가 없었고 포맷 검사도 각각 529개·548개 파일에서 변경 0개였다. 독립 코드 검토도 통과했다. 서로 다른 체크아웃이나 관련·전체 검사 수를 합산하지 않는다. 원본의 기존 647개 다른 소스와 기존 테스트·환경 파일, 앞서 설치한 PR #188 아이폰 release 번들의 해시도 유지돼 이번 화면 범위만 달라졌음을 확인했다.

먼저 모바일 화면 수정과 회귀 구현·로컬 검증을 완료했다. 초기 승인은 이 구현 범위까지였다. API·DB·인증·파서·네트워크 설정·환경 계약·의존성·플랫폼을 바꾸지 않고 기존 학습 기록을 재계산하지 않는다. 초기 구현 검증에서는 운영 DB 조회·쓰기와 기기 설치를 하지 않았고 17:54:20 KST의 익명 Data API HEAD는 404였다. 이는 차단 확인이며 설정을 바꾼 결과가 아니다. 이 최초 로컬 결과를 PR 병합·서버 배포·아이폰 설치의 증거로 대신하지 않았다. [설계와 검증 기록](../operations/plans/kana-study-partial-failure-2026-10-21.md)에 현재 상태를 남긴다.

### 승인 후 병합과 실제 기기 반영

이후 사용자가 병합·아이폰 반영과 가나 실패 재시도·다른 레슨 진입 확인을 승인했다. [PR #190](https://github.com/WhiteMouseDev/HaruKoto/pull/190)을 19:01:26 KST에 병합하고, 기존 개선을 보존한 원본 통합 release 빌드와 서명·소스·환경 해시, AOT 가나 안내 포함을 확인했다. 기기 잠금으로 설치를 기다린 뒤 19:50–19:51 KST경 같은 앱을 아이폰에 업데이트해 로딩 뒤 기존 로그인 홈·연속 학습 카드·N5 숙련도 2%를 확인했다. 앱 삭제·로그아웃·초기화와 시작 오류는 없었다.

전용 Simulator의 메모리 가나 표시만 켜고 대시보드 GET만 실패시켜 실제 오류 화면을 확인했다. 같은 상태에서 ‘공통점이 반가울 때’ 레슨 본문과 상세 HTTP 200은 정상으로 열렸다. fault를 복구하고 같은 ‘다시 불러오기’를 누르자 버튼이 로딩 동안 비활성화됐고 실제 대시보드의 0/208로 복구됐다. 이 재시도에서 대시보드 요청은 11→12, 다른 GET은 3→3, GET 외 요청은 0이었다. 앞선 실패 11회에는 기본 자동 재시도가 포함돼 수동 열한 번을 의미하지 않는다. 원래 주소·인터셉터·메모리와 저장 설정을 복구한 뒤 기존 로그인과 정상 홈, 소스·release 산출물 불변을 확인했다.

### GET 요청만으로 쓰기 부재를 단정할 수 없었다

운영 SELECT 감사에서는 15개 범위의 수와 14개 해시가 같았지만 daily_missions 561행의 전체 해시는 달랐다. 19:36:11 KST 추가 검사에서 승인된 테스트 계정의 당일 미션 한 행의 집계 current_count만 가상 교체한 20개 후보 중 하나가 변경 전 전체 SHA와 정확히 일치했다. 실제 DB를 수정하거나 이전 값·계정·개인 행을 출력하지 않았다. 해시 기준으로 나머지 미션 행·필드와 원본 퀴즈·답안·레슨·복습·XP는 유지됐고 차이는 미션 집계 한 필드였다.

기존 미션 GET의 집계 동기화와 부합하지만 원인이 된 HTTP 요청까지 특정하지 않았다. Non-GET 요청 0회를 앱 서버 쓰기 0회나 모든 기록 완전 불변으로 바꾸지 않는 이유다. 도구 쓰기·DB 권한·설정 변경과 추정 보정은 없었고 Data API 404·health 200은 유지됐다. 기기 업데이트 후 19:51:02 KST 감사는 Simulator 이후 기준선과 15개 수·전체 행 SHA가 모두 같았다. 최초 기준선과는 14개 SHA 및 앞서 설명한 미션 집계 한 필드 차이가 유지됐다. 이 두 기준을 섞지 않았다. 아이폰은 실제 설치·기존 로그인 홈까지 확인했고 가나 오류·재시도와 다른 레슨 진입의 실제 조작은 Simulator에서 검증했다. 폰에서 오류를 강제로 재현했다고 확대하지 않는다. [적용 기록](../operations/plans/kana-study-partial-failure-2026-10-21.md)에 범위를 구분했다.

## 13 레슨의 이어하기와 복습 정책 비교를 서로 다른 문제로 다루기

### 같은 기기에서 학습한 위치를 기억하기

레슨을 중단한 뒤 앱을 다시 켰을 때 필요한 것은 완료한 레슨의 표시만이 아니다. 어느 단계의 몇 번째 항목이었는지, 아직 확정하지 않은 선택과 배열·매칭도 이어져야 한다. 일반 퀴즈의 서버 이어 풀기와 다른 문제여서, 기존 로그인과 서버 기록을 유지하는 계정·레슨별 로컬 체크포인트로 설계했다.

저장에는 위젯 단계·위치·확정 답안·현재 입력과 섞인 배치를 포함하고 인증 토큰은 넣지 않는다. 콘텐츠 서명과 서버 진행을 확인해 내용이 바뀐 답안이나 이미 완료된 임시 상태를 복원하지 않게 한다. 쓰기를 직렬화해 늦게 끝난 저장이 최신 상태나 완료 처리를 덮지 않게 하고, 실패한 저장은 저장됐다고 안내하지 않는다. 같은 설치·같은 계정의 복원 범위이며 기기 간 동기화나 앱 삭제 후 복원은 포함하지 않는다. OS가 쓰기 완료 전에 프로세스를 강제 종료한 경우까지 보장한다고 표현하지 않는다.

### 응답을 잃은 제출은 자동으로 다시 보내지 않기

레슨의 기존 제출 API에는 멱등 키가 없어 같은 POST를 다시 보내면 시도와 복습 상태도 다시 갱신될 수 있다. 따라서 제출 직전의 pending 상태를 저장하고, 결과를 확인하지 못한 제출을 복원할 때 자동으로 재전송하지 않는다. 최신 GET에 완료·시도가 반영돼 있으면 서버 기록을 따르지만, GET 결과가 그대로여도 앞선 요청이 나중에 반영될 수 있어 안전한 재전송의 증거로 삼지 않는다. 확인되지 않은 답안을 보존하고 읽기 전용 상태 확인을 제공하는 경계다. 멱등 제출을 추가하려면 별도 API·DB 검토가 필요하다.

### 복습 간격의 차이는 먼저 현재 동작으로 고정하기

이어하기와 함께 레슨·퀴즈의 SRS를 비교했지만, 정책을 바꾸지는 않았다. 실제 갱신 함수에 같은 상태·정오·반응시간·고정 시각을 주고 DB 경계만 대체한 비교 회귀로 현재 차이를 드러냈다.

| 같은 조건에서 비교한 사례           | 레슨의 현재 결과         | 퀴즈의 현재 결과                    |
| ----------------------------------- | ------------------------ | ----------------------------------- |
| 초기 LEARNING에서 정답              | LEARNING, 다음 기한 +3일 | LEARNING, 다음 기한 +1일            |
| 새 항목의 실제 등록 경로 뒤 첫 정답 | LEARNING, +3일           | PROVISIONAL, +1일                   |
| 초기 LEARNING에서 오답              | 다음 기한 +1일           | 다음 기한 +10분                     |
| 일부 장기 REVIEW·MASTERED에서 오답  | RELEARNING, +1일         | 이전 간격에 따라 RELEARNING, +2~3일 |

반응시간·메타데이터·같은 날 반복과 날짜 경계의 차이도 확인했다. 이 결과는 어떤 간격이 더 좋은지 입증하지 않으며, 사용자들의 기존 복습 기한을 보정할 근거도 아니다. DB 없는 비교 회귀 90개가 통과했고 API 전체는 900개 통과·기존 admin fixture 스킵 13개, 실제 PostgreSQL 필수 회귀는 85개 모두 무스킵 통과했다. Ruff 295개 파일과 mypy 172개 소스도 오류가 없었다. 각 검증 범위의 수를 합산하지 않는다.

### 현재 완료한 범위와 남은 검증

모바일 구현과 회귀를 마치고 전체 657개가 통과했다. 기존 617개와 신규 40개이며 정적 분석 오류 0개·포맷 539개 파일 변경 0개도 확인했다. 계정·레슨별 저장, 콘텐츠와 서버 가드, 입력·배치와 실패·제출 경계를 다룬 검사다.

별도 오프라인 native QA 앱은 실제 SharedPreferences를 사용하되 서버 통신·Supabase 초기화를 차단하고 identity를 합성 값으로 대체했다. 재설치 없이 실제 OS 종료·실행으로 어휘 2/3, 문법 2/2, 이해 체크 2/2의 선택 d와 기존 답안, 매칭 한 쌍과 왼쪽 선택·양쪽 배열, 중복 は 두 개를 포함한 배열 2/3과 남은 보기 순서를 복원했다. 합성 시작 한 번·제출 0번을 관찰했다. hot reload나 합성 메모리만으로 복원을 주장하지 않았고 운영 로그인·서버 저장의 증거로도 바꾸지 않는다.

마지막 안내 문구 한 줄을 포함한 최종 native 빌드로 업데이트한 뒤 배열의 は 두 개·2/3 입력·남은 보기 순서를 재확인했고 추가 OS 종료·재실행 뒤에도 유지됐다. 어휘·문법·이해 체크·매칭 네 유형은 안내 수정 전의 동일 복원 로직에서 검증했고 최종 빌드는 배열을 다시 확인했다. 모든 유형을 마지막 산출물에서 반복했다고 확대하지 않는다. 최초 구현 검증에서는 서버 정책·API·DB·기존 기한과 이력·실제 운영 Data API·권한·설정을 바꾸지 않았고 운영 데이터 조회·수정, PR 병합·서버 배포·아이폰 실기기 설치도 하지 않았다. 당시 승인은 구현과 회귀 테스트 범위였다. [설계와 검증 기록](../operations/plans/lesson-local-resume-and-srs-comparison-2026-10-21.md)에 로컬 native 확인 결과와 적용 범위를 기록했다.

### 승인 후 병합과 실제 폰의 레슨 재진입

이후 사용자 승인으로 [PR #192](https://github.com/WhiteMouseDev/HaruKoto/pull/192)을 21:59:02 KST에 병합했고 main CI도 성공했다. 기존 UI·저장 개선을 보존한 원본 통합본은 전체 760개와 관련 53개, 정적 분석 오류 0개·대상 23개 파일 포맷 변경 0개를 확인했다. 최초 깨끗한 체크아웃의 657개와 합산하지 않는다. 기존 release를 확인·보관하고 같은 서명·권한·환경의 새 release 빌드를 완료했다. 22:10경 아이폰을 업데이트하고 실제 기존 로그인 홈·N5 숙련도 2%를 확인했다. 앱 삭제·로그아웃·초기화는 하지 않았다.

사용자가 ‘공통점이 반가울 때’의 단어 2/5 ‘音楽/음악’을 본 뒤 X로 닫고 같은 레슨을 다시 열었다. Codex가 실제 캡처에서 2/5와 이어하기 안내를 확인했다. 이후 Codex가 앱 프로세스를 종료·재실행했고 새로운 프로세스와 기존 로그인 홈을 확인했다. 22:16:21 사용자가 동일 레슨에 재진입한 뒤 실제 캡처에서 2/5의 音楽·おんがく·음악과 기기에 저장된 위치에서 이어간다는 안내를 확인했다. 재설치 없이 화면 재진입과 OS 재실행 뒤 재진입 모두 복원됐다. 실제 폰에서는 어휘 학습 단계만 확인했고 연습·제출은 누르지 않았다. 다른 네 유형의 실제 프로세스 복원은 앞선 오프라인 native QA의 결과다. 이번 추가 Simulator는 준비만 했고 실행하지 않았으며 앞선 오프라인 다섯 유형 QA와 실제 폰 증거를 구분한다.

업데이트 후 22:13:03에 이어 실기기 QA 뒤 22:17:16 최종 읽기 전용 감사를 완료했다. 제외 없이 전체 계정의 15개 범위 개수·전체 행 SHA와 보안 지문이 최초 21:59:13과 업데이트 후 22:13:03의 두 기준선 모두와 같았고 Data API 404·health 200을 유지했다. 감사 도구의 DB·설정 쓰기나 별도 Auth·학습·미션 API 호출은 없었다. 기존 기한과 기록을 보정하지 않았으며 이 관찰을 최종 감사 이후의 정상 사용까지 확대하지 않는다. 병합 때 기존 workflow가 API 테스트 경로를 감지해 자동 Cloud Run 배포도 성공했다. 서버 운영 코드·SRS 정책 변경이나 수동 배포는 아니지만 실제 자동 배포가 있어 ‘서버 배포 없음’으로 기록하지 않는다.

## 14 저장된 레슨의 복원과 발견은 다른 문제였다

### 저장은 됐지만 어디서 다시 열어야 할까

앞선 실기기 검증에서는 같은 레슨을 찾아 들어가면 어휘 2/5가 복원됐다. 하지만 학습 화면의 추천은 여전히 다른 레슨을 가리킬 수 있었다. 로컬 어휘·문법 위치는 연습 시작 요청보다 먼저 저장되므로, 저장이 있어도 서버 목록의 상태는 NOT_STARTED일 수 있다. 학습 탭과 전체 레슨 목록이 서버 상태만으로 추천하면 사용자가 원래 레슨을 기억해 찾아야 했다. 복원 성공이 저장된 진행의 발견성까지 보장하지는 않았다.

2026년 10월 23일 후속 MVP는 이 간격을 메우는 진입점이다. 저장된 레슨 영역을 학습 탭과 전체 목록이 공유하되 서버 추천·완료·역 스탬프를 바꾸지 않는다. 현재 계정과 현재 레벨의 목록에 공개된 레슨 ID만 대상으로 로컬 저장을 읽고 다른 계정이나 인증 키를 훑지 않는다.

### 목록이 아는 사실까지만 표시하기

체크포인트에 저장 시각이 없으므로 최신 학습이나 날짜 순서를 추측하지 않는다. 여러 저장은 커리큘럼 순으로 최대 세 개를 보여주고 선택 시트로 고를 수 있게 설계한다. 목록을 채우기 위한 레슨별 상세 GET이나 학습 시작·제출 요청은 추가하지 않는다. 총 문항 수·정확한 퍼센트·복원 성공도 목록의 정보만으로 확정하지 않는다.

제출 확인 중이거나 형식·버전을 신뢰할 수 없는 저장은 보존하고 일반 이어하기와 구분한 확인용 진입점으로 다룬다. 한 저장을 읽는 데 실패해도 다른 저장과 기존 추천·레슨 진입을 막지 않게 한다. 실제 레슨에 들어간 뒤에는 PR #192의 콘텐츠·서버 상태 검증을 거친다. 목록에 저장이 있다는 표시를 콘텐츠가 그대로라는 증거나 재제출 허가로 쓰지 않는다.

구현 검토에서는 인증 알림이 늦게 전달될 때 이전 계정의 캐시가 표시될 가능성을 발견했다. 표시 직전에 화면의 계정·레벨과 인증의 실제 현재 계정, 저장 목록의 소유자·레벨을 함께 대조하도록 보완하고 인증 스트림 지연 회귀를 추가했다. 운영에서 노출이 발생했다고 판단한 결과는 아니며 병합 전 코드 검토에서 막은 경로다. 새 구역의 동작 문구에는 기본 본문색을 쓰고 브랜드 핑크 아이콘은 보조로 두어 읽기와 강조를 구분했다. 최종 시각 검토에서는 테마가 정의하지 않은 보조 테두리 기본값이 검정·흰 테두리를 만드는 것도 발견했다. 새 위젯만 기존 카드 배경·테두리와 밝기에 맞는 보조 본문색으로 연결하고 정확한 토큰·글자 대비 회귀를 보강했다. 전역 테마를 바꾸지는 않았다.

### 복습 정책 검토를 화면 MVP와 분리하기

별도 [SRS 정책 정렬 검토안](../operations/plans/srs-policy-alignment-proposal-2026-10-23.md)에는 앞선 비교 회귀의 고정 상태 아홉 가지와 부가 필드·이벤트 실패 처리 차이를 정리했다. 웹에 별도의 계산 경로도 있어 모바일 백엔드 두 경로만 정리하면 제품 전체가 단일 정책이 된다고 볼 수 없다. 이는 소스와 기존 테스트 검토이며 운영 트래픽이나 학습효과를 조사한 결과가 아니다.

후보는 현재 결과를 보존하는 계산 경계 정리(A), 앞으로 낼 레슨 답안에 퀴즈 계산을 적용하는 안(B), 반대로 레슨 전이를 퀴즈에 적용하는 안(C)으로 구분했다. A도 현재 동작을 보존하는 리팩터링 제안이고 이번 MVP에서는 구현하지 않는다. B/C는 과거 데이터를 재계산하지 않아도 새 답안의 다음 기한이 바뀌므로 영향과 적용 범위를 먼저 확인해야 한다. 문항별 반복 반영과 제출 멱등성도 별도 결정이다. 정책을 통합했다거나 더 좋은 간격을 증명했다고 기록하지 않는다.

### 현재 운영 문장과 공개 음성을 새로 대조하기

15:59:53 KST의 운영 스냅샷은 공개 N5 50개 레슨·아홉 챕터였다. 대화 198개와 문제 안내 250개의 총 448개를 같은 스냅샷의 저장 TTS와 비교했다. 원문, 실제 runtime의 strip 결과, 기존 문장부호 정규화 검사는 각각 448/448 일치했고 누락·고아·중복·불안전한 URL은 0개였다. 공식 CA를 검증한 TLS와 REPEATABLE READ·READ ONLY, 시간·행 수 제한을 사용했으며 개인 학습 행을 내보내지 않았다.

공개 파일 검사는 DB 연결 없이 그 스냅샷만 사용했다. 첫 제한 환경의 실행은 HTTP 응답이 0개여서 환경 제한으로 별도 기록했고 음성 불량으로 세지 않았다. 허용된 네트워크의 실제 검사는 16:07:23–16:08:17 KST에 URL당 한 번씩 GET해 448개 모두 HTTP 200·다운로드·파일 probe를 통과했다. 파일 SHA도 448개 전체를 다시 확인했고 총 29,791,585바이트·고유 SHA 448개였다. 과거와 숫자가 같아도 이번 결과는 현재 파일을 새로 측정한 증거다.

### 네 줄의 제품 체험과 전문 검수를 분리하기

사용자가 5~10분 동안 들어볼 기본 표본은 ‘공통점이 반가울 때’의 대화 네 줄이고 기초 대안은 ‘처음 만난 자리’다. 두 레슨의 여덟 파일은 현재 문장 일치·HTTP 200·파일 검사와 경고 0을 확인해 [듣기 확인표](../operations/plans/n5-representative-listening-check-2026-10-26.md)에 연결했다. 직접 듣는 판정은 빈칸으로 남겼다.

화면과 소리 대응, 앞뒤 잘림, 정지·다시 듣기, 화면 이동 뒤 겹침과 속도의 편안함을 먼저 확인한다. 재생 중 누르면 정지하고 다시 눌러 대상 문장을 재생하는 현재 동작과 그 사용감 의견도 구분한다. 일본어 읽기·장음·촉음·억양은 숙련 검수자의 영역이며 확신이 없으면 확인 필요로 남긴다. 네 줄 체험이 최소 대표 기준인 한 챕터 전체나 N5 전체의 승인으로 바뀌지는 않는다.

단어 카드 음성은 별도 어휘 경로다. 문제 안내 250개는 현재 모바일 문제 UI에 재생 버튼이 없어 검수 링크로 확인한다. 두 대표 레슨에는 전체 대화 audioUrl이 없으므로 전체 듣기 버튼이 없는 상태를 이번 표본의 누락 오류로 세지 않는다. 기존 N4 판정 적용 도구도 HN5를 지원하지 않아 그대로 실행하지 않는다.

### 도구 검증과 현재 적용 상태

이번 충돌 정리와 최신 packet 선택 회귀의 관련 25개, API 전체 909개가 통과했다. 기존 Wave1 fixture 스킵 13개와 별도로 필수 PostgreSQL 85개는 모두 무스킵 통과했다. 실제 DB 검증은 격리한 PostgreSQL만 사용했다. Ruff·포맷 297개와 app 172개·보고 스크립트 두 개의 mypy 검사도 통과했다. 현재 PR의 소스 네 파일 중 이번 통합에서 추가로 손본 것은 두 파일이며 운영 API·DB·스키마·환경·의존성을 바꾸지 않았다.

15:59:53과 16:19:51 KST의 사후 비교에서 공개 레슨 50개·아홉 챕터·TTS 448개의 허용 메타데이터 SHA와 입력 일치, 보안 지문은 같았다. health 200·Data API HEAD 404도 각 한 번 확인했다. 다만 보호하는 일부 학습 기록의 집계·지문은 달라 모든 기존 기록이 불변이었다고 결론 내리지 않았다. 도구의 읽기 전용 조회에서 쓰기는 0번이었지만 변화 원인까지 특정하지는 않았다. 개인 행을 추가 조사하거나 추정 보정하지 않았다. 검수 대상의 보존, 읽기 전용 실행과 운영 기록 전체의 불변은 서로 다른 주장이다.

현재 완료한 것은 충돌 정리, 현재 목록·파일 검사·사후 비교와 사용자 확인표 준비다. TTS 생성·재생성·seed·STT·자동 PASS·판정 적용은 하지 않았고 사람 청취도 남아 있다. 이 문서의 회귀 수는 로컬 검증 결과이며 원격 CI의 최신 상태는 [PR #162 checks](https://github.com/WhiteMouseDev/HaruKoto/pull/162/checks)에서 별도로 확인한다. PR #162 병합·운영 배포·Codex의 직접 청취는 수행하지 않았다. [작업과 검증 기록](../operations/plans/n5-audio-qa-refresh-2026-10-26.md)에 확인 범위와 남은 판정을 구분해 남긴다.

### 후속 사용자 확인에서 드러난 화자 구분 문제

사용자는 문장 대응·잘림, 정지·다시 듣기, 화면 이동 뒤 겹침, 따라가기 편한 속도 네 항목의 정상 동작을 직접 보고했다. 다만 두 화자가 같은 여성 목소리라 어색하다는 문제가 남았다. 이번 보고의 레슨·문장·기기는 명시되지 않아 대표 여덟 줄이나 전체 N5의 개별 판정으로 확대하지 않는다. 기능 PASS와 화자 구분 FLAG, 아직 대기인 정식 언어 검수를 나누었다.

원본에는 김의 남성 voice alias와 다나카의 여성 alias가 이미 있었지만 서버는 원문만 전달하고 ElevenLabs의 단일 voice ID로 생성했다. 기존 캐시도 음성 역할을 구별하지 않았다. 파일이 있고 문장이 맞는 기계 검사만으로 대화의 화자 구분을 보장할 수 없다는 사례다. 성씨를 근거로 인물 설정을 바꾸지 않고 기존 역할의 실제 음성 전달을 먼저 바로잡는 [수정안](../operations/plans/n5-dialogue-speaker-voices-2026-10-26.md)을 준비했다. 새 설정·유료 표본 생성·운영 음성 캐시 교체는 별도 결정이며 아직 실행하지 않았다.

## 블로그로 공개할 때 남겨야 할 구분

이 작업에서 화면의 숫자와 DB의 숫자가 다르면 어느 쪽이 맞는지 추측하지 않고 저장된 사실과 지표의 정의를 따로 확인했다. 0점은 트랜잭션의 저장 문제였고, 이어 풀기의 0%는 다른 지표를 표시한 문제였다. 두 현상을 같은 원인으로 묶으면 수정도 검증도 빗나간다.

접근 제한과 성능도 같은 방식으로 다뤘다. 로그를 없애기 위해 Data API를 다시 열지 않았고, SELECT 감소를 전체 Disk IO 개선률로 바꾸지 않았다. 새 파티션을 만들면서 기존 학습 기록을 정리하거나 과거 이벤트를 추정해 채우지도 않았다.

공개 글에는 테스트 계정 자격 증명, 토큰, 고객 식별자와 답안, 개인 기기 식별자, 비공개 대시보드 주소를 넣지 않는다. 화면이 필요하면 실제 계정 정보가 없는 예시 데이터로 다시 만들고, 문제를 설명하는 수치에는 검증한 환경과 시점을 함께 적는다.

각 사례의 발행 순서와 남은 확인 항목은 [블로그 시리즈 구성안](2026-10-21-harukoto-blog-outline.md)에 정리한다.

# 학습 저장을 잠시 멈추되 로그인과 기록은 남기는 방법

한 문항을 저장하면 학습일로 인정하는 기능은 새 테이블과 서버 잠금 순서를 함께 바꾼다. 기존 서버 요청이 계속 실행되는 동안 새 코드만 배포하면 이전 잠금 순서와 섞일 수 있다. 그래서 새 기능의 배포 전에 학습 저장의 신규 진입을 잠시 막는 STOP 처리를 별도로 준비했다. 이 글은 소스·격리 검증 기록이며 운영 적용 기록이 아니다.

먼저 기준 코드를 분리했다. 학습일 기능 브랜치에는 이미 새 모델이 있으므로 그 코드로 STOP을 만들면 마이그레이션 전 운영 DB를 읽을 수 없게 된다. 실제 운영 API와 웹의 배포 커밋을 읽기 전용으로 확인하고, 같은 서버·웹 소스를 가진 main에서 별도 작업 공간을 만들었다. 테스트 DB도 새 기능의 p6가 아닌 기존 o5 스키마를 사용했다. Prisma의 생성된 client까지 구 스키마로 다시 만들어, 소스는 구 버전인데 생성물은 신버전인 착각도 피했다.

‘POST만 막으면 된다’는 가정은 맞지 않았다. 오늘의 미션을 조회하는 GET은 XP를 지급하고, API의 미완료 퀴즈 조회는 오래된 세션을 완료 상태로 바꾼다. 이 요청도 중지 대상으로 넣었다. 반대로 음성 캐시나 로그인 bootstrap, 결제 callback은 쓰기가 있어도 유지해야 한다. 모든 DB 쓰기를 끄는 기능 대신 학습·보상 요청을 method/path별로 분류했다. 새 route가 추가되면 분류 검토를 요구하는 테스트도 넣었다.

차단은 인증·본문 파싱·DB·AI 호출 전에 실행한다. 503과 잠시 후 같은 기록으로 재시도하라는 안내, Retry-After와 비공개 캐시 헤더를 반환한다. 로그인·통계·기존 영수증·캐시 음성은 기존 인증을 거쳐 계속 이용하게 한다. HEAD가 GET 보상 코드를 실행하는 경우와 인코딩 경로, 이미지 확장자처럼 보이는 동적 API ID도 검사했다.

서버가 안전하게 거절하는 것과 화면이 안전하게 기다리는 것은 별개였다. 기존 웹의 일부 퀴즈는 답안 저장 응답을 기다리지 않고 다음 문제로 넘어갔다. 새 일반 퀴즈·가나 화면에서는 점검 응답을 받으면 진행을 멈추고 같은 payload를 재시도하게 했다. 모바일의 기존 레슨 제출은 이미 고정 제출 ID와 체크포인트를 보존하므로, 503 뒤 provider를 다시 만들고 같은 ID로 재시도하는지 따로 확인했다.

격리 PostgreSQL에서는 중지 요청이 DB dependency를 열지 않고 기존 사용자·답안·학습 기록·복습 기한·음원과 권한 상태를 바꾸지 않는지 비교했다. 실제 compiled Next의 ON 빌드도 로컬 합성 인증 서버와 연결해 로그인된 페이지는 열리고 저장 요청은 인증 호출 전 거절되는지 확인했다. 테스트 mock의 플래그만 켠 결과를 실제 배포 artifact의 동작으로 대신하지 않았다.

한계도 남겼다. 이미 열린 예전 웹 탭에 새 JS 처리가 소급되지는 않는다. 서버에 저장되지 않은 선택지가 브라우저 종료 후 복원된다고 보장할 영속 outbox도 이번에 추가하지 않았다. STOP이 이미 실행 중인 handler를 취소하거나, 모든 예전 배포 URL에 자동 적용하는 것도 아니다. 운영 전에는 대상 host 차단, 기존 요청 종료 증거, 사용자 안내와 실제 클라이언트 검수가 필요하다.

코드의 기본값은 OFF다. 실제 중지는 별도 승인한 ON 소스 커밋·빌드·배포로 수행한다. 기존 DB 단계에서는 같은 구 스키마의 OFF artifact로 복귀할 수 있고, 새 모델·writer가 들어간 뒤에는 새 스키마를 이해하는 호환 OFF artifact를 사용한다. 복구를 위해 학습 기록을 삭제하거나 Data API를 다시 열지 않는다. [구현·검증·적용·롤백안](../operations/plans/legacy-study-write-stop-2026-11-03.md)에 구체적인 조건을 남겼다.

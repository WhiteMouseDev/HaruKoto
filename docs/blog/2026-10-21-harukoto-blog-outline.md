# 하루코토 개선 사례 블로그 시리즈 구성안

학습 앱 개선을 디자인 소개 하나로 끝내지 않고, 사용자 관찰에서 문제를 좁히고 저장·보안·운영을 검증한 과정으로 나누어 발행한다. 각 글은 **문제 → 원인 → 설계 선택 → 수정 → 검증 → 남은 작업** 순서로 읽을 수 있게 구성한다.

본문 초안은 [개선 사례집](2026-10-21-harukoto-improvement-casebook.md)에 있다. 이 파일은 글을 나눌 기준과 상태를 관리한다. 작성일 기준으로 완료된 운영 변경과 로컬 변경, 구현·검증한 코드와 아직 적용하지 않은 운영 설정을 구분한다.

운영 배치 후속 글로는 **검사 성공·예약 호출 성공·알림 수신이 서로 다른 이유**를 다룬다. 전용 최소 권한 계정, 고정 이미지와 Secret, 실제 누락 감지, 이메일 digest 지연과 명시적 설정 승인을 사례집 9번에서 이어 쓴다.

연속 학습일은 별도 글로 준비한다. 영속 출석 기록의 스키마와 완료 경로 연결이 끝나기 전에는 `정확한 연속 학습일을 완성했다`는 제목으로 발행하지 않는다. 현재는 날짜 기준과 UI, 데이터 모델의 한계를 다루는 설계 글로 쓸 수 있다.

## 글마다 확보할 증거

### 1 학습 노선도와 브랜드

- 예시 데이터의 1장 미시작·5장 완료 화면과 추천 열차 화면을 나란히 둔다.
- 밝은 테마·어두운 테마, 작은 화면·큰 글자의 실제 위젯 렌더링을 사용한다.
- Stitch 시안의 토큰 불일치와 선택적으로 채택한 원칙을 설명한다.
- `studyMapEnabled`는 재빌드가 필요한 소스 스위치임을 명시한다.
- UI 실험이 학습 기록이나 API 계약을 바꾸지 않는 이유를 보여준다.

### 2 답안 저장과 결과 피드백

- 파티션 INSERT 실패가 실제 PostgreSQL에서 발생하는 재현 조건을 넣는다.
- Python 예외 처리와 DB 트랜잭션 복구를 구분하는 작은 코드 예시를 둔다.
- 정답 10건이 새 세션에서 다시 읽히고 중복 재전송에도 증가하지 않는 테스트를 연결한다.
- 결과 카드 전후는 예시 수치로 재제작하고 계정 화면을 그대로 공개하지 않는다.
- 특수 모드의 완전한 이어 풀기는 아직 별도 계약 과제임을 구분한다.

### 3 날짜와 이어 풀기

- naive UTC와 aware UTC/KST의 24시간 경계 사례를 표로 보여준다.
- API 검증과 실제 아이폰 검증을 다른 결과로 적는다.
- 실제 기기 재시작 전후 `1/20·5%` 관찰과 사용자 확인 `2/20`을 분리한다.
- 같은 유형·레벨이 아닌 미완료 퀴즈가 홈 지표를 덮지 않는 테스트를 넣는다.
- 546개와 649개는 서로 다른 체크아웃의 테스트 수임을 함께 적는다.

### 4 보안과 플랫폼 정책

- Data API·서버 DB 연결·Supabase Auth의 역할을 간단히 그린다.
- 역할별 접근 거부, Auth 생성 트리거, 서버 쓰기의 실제 테스트를 연결한다.
- `GRANT`를 광범위하게 복구하는 해결책을 제시하지 않는다.
- 10월 14일 경고와 10월 30일 정책 안내를 별개 사건으로 설명한다.
- 10월 30일 이후의 확인은 실행된 뒤에만 완료 상태로 갱신한다.

### 5 성능과 운영 로그

- 후보·학습 ID SELECT가 20회에서 2회로 줄었다는 측정 범위를 고정한다.
- 오류 0건 관찰에는 10월 15일의 한정된 시간 구간을 붙인다.
- 전체 Disk IO 개선률, 비용 절감률, 장애 감소율을 새로 만들어 넣지 않는다.
- 요청 범위 재사용이 사용자 간 데이터 공유를 만들지 않는 테스트를 보여준다.

### 6 CI와 파티션

- CI 584통과·23스킵과 로컬 594통과·13스킵의 차이를 설명한다.
- 필수 10개에서 25개, 52개로 늘어난 시점을 구분하고 전체 테스트 수를 합산하지 않는다.
- 7개 추가·11개 전체·2027년 2월 1일 미포함 경계를 일관되게 적는다.
- 운영 28개 검사와 배포 후 15개 검사는 별도 단계다.
- 기존 학습 기록 보존은 DML·DROP·DETACH를 하지 않은 설계와 메타데이터 확인으로 설명한다.
- 과거 저장 실패 이벤트를 복원했다는 주장은 하지 않는다.

### 7 읽기 전용 검사와 이후 알림

- 완료된 구현의 실제 옵션·출력·종료 코드만 예시로 쓴다.
- 중간 월 누락, UTC 경계, 비 UTC 세션, 보안 이상과 DB 접속 실패의 회귀 사례를 담는다.
- 검사 중 쓰기가 거부되는 실제 DB 테스트를 확인하고, 원래 데이터·보안 설정 불변을 검증한다.
- 운영 DB 권한과 클라우드 변경이 필요하면 변경안과 적용 결과를 구분한다.
- 정기 실행·이메일 수신 시험이 끝나기 전에는 자동 감시가 활성화됐다고 쓰지 않는다.

### 8 레슨 문항과 SRS 대상

- 학생 문항이 `私`, 문법 문항이 단어에 연결될 수 있는 위치 기반 fallback을 설명한다.
- 원본의 카탈로그 순서 번호와 환경별 UUID, 문항 표시 순서를 구분한다.
- 81개 레슨·405개 문항의 문구·정답·선택지 보존, 명시 대상 400개와 채점 유지·SRS 제외 다섯 개를 구분한다.
- 대상 누락·충돌의 409가 모든 SRS·진도 쓰기 전에 발생하는 테스트를 연결한다.
- 전체 API 757개 통과·선택적 스킵 13개, 필수 PostgreSQL 61개 무스킵 통과, Node 원본 테스트 여덟 개를 각 범위대로 기록한다.
- 운영 읽기 전용 조사 범위는 이벤트 94건·계정 세 개·레슨 열 개·현재 어휘 진도 행 62개다. 계정 식별자나 답안은 공개하지 않는다.
- 현재 검토안과 다른 77건과 일치하는 17건을 과거 정오 판정으로 바꾸지 않는다. 문항 순서·답안·시도 ID·콘텐츠 버전이 없어 정확한 역사 재생이 불가능하다.
- 기존 94개 이벤트·62개 진도 행과 점수·XP·연속 학습일은 보존했다. 콘텐츠 대상 보정과 과거 학습 기록 교정을 구분하고, 과거 기록을 교정했다고 쓰지 않는다.
- 같은 문법의 세 문항을 SRS 세 번으로 처리하는 기존 정책과 대상 식별 수정을 구분한다.
- 추가 문법 링크 17개는 non-core여도 기존 소개·SRS 등록에 나타날 수 있음을 포함한다.
- 81개 레슨 JSON과 링크 17개의 DML은 13:19:55 KST에 적용됐다. 새 리비전 100% 전환 13:14:24 KST와 300초 요청 해소 대기, 콘텐츠 적용, 실제 사후 검사 45개 통과를 구분한다. 공통 JWT/API 및 이메일·비밀번호 Auth 검증이며 아이폰·SNS 제공자 UI 확인은 아니다.
- 로컬 도구 검증과 운영 쓰기를 구분한다. 기존 링크 548개를 유지해 총 565개가 됐다. 기존 14개 테이블과 레슨 발생 이벤트 94건을 합한 15개 범위의 개수·SHA는 트랜잭션 안과 커밋 뒤 감사에서 같았고, 13:27 KST의 QA 후 감사도 신규 QA 부분만 제외하면 최초 baseline과 완전히 같았다. RLS·권한 지문 불변과 읽기 전용 예정 변경 0개도 확인했다.
- 운영 45개는 계정 생성 1개·로그인과 조회 18개·레슨 제출 3개·DB 대상 6개·이어 풀기 17개다. 로컬 보조 도구 회귀 23개와 합쳐 하나의 운영 검사 수로 쓰지 않는다.
- 학생 문항만 틀린 레슨 4/5에서 学生 오답 1회, 私 정오·반복 0, 문법 정답 3회를 확인했다. 1/2·50% 퀴즈는 QA 세션 로그아웃·새 로그인 뒤 같은 문제와 답안으로 다음 문제부터 재개해 2/2·100%·20 XP로 저장됐다.
- Data API UI 비활성화와 익명·로그인 HEAD 404, 보호 API 익명 401을 구분한다. 새 리비전의 전환 이후 검사 시점 ERROR·5xx 0건은 한정된 관찰 결과다.
- QA 계정과 새 활동은 감사 증거로 유지하고 기존 계정·세션은 변경하지 않았다. 검증 태그 두 개를 제거한 최신 리비전 100%와 배포 워크플로 활성 상태를 기록한다. 계정·토큰·답안 내용은 공개하지 않는다.
- Python 버전 차이의 CA 검증 문제는 공식 CA·호스트명 검증을 유지한 실행 환경으로 해결했으며 SSL 검증을 해제했다고 쓰지 않는다. 공유 CI/CD 비활성화 거절은 실제 설정 변경과 구분한다.

### 9 이번 오답 복습의 Simulator 검증

- 사용자가 로그인한 테스트 계정으로 대신 풀도록 요청한 Simulator 검증이다. 앞선 아이폰의 PR #186 설치·로그인 확인, Simulator 실제 오류·재개 조작, 이후 PR #188 한국어 안내 포함 아이폰 업데이트·홈 확인을 구분한다. 이번 폰에서 고의 오류나 새 퀴즈 풀이는 하지 않았다.
- 실제 10문항 8/10·80%·80 XP와 오답 もう·先를 기록했다. 앱 Dio 주소만 일시 실패시켜 오류를 확인하고 공식 API 복원 뒤 같은 재시도로 정확한 두 항목·순서와 자식 세션 한 개를 확인했다. OS·TLS·서버 설정 변경이나 Data API 설정 변경은 없다.
- 원문 Dio 영문 노출을 한국어 사용자 안내로 보완하고 실제 화면에서 확인했다. 모바일 네 파일, 새 회귀 13개·관련 53개·깨끗한 전체 597개·원본 통합 700개 및 분석·포맷 통과를 범위별로 적는다. 이후 [PR #188](https://github.com/WhiteMouseDev/HaruKoto/pull/188)을 승인 후 병합하고 아이폰에 업데이트했다. AOT 안내 포함과 실제 로그인 홈은 확인했지만 폰에서 오류 안내를 강제 재현한 것은 아니다.
- 1/2·50%에서 실제 프로세스 종료·재실행 뒤 로그인·진행률이 유지됐고 2/2 先부터 이어 100%·20 XP로 완료했다. hot reload를 프로세스 재시작으로 쓰지 않는다.

- SRS 검토의 고정 상태 표본 아홉 가지는 각 행의 step·interval·streak와 8초 정오 조건에서 나온 관찰값이다. 메타데이터·이벤트 실패와 웹의 세 번째 계산 경로도 확인했지만 운영 트래픽이나 학습효과를 조사한 것은 아니다.
- A는 기존 동작을 보존하는 계산 경계, B/C는 향후 답안 일정 변경을 포함하는 선택지다. 이번 MVP에는 어느 안도 구현하지 않는다. 과거 기한 보존과 새 답안의 기한 불변을 혼동하지 않고 정책 적용·반복 문항 집계·제출 멱등성의 사전 검토 경계를 남긴다.

## 공개 전 공통 확인

이번 오답 복습의 신규 API는 기존 기한 복습의 의미를 바꾸지 않는 별도 계약이다. 첫 지원 유형·미완료 중 재사용 범위와 완료 후 새 시도, 기존 기록 보존이 신규 시작 호출 범위라는 점을 함께 적는다. 로컬 테스트·CI·병합·서버 배포·실기기 확인을 각각 실제 완료한 단계까지만 기록한다. 현재 상태는 사례집 11번과 상세 계획의 최신 검증 결과를 따른다.

- [ ] 본문에 비밀번호, 토큰, `.env` 값, 고객·테스트 계정 식별자가 없다.
- [ ] 개인 기기 식별자, 계정 이메일, 비공개 대시보드 URL을 제거했다.
- [ ] 화면은 민감 정보가 없는 예시 데이터이거나 공개에 맞게 정리했다.
- [ ] 구현·병합·배포·운영 확인·실제 기기 확인을 서로 구분했다.
- [ ] 관찰한 현상과 입증한 원인, 설계 제안을 혼동하지 않았다.
- [ ] 수치는 대상, 환경과 시점에 맞고 다른 버전의 테스트를 합산하지 않았다.
- [ ] 롤백 설명은 실제로 보존되는 데이터와 제거되는 상태를 정확히 설명한다.
- [ ] 남은 작업의 상태와 필요한 승인 범위가 현재와 일치한다.
- [ ] 외부 제품 정책은 발행 시점의 공식 문서로 다시 확인했다.
- [ ] 공개 저장소 링크는 실제 변경과 연결되며 접근 가능한지 확인했다.

## 이후 기록을 추가하는 방법

새로운 문제가 해결될 때마다 등록부에 한 행을 추가하고 사례집에 문제·설계 선택·변경·검증 결과를 남긴다. 운영 적용 전에는 구현과 로컬 검증까지만 기록하고, 적용 후에 배포와 기능 확인을 덧붙인다. 오래된 `대기` 문구는 해당 사례의 최종 상태로 정리하되, 당시 왜 그 결정을 내렸는지 필요한 맥락은 유지한다.

연속 학습일 영속 기록과 특수 모드 이어 풀기는 독립된 후속 과제로 남는다. 파티션 정기 알림은 사례집 9번과 운영 적용 기록에서 구현·운영 실행·실제 수신·자연 정기 실행을 구분해 갱신한다.

레슨 문항의 SRS 귀속은 사례집 10번에 코드 준비·사용자 승인·새 리비전 준비·실제 전환을 구분해 기록한다. 선택적 DML·기존 기록 보존·실제 기능 검사 45개 통과를 완료로 기록한다. 과거 이벤트 재생의 한계와 문항별 SRS 반복·콘텐츠 검토 과제는 별도로 유지한다.

# 며칠 뒤 이어 푼 퀴즈가 학습 기록을 바꾸지 않도록

일본어 학습앱에서 퀴즈를 중단한 뒤 며칠 후 돌아오면, 저장된 문제부터 계속 풀 수 있어야 한다. 그런데 기존 구현에는 24시간이 지난 미완료 세션을 조회하는 순간 자동 종료하는 경로가 있었다. 다른 퀴즈를 새로 시작할 때도 이전 퀴즈를 정산했다. 사용자가 요청한 ‘조회’가 실제로는 기록을 바꾸고 있었다.

첫 번째 변경은 조회와 저장을 분리하는 것이었다. 미완료 목록과 이어하기는 보존된 답안·snapshot을 읽고, 새 퀴즈 시작은 별도의 세션을 만든다. 답안이 없는 최근 세션 여러 개 때문에 실제로 이어 풀 수 있는 오래된 퀴즈가 목록에서 밀리지 않도록, 답안이 저장된 미완료 세션을 먼저 걸러 페이지 제한을 적용하고, 각 항목의 재개 가능 상태를 따로 표시했다.

두 번째 문제는 ‘결과 복구’와 ‘오늘의 학습’이 같지 않다는 점이다. 월요일에 모든 답안을 저장했지만 완료 응답을 받지 못했다가 목요일에 결과만 확인할 수 있다. 완료 보상은 한 번 지급해야 하지만, 목요일에 새 문제를 풀었다고 기록해서는 안 된다. 연속일 계산만 생략하면 충분하지 않았다. 달력은 XP나 완료 횟수를 보고 다시 그날을 학습일로 해석할 수 있기 때문이다.

이를 위해 nullable Boolean 하나를 사용했다. NULL은 기존 과거 기록의 해석을 유지하고, FALSE는 결과 복구만 한 날, TRUE는 이미 인정됐거나 실제 활동으로 인정한 학습일을 나타낸다. 과거 행을 백필하지 않는다. 이미 TRUE인 날을 FALSE로 내리지 않고, 결과 복구 뒤 실제 새 답안을 저장하면 TRUE로 올린다. 같은 사용자의 답안 저장과 결과 정산에는 일관된 잠금 순서를 적용해 동시 요청도 같은 규칙을 지키게 했다.

웹에서는 재전송과 재도전도 구분했다. 네트워크 때문에 같은 답안을 다시 보내는 경우는 같은 attemptId로 한 번만 반영한다. 매칭 문제에서 실제로 다시 도전하는 경우에는 새 attemptId와 직전 답안의 previousAttemptId를 연결한다. 저장 응답을 확인하기 전에 완료를 진행하지 않으며, 구형 요청을 애매하게 추정해 기록을 바꾸지 않는다.

운영 전환은 컬럼 추가, 호환 OFF 버전, 정책 ON, 앱 업데이트 순서로 나눴다. 새 ORM을 먼저 배포하면 아직 없는 컬럼을 조회할 수 있고, 새로운 FALSE를 이해하지 못하는 구 버전으로 되돌리면 출석을 잘못 해석할 수 있다. 그래서 롤백도 새 판정을 읽을 수 있는 호환 OFF 버전으로만 준비했다. 컬럼 삭제나 과거 기록 재계산은 롤백에 포함하지 않았다.

테스트는 화면 표시만 보지 않았다. 실제 PostgreSQL에서 동시 제출·응답 유실·재시도·KST 날짜 경계·완료와 새 답안의 경합을 검증했다. 격리 시뮬레이터에서는 오래된 모든 답안의 결과 복구가 XP를 한 번만 정산하고 새 학습일을 만들지 않는지, 이후 새 답안은 정상적으로 학습일로 인정되는지 확인했다. 운영에서는 이미 존재하는 약95시간 전 문장 배열·매칭 세션을 사용했고, 실제 앱 종료·재실행 뒤 같은 세션과 진행 위치가 유지되는 것을 확인했다. 검증 편의를 위해 기존 세션 날짜를 조작하지 않았다.

운영 적용 결과와 실제 확인 범위, 수치, 롤백 대상은 [운영 전환 기록](../operations/plans/quiz-retention-credit-operating-rollout-2026-11-03.md)에 연결한다. 비밀키·토큰·사용자 답안 원문은 이 글과 이번 운영 기록에 포함하지 않는다.

마지막 비교에서는 별도 계정의 대화 활동도 발견했다. 전체 DB가 전혀 바뀌지 않았다고 포괄적으로 결론내리지 않고, 우리 검사로 확인한 퀴즈·답안·복습·음원의 보존과 동시 활동 증가분을 분리해 기록했다. 검증 결과를 정확히 설명하는 것도 구현의 일부였다.

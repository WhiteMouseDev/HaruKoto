## 기존 데이터 보존을 먼저 증명한 이유

운영 QA 전에 12개 보호 테이블 **5,468행**을 기본 키와 서버 측 행 해시로 대조했다. 마이그레이션 직후와 배포 직후 모두 변경·누락·추가 0이었다. 기준은 사용자 22명, 퀴즈 세션 437개, 답안 2,634개, 일별 진도 103개, 단어 진도 1,007개, 문법 진도 30개, 레슨 진도 23개, 가나 진도 55개·단계 96개, 학습 단계 진도 0개, 복습 이벤트 210개, 음원 캐시 851개다. 행 해시에는 기존 복습 기한도 포함한다. 기존 스키마·권한·RLS·함수·트리거·역할·PostgREST 메타데이터 해시도 동일했다.

기존 미완료 퀴즈 9개는 모두 24시간 이상 경과한 상태였다. 기존 계정의 홈이나 `/quiz/incomplete`를 호출하면 정상 만료 정책 자체가 세션을 변경할 수 있다. 이 때문에 기존 앱을 실행해 확인하는 대신 새 일반 QA 계정 한 개를 만들고, 그 계정의 정상 학습으로 생긴 행만 구분했다. 계정 생성 메일·권한 상승·기존 계정 변경은 없었다.

실제 앱 이메일 로그인과 N5 온보딩, 재실행 후 인증 복원을 확인했다. 같은 신규 QA의 운영 `/user/profile`은 200과 UID 일치였다. Supabase의 `users`·`lesson_submissions` Data API에 본문 없는 HEAD 요청을 보내 익명·인증 상태 모두 404를 확인했다. TLS 검증과 리디렉션 차단을 유지했다.

## 실제 운영 서버를 사용한 시뮬레이터 검증

승인된 main과 실행 코드가 같은 Flutter 앱을 고정 SDK 3.41.3으로 빌드했다. 기존 프로덕션 `.env`와 추적 파일·lockfile을 변경하지 않았다. 별도 QA 시뮬레이터에서 실제 Supabase 인증과 Cloud Run API를 사용했다. 로컬 API·인증 대체·프록시·응답/답안 주입은 사용하지 않았다.

QA 앱의 PID·단일 실제 `AppHttpClient` 인스턴스·공식 HTTPS 주소·빈 Sentry DSN을 확인한 후 지정한 레슨의 신규 제출 POST에만 일회성 통신 실패를 주입했다. 기존 QA env에는 Sentry DSN이 없으며 운영 설정은 바꾸지 않았다. 헤더·토큰·본문을 수집하지 않고 메서드/경로/상태 코드만 기록했다. 초기 학습 조작은 Flutter debug service에서 현재 화면의 실제 입력·버튼 콜백을 호출했으므로 OS 터치 hit-test 검증과 구분한다. 재실행 후 학습 탭·저장된 제출 카드 열기는 Device Hub의 네이티브 화면을 직접 클릭해 확인했다.

새 시뮬레이터의 온보딩은 일반 iOS 알림 권한 창에서 대기했다. 앱 재실행만으로는 시스템 창이 사라지지 않았으므로 Device Hub에서 해당 QA 시뮬레이터의 「허용 안 함」을 직접 눌렀다. 앱 내부 위젯 상태만으로 실제 시스템 창까지 해소됐다고 판단하지 않았다. 운영 알림·기존 시뮬레이터의 권한은 변경하지 않았다. 이 전 단계의 시스템 알림 창이 포함된 캡처는 결과 화면 증거로 사용하지 않는다.

### A. 서버 전송 전 실패 → 같은 제출 재시도

HN5-001 「처음 만난 자리」의 단어·문법·대화·선택형·매칭·문장 배열을 일반 화면으로 진행했다. 최종 POST 한 번을 HTTP 전송 전에 실패시켰다. 앱은 답안을 보관하고 결과 확인/같은 답안 재시도 안내를 표시했다. 그 시점의 DB는 영수증 0개·시도 횟수 0회였으며, 정상 레슨 시작에 따른 IN_PROGRESS 행 외 제출 효과가 없었다.

「같은 답안으로 제출 재시도」를 누르면 저장된 같은 ID로 GET 조회 후 POST를 수행하고 200을 받았다. 실제 결과는 **100%·5/5 정답**, 영수증 정확히 1개·시도 횟수 1회였다. 첫 완료에 따른 단어 6개·문법 1개 등록과 복습 이벤트 5개가 생겼다. 기존 레슨 정책에 따라 이 경로의 XP·연속일·daily_progress는 0으로 유지됐으므로 XP 보상을 검증했다고 표현하지 않는다.

### B. 서버 저장 성공 → 응답 유실 → 완전 재실행 복구

HN5-004 「공통점이 반가울 때」도 화면에서 학습했다. 이번에는 실제 운영 POST의 200이 돌아온 뒤 앱에 전달되기 직전 한 번 실패시켰다. UI는 제출 확인 대기 상태였지만, 읽기 전용 DB 조회로 같은 제출 ID의 영수증과 5/5·시도 1회가 이미 커밋됐음을 먼저 확인했다. 디스크 체크포인트의 ID·답안 해시를 보관한 뒤 앱 프로세스를 종료했다.

새 프로세스에서 기존 로그인이 유지됐다. 실제 학습 탭의 「공통점이 반가울 때 · 제출 결과 확인」 카드를 열면 같은 제출 ID의 **GET 1회·200**, **POST 0회**로 원래 결과를 받았다. 실제 화면은 「레슨 제출 결과를 복구했어요」「5/5문항 정답」「레슨 완료」와 처음 제출한 시각을 표시했다. 복구 후 pending 체크포인트는 정상 확인 완료되어 0개가 됐다. 검증용 실패 주입은 프로세스 종료와 함께 사라졌으며 새 프로세스에는 읽기 관찰만 추가했다.

## 기존 시뮬레이터 업데이트

기존 시뮬레이터에는 같은 `Runner.app`를 삭제 없이 덮어 설치하고 앱을 실행하지 않았다. 설치 전/프로세스 종료 후/설치 후 설정 13개 전체 바이트가 동일했고, 레슨 체크포인트·로그인 저장값·퀴즈 이어하기 항목의 해시도 같았다. 설치 과정의 데이터 컨테이너 경로 변경은 정상 동작이며 내용은 보존됐다. 설치된 앱의 커널·실행 파일 해시가 QA에 사용한 프로덕션 빌드와 정확히 일치했다. 물리 아이폰은 변경하지 않았다.

## 운영 적용 중 발견한 검증 도구의 함정

첫 마이그레이션 시도는 DDL 실행 전에 중단됐다. 기준 캡처는 `search_path=pg_catalog`, 적용 도우미는 `pg_catalog,public`을 사용해 PostgreSQL의 `pg_get_*`가 기본값·FK를 다른 문자열로 표현했기 때문이다. 읽기 전용 A→B→A 대조로 실제 DB 변경이 없고 표현만 달랐음을 증명했다. 비교 경로를 통일하고 승인된 SQL 실행 구간에만 public을 노출했다. 비교 항목을 빼거나 마이그레이션 원본을 바꾸지 않았다. 수정 후 같은 승인 SQL로 적용하고 별도 연결에서 재확인했다.

이 사례는 데이터 변경뿐 아니라 **검증 메타데이터를 생성하는 세션 설정도 고정해야 한다**는 운영상의 교훈이다. 또한 기록 보존을 요구받은 검사에서는 읽기 전용처럼 보이는 홈 조회가 실제 만료 갱신을 일으키는지까지 확인해야 한다.

## 최종 확인과 후속 범위

완전 재실행 복구 직전/직후의 **신규 QA 전체 행 해시가 동일**했다. 두 영수증의 원래 응답·처리 시각, 레슨별 시도 1회, 단어/문법 복습 기한과 복습 이벤트 10개 모두 같았다. 재조회는 추가 학습 효과를 만들지 않았다.

2026-11-02 **12:27:52 KST** 최종 전역 비교에서도 기존 5,468행은 변경·누락 0이었다. 새 보호 대상 26행은 전부 지정한 신규 QA 소유임을 확인했다. 구성은 사용자 1개·단어 진도 11개·문법 진도 2개·레슨 진도 2개·복습 이벤트 10개이고, 이와 별도로 새 영수증 2개가 있다. 다른 사용자 소유의 추가 행은 없었다. 851개 음원과 기존 보안 해시는 동일하며 새 테이블의 RLS·클라이언트 권한 0도 유지됐다.

최종 Cloud Run 확인에서 새 revision·트래픽 100%·불변 이미지·runtime·음성 설정·IAM·파티션 점검 설정이 모두 유지됐다. **12:04:45–12:27:49 KST** 해당 revision의 ERROR/HTTP 5xx는 0건이었다. 이는 기간을 제한한 Cloud Run 로그 판정이며 직접 Sentry를 조회한 결과나 향후 오류 부재 보장은 아니다.

- 기존 시뮬레이터의 **실행 후** 오래된 미완료 퀴즈는 정상 정책에 따라 만료될 수 있다. 보존 검사에서는 앱을 실행하지 않고 저장 데이터 자체를 비교했다.

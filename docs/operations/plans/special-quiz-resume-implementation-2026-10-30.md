# 특수 퀴즈 이어하기 구현·검증 기록

## 범위와 현재 상태

이 문서는 PR #209의 구현·격리 검증 시점 기록이다. 이후 승인된 웹·서버·앱 운영 적용과 실제 Supabase 로그인 검증 결과는 [별도 운영 반영 기록](special-quiz-resume-production-rollout-2026-10-30.md)을 따른다.

2026년 10월 30일 사용자가 [계약 제안](special-quiz-resume-contract-proposal-2026-10-30.md)의 구현과 시뮬레이터 검증을 승인했다. PR #208은 `41699f9f42786df93b0dce9ce10af932fff00316`으로 병합했다. #208 자체는 앞선 파티션 작업의 문서 PR이다.

FastAPI·Flutter·웹 BFF·OpenAPI 생성 타입·CI 회귀 구현과 아래 격리 시뮬레이터 검증을 완료했다. **이 구현·격리 검증 단계에는 새 기능의 운영 배포·아이폰 업데이트를 포함하지 않았다.** 운영 DB DML/DDL, 기존 세션 백필·재채점, 학습 기록·복습 기한 보정, 권한·클라우드 설정·음원 캐시 변경은 없다.

## 문제와 설계

기존에는 콘텐츠 카테고리인 `quizType=VOCABULARY`와 화면 모드인 `matching`을 별도로 보존하지 않았다. 시작할 때 짝 맞추기였던 세션을 홈에서 재개하면 일반 선택형으로 열리거나 표시할 일본어·뜻이 없어질 수 있었다. 문장 배열도 원본 모드와 토큰을 복원하는 계약이 필요했다.

카테고리를 화면 모드로 덮어쓰지 않는다. 카테고리는 답안 연결·SRS·통계에 쓰이므로, 신규 matching/arrange만 기존 `questions_data` JSON에 원본 문항·순서·canonical UUID·mode·표시 스냅샷을 함께 저장한다. matching은 시작할 때 사용한 같은 pair ID와 `matchingPairs`를 보존하고, 문장 매칭은 일본어 상대 문장도 보존한다. 컬럼·마이그레이션 추가는 없다.

재개 시 저장된 질문 ID 집합으로 이미 제출한 정답과 오답을 모두 제외한다. 매칭은 임의 순서로 풀 수 있으므로 “답한 개수만큼 앞에서 자르기”를 하지 않는다. 원본 전체 수는 유지하고, 미제출 토큰·좌우 선택·셔플 상태는 복원하지 않는다.

### 계약과 소비자

| 경로                                    | 추가한 선택적 응답 필드                | 처리                                                    |
| --------------------------------------- | -------------------------------------- | ------------------------------------------------------- |
| `POST /quiz/start` 및 공유 start 모델   | `mode`                                 | 실제 실행 모드 반환                                     |
| `GET /quiz/incomplete`                  | `session.mode`, `session.resumeStatus` | `available` / `legacy_unavailable` / `invalid_snapshot` |
| `POST /quiz/resume` 및 공유 resume 모델 | `mode`, `matchingPairs`                | 원본 질문·저장 답안 ID와 함께 반환                      |

새 경로·요청 키·필수 응답 필드는 추가하지 않았다. OpenAPI 103개 경로와 기존 선언은 유지하고, 생성 타입은 선택적 속성 5개에 해당하는 10줄만 추가했다. 모바일은 서버가 검증한 모드를 우선 사용한다. 구 서버의 필드 부재는 유효한 일반 선택형에 한해 호환한다.

특수 세션을 안전하게 복원할 수 없으면 기존 `detail` 문자열 형식으로 한국어 409를 반환한다. 앱은 **resume 경로에 한정한 예외**로 기록 보존 안내와 돌아가기를 표시한다. 일시적 통신 실패는 같은 세션의 재시도를 제공한다. 다른 409의 전역 의미는 바꾸지 않고, 복원 실패를 자동 새 퀴즈 시작으로 대체하지 않는다.

웹은 같은 DB를 읽지만 자체 Prisma 채점 경로가 있다. 웹 자체 생성 형식은 검증해 유지하고, FastAPI의 `id/type/question` 형식은 일반 선택형을 포함해 resume·answer·complete 모두 **쓰기 전에** 앱 이용 안내로 거절한다. 이는 새 API 세션을 기존 웹 채점·복습 정책에 넘기지 않기 위한 경계다. 이번에 웹이 API 특수 퀴즈까지 지원한다고 표현하지 않는다.

### 기존 세션과 보존 정책

- 기존 배열/객체 JSON 중 표시 데이터·canonical ID·pair 관계가 완전한 알려진 VOCAB/GRAMMAR matching과 `SENTENCE_ARRANGE` arrange는 저장 스냅샷만 읽어 복원한다. 현재 콘텐츠를 조회해 과거 문장을 보충하지 않는다.
- 일본어 상대 문장이 없는 과거 문장 매칭, 필수 데이터 누락·혼합·중복·미등록 답안·모순된 채점은 거절한다. 기존 `VOCABULARY/GRAMMAR + arrange`도 카테고리 재해석 없이 거절한다. 누락을 맞추려고 기존 `quizType`이나 복습 대상을 바꾸지 않는다.
- 중복된 과거 답안은 첫 답안 기준으로 읽는다. 재개 조회 중에는 저장 행·정답수·채점·XP·복습 기한을 고쳐 쓰지 않는다. 완료 시 canonical 첫 답안으로 정답수를 맞추는 기존 정책은 유지한다.
- 새 답안의 실제 제출에만 기존 SRS 정책을 적용한다. 동일 답안 재시도·동시 제출·완료 재호출은 기존 한 번 반영 원칙을 유지한다. 재개 조회만으로 XP나 복습 기한이 갱신되지 않는다.
- 기존 `GET /quiz/incomplete`의 24시간 만료 처리와 `/quiz/start`의 기존 미완료 자동 종료·pending XP 정책은 유지한다. 따라서 incomplete를 운영 기록 보존 확인용 순수 읽기 API로 호출하지 않았다.

### 실제 UI 검증에서 함께 발견해 수정한 부분

1. 모바일 공개 자유 퀴즈는 stage 없이 matching을 요청하지만 API는 stage를 요구해 400을 반환했다. 단어·문법 자유 매칭은 요청 JLPT 풀로 생성하도록 맞췄다. stage가 있으면 기존 `content_ids`만 사용하고 다른 항목을 섞지 않는다. 지원하지 않는 유형·모순된 stage는 400이며 기존 자동 완료·XP 변경도 트랜잭션에서 롤백한다.
2. 신규 문장 배열 시작은 앱에서 요청·유효 카테고리를 `SENTENCE_ARRANGE`로 맞춘다. 이전 세션의 카테고리를 바꾸는 처리는 아니다.
3. 전체 Alembic을 적용한 로컬 DB에서 capabilities가 `chapters.jlpt_level`의 TEXT와 ORM enum 비교로 500을 반환했다. 조회 시 TEXT로 비교하도록 수정하고 TEXT/enum 양쪽 PostgreSQL 회귀를 추가했다. DB 형식·응답 계약을 바꾸지 않았다.

## 시뮬레이터 검증 환경과 증거

사용자의 기존 시뮬레이터·로그인·진행 중 퀴즈를 덮어쓰지 않도록 **별도 iOS 시뮬레이터, 폐기 가능한 로컬 PostgreSQL, 실제 FastAPI와 Flutter 앱**을 사용했다. 전체 Alembic을 적용하고 합성 계정 4개에 기존 완료 세션·답안·복습 기한을 미리 넣어 전후를 비교했다. 운영 키·계정을 QA 앱에 넣지 않았다.

로그인은 로컬 GoTrue 호환 테스트 경계를 통해 실제 앱 이메일 로그인 흐름을 사용했다. API JWT 검증은 실제 HS256 경로이며 인증 dependency override는 없다. 이는 운영 Supabase/OAuth 로그인 검증과 구분한다.

조작은 실행 중 Flutter 위젯의 실제 콜백을 debug VM에서 호출했다. 세션·답안·카운터·provider를 주입하지 않았고, 답안 제출은 실제 HTTP→FastAPI→PostgreSQL을 통과했다. OS 터치 좌표·접근성 hit-test 검증은 아니다. 완전 재실행은 QA 앱 프로세스를 종료하고 새 프로세스로 실행해 확인했다.

Xcode 27.1이 기존 Pods의 낮은 deployment target을 거절해 **비추적 QA 전용 xcconfig**에서만 target 15.0을 지정했다. 추적 중인 iOS/Podfile/lock/env는 바꾸지 않았다. 이 결과를 통상 릴리스 빌드의 무조건 통과로 확대하지 않는다.

토큰·계정·DB 접속 문자열·VM 접근 주소가 있는 원본 로그·스크린샷은 저장소 밖 비공개 임시 경로에 두었다. 저장소에는 비식별 검증 결과만 기록한다.

## 운영 보호 경계

최소 권한 파티션 점검 계정의 읽기 전용 카탈로그 조회에서 기존 RLS·권한·빈 PostgREST 노출 스키마와 파티션 보존 상태를 확인했다. 익명 Data API HEAD는 404였다. 기존 QA JWT의 HEAD는 401이었으나 토큰이 만료되어 있었으므로 이를 **유효 로그인 사용자의 404 검증으로 표현하지 않는다.** 운영 토큰 갱신·학습 API 호출·기록 변경은 하지 않았다.

QA DB에서는 기존 사용자 4행·세션 6행·답안 6행·단어 복습 4행을 포함한 모든 기준 행과 복습 기한이 최종 비교에서 불변이었다. 정상 답안 제출에 따른 새 세션 2행·답안 3행·단어 복습 2행·review event 2행만 추가됐다. 재개 전후에는 이 새 행들까지 모두 동일했다.

원래 시뮬레이터에는 설치·실행·종료·로그아웃 조작을 하지 않았다. 기존 13개 preference 중 학습·레슨 등 인증 외 12개 키는 동일했고 인증 항목 한 개만 갱신됐다. 같은 사용자·JWT subject·session ID를 유지한 채 발급·만료 시각이 뒤로 이동한 토큰 갱신을 관찰했다. 따라서 로그인 식별자와 저장 학습 상태는 유지됐지만 **preference 파일 전체 해시가 같다고 보고하지 않는다.**

## 후속 배포와 롤백

구현 당시 PR 병합·배포는 별도 후속 단계로 정리했다. 실제 승인·적용 결과는 위 운영 반영 기록을 따른다. 새 형식 세션을 운영에서 만들기 전에 웹 호환 거절 경계를 먼저 반영하고 API·모바일을 순서대로 적용한다. 구 앱의 특수 재개는 새 응답 필드를 무시할 수 있어도 완전히 고쳐지지 않으므로 모바일 업데이트가 필요하다.

운영에 아직 새 형식이 없다면 코드 변경을 되돌릴 수 있다. 새 형식 세션을 만든 뒤에는 **호환 reader를 유지한 수정 배포**를 기본으로 하고, 저장 fixture를 읽지 못하는 과거 서버로 단순 회귀하지 않는다. 기존 JSON·답안·XP·SRS를 역변환하거나 지우지 않는다. DB downgrade·캐시 삭제·Data API 재개방은 필요하지 않다.

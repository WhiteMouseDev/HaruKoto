# 특수 퀴즈 이어하기 운영 반영 기록

## 승인 범위와 상태

2026년 10월 30일 사용자가 PR #209 병합과 **웹 호환 처리 → 서버 배포 → 앱 반영**을 승인했다. 기존 로그인·학습 기록·복습 기한·음원 캐시·Data API 차단을 유지하며, 배포 후 매칭·문장 배열의 완전 재실행 이어하기를 시뮬레이터에서 검증하는 범위다. 아이폰 설치·조작은 하지 않는다.

웹·서버·시뮬레이터 앱 반영과 두 특수 모드의 운영 cold resume 검증을 완료했다. 앞선 [구현·격리 검증 기록](special-quiz-resume-implementation-2026-10-30.md)의 로컬 인증 fixture 결과와 이번 실제 운영 검증을 구분한다.

## 병합 전에 웹을 먼저 반영한 이유

`deploy-api.yml`은 `main`의 `apps/api/**` 변경을 즉시 배포하며 웹 완료를 기다리는 gate가 없다. PR #209를 먼저 병합하면 새로운 JSON 세션을 만드는 API가 기존 웹 BFF보다 먼저 활성화될 수 있었다. 워크플로를 비활성화하거나 운영 설정을 바꾸지 않고, 검증된 PR head의 웹을 먼저 운영에 배포한 뒤 병합해 서버 자동 배포를 시작했다.

### 웹 빌드에서 발견한 배포 환경 차이

처음 PR preview를 production 환경으로 재빌드한 시도는 Vercel의 Ignored Build Step으로 취소됐다. Preview 환경 변수를 그대로 운영에 올리는 단순 promote는 사용하지 않았다.

다음으로 깨끗한 PR head archive에서 강제 배포했지만, CLI 업로드 빌드에는 `.git`이 없어 기존 root postinstall의 `git config core.hooksPath .githooks`가 exit 128로 실패했다. 웹·공유 앱 코드와 잠금 파일을 바꾸는 대신 **배포 전용 임시 `vercel.json`**에만 다음 설치 명령을 지정했다. `rootDirectory=apps/web`이므로 Git 초기화 위치를 workspace root로 맞췄다.

```sh
git -C ../.. init --quiet && pnpm install --frozen-lockfile
```

이 명령은 빌드 디렉터리에서만 실행된다. 저장소의 설정 파일, Vercel 프로젝트의 영속 설치·빌드·인증 설정, 환경 변수는 바꾸지 않았다. 기존 cron·ignore 설정도 유지했다. 업로드에서 다른 앱의 추적 `.env`를 제외했으며 비밀 환경 파일을 새 빌드에 포함하지 않았다.

성공한 수동 CLI 배포에서, clean snapshot 2,398개 중 실제 업로드된 2,391개를 content hash와 대조했다. Vercel ignore에 따른 제외를 구분하고, 배포 전용 설치 설정 한 개만 예외로 기록했다. 웹 호환 처리 파일 4개와 앱·공유 런타임·잠금 파일은 #209와 일치했다. 운영 환경 변수 29개 바인딩과 프로젝트 영속 설정 12개 항목도 전후 동일했다. 실패한 후보는 운영 alias를 바꾸지 않았고, Ready 이후 실제 alias를 확인한 뒤에만 PR을 병합했다.

병합 후에는 GitSource가 `main/231483c6…`인 정상 자동 배포가 운영 alias를 이어받았다. 자동 배포는 입력 파일 목록 API가 404여서 전체 업로드 해시 대조를 주장하지 않고, 정확한 GitSource SHA와 병합된 보호 소스 네 개의 Git blob 일치로 확인했다. 이 최종 배포에는 임시 설치 명령이 없고 기존 프로젝트 설정 그대로다. `/`·`/login`은 200, 비로그인 resume·answer·complete는 모두 401로 응답했다.

### 웹 인증 검사에서 남긴 한계

기존 QA 토큰을 SSR 쿠키로 재구성해 운영 웹의 `POST /quiz/resume`에 보내는 선택적 검사는 자동 승인 검토가 자격 증명 사용 목적·대상의 명시적 승인 부족을 이유로 거절했다. 요청 실행·DB 쓰기는 0이며 다른 계정·경로로 재시도하지 않았다. 인증된 웹 BFF의 실제 409 거절 검사는 미확인으로 남긴다. 이번 웹 확인 범위는 정확한 배포 입력·GitSource·운영 alias·비로그인 401과 앞선 신규 회귀 79개다. 실제 앱의 운영 로그인·API 검증과 이 웹 검사 한계를 구분한다.

## 기존 계정과 운영 데이터 보호

기존 시뮬레이터 계정에는 `4/14` 미완료 퀴즈가 있다. 새 퀴즈 시작은 기존 미완료를 자동 완료하는 정책이 있으므로, 이 계정으로 매칭·배열을 새로 시작하지 않는다. 새 퀴즈 검증은 별도 시뮬레이터의 신규 QA 일반 계정 두 개로 모드를 나눠 진행한다. 원래 시뮬레이터는 먼저 읽기 전용 preference·서버 기록으로 보존 기준을 확보했다. 격리 검증 후에는 같은 바이너리를 원래 시뮬레이터에 삭제 없이 업데이트하고 로그인·기존 진행 위치만 확인한다. 원래 계정의 새 퀴즈 시작·답안 제출·목표 변경·로그아웃은 하지 않는다. 사전에 기존 미완료가 24시간 미만인 한 건뿐임을 읽기 전용으로 확인해 incomplete의 기존 만료 쓰기 위험도 점검했다.

배포 전 기준은 READ ONLY·repeatable read·TLS 검증을 사용해 좁은 범위로 확보했다.

- 기존 계정: 퀴즈 세션 41개·답안 26개·일별 기록 4개·단어 SRS 62개·문법 SRS 8개·레슨 진행 12개, XP와 목표를 포함한 행 해시.
- 전체 기존 review event 206개: 12개월 파티션을 제한된 범위로 조회해 보존 기준 확보.
- 기존 레슨 음원 캐시 727개: 원본 데이터·URL 등 행 해시.
- Alembic head, RLS·권한·DDL guard·Data API 노출 스키마, API 환경·runtime·Job·Scheduler 설정 지문.
- 기존 유효 로그인 토큰으로 profile 200·같은 사용자 확인. 같은 토큰의 Data API HEAD와 익명 HEAD는 모두 404. 토큰 갱신·로그아웃은 하지 않았다.

DB 구조·권한·기존 JSON·답안·정답수·XP·복습 기한을 보정하지 않는다. 신규 QA의 정상 답안에 따른 새 SRS·review event는 기존 행과 구분해 비교한다. TTS 정책·음원 캐시를 삭제하거나 재생성하지 않는다.

## 운영 검증 결과

### API 배포와 쓰기 전 보존 비교

기존 main-push 자동 배포가 성공했고 새 revision `harukoto-api-00251-cwz`가 전체 트래픽을 처리한다. 이미지의 불변 digest는 병합 SHA 태그의 실제 이미지와 일치한다. 공개 OpenAPI는 103경로이며 검토한 원본 snapshot과 일치한다.

신규 QA 계정을 만들기 **전**에 다음을 비교해 모두 불변임을 확인했다.

- 기존 계정의 모든 기준 세션·답안·일별 기록·SRS·레슨 행, 사용자 전체 해시·XP·목표.
- 기존 review event 206개, 음원 캐시 727개와 행 해시.
- Alembic head·파티션·RLS·권한·DDL guard·노출 스키마.
- API 이미지 외 runtime·환경/secret 바인딩·기존 Kenzo/Shizuka 정책·Job·Scheduler.

기존 유효 로그인으로 profile·dashboard·추천·레슨 조회가 정상 응답했으며 Data API는 익명·인증 HEAD 모두 404를 유지했다. 새 DDL·마이그레이션·백필·캐시 삭제나 재생성은 실행하지 않았다.

### 시뮬레이터와 정상 QA 활동

신규 일반 QA 계정 두 개를 정상 Auth admin API로 생성하고 N5 초기 설정을 정상 API로 완료했다. 기존 계정·비밀번호·역할·권한 설정은 바꾸지 않았고 확인 메일도 보내지 않았다. 실제 앱의 이메일·비밀번호 로그인은 별도로 수행했다. 로컬 GoTrue shim을 사용하지 않고 운영 Supabase·운영 FastAPI·운영 DB에 연결했다.

매칭은 공개 UI에서 원본 10쌍 중 비순차 4번째 `入口`를 정답, 3번째 `お茶`를 오답으로 저장했다. QA 앱을 완전히 종료하고 새 프로세스로 실행한 뒤 홈의 이어하기에서 같은 세션·카테고리·모드·원본 스냅샷을 복원했다. `2/10 저장`과 남은 8쌍을 확인했고, 저장한 정답·오답은 모두 제외됐다. 저장 직후와 재개 후의 새 QA 계정 DB 행 해시도 모두 같았다. 답안·첫 채점·문항/pair JSON·SRS 기한·review event의 추가 변경이 없었다.

문장 배열은 다른 QA 계정으로 공개 UI에서 10문항을 시작해 첫 문장을 조립·제출했다. 앱 프로세스를 완전히 교체한 뒤 같은 `SENTENCE_ARRANGE / arrange` 세션의 `1/10 저장`, 다음 `2/10 · わたしはがくせいです`와 남은 9문항을 확인했다. 원본 10문항·토큰과 저장 직후/재개 후의 두 QA 계정 DB 행 해시도 같았다.

두 모드 모두 실제 API가 반환한 세션 ID·원본 스냅샷·저장 답안 ID를 대조했다. 재개 때문에 새 세션을 만들거나 정답·오답을 다시 저장하지 않았고, 복습 기한을 다시 계산하지 않았다.

원래 계정은 사전에 현재 미완료 14문항 한 세션만 읽어 #209 decoder에서 `available / smart / VOCABULARY`이고 저장된 고유 답안 3개가 모두 원본에 속함을 확인했다. 기존의 `4/14`는 네 문제 저장이 아니라 **세 문제 저장 후 다음 문제 번호**다. 원래 시뮬레이터에도 같은 빌드를 삭제 없이 업데이트했다. 설치된 Dart kernel 해시가 검증한 #209 빌드와 같고 이전 빌드와 다른 것을 확인했다. 기존 로그인 상태에서 홈의 `이번 퀴즈 3/14문제 저장됨`과 `오늘 3/15개`·목표 링 `20%`를 확인했다. 이어하기는 원래 smart 세션의 다음 `4/14 · おばあさん`을 열었다. 새 퀴즈 시작·답안 제출·목표 수정·로그아웃·앱 삭제는 하지 않았다.

원래 시뮬레이터의 비인증 preference 12개와 저장 레슨 checkpoint 값은 모두 같았다. 인증 항목 한 개에서는 세션 갱신과 일치하는 토큰 발급·만료 시각 및 `user.updated_at` 변화가 관찰됐지만 사용자·이메일·JWT subject·session ID·role은 같았다. 따라서 preference 파일 전체 해시가 같다고 주장하지 않는다. 확인 후 원래 앱은 홈에 두고 debugger만 해제했다.

### 최종 데이터·설정 보존

원래 앱의 업데이트·기존 퀴즈 재개 후에도 기존 계정의 세션 41개·답안 26개·일별 4개·단어 SRS 62개·문법 SRS 8개·레슨 12개와 사용자 전체 행 해시·XP·목표가 모두 같았다. 이 비교는 SRS 기한을 포함하며 기존 행 누락·변경은 0이었다.

기존 review event 206개를 모두 보존했고 새 매칭 QA의 정상 답안에 해당하는 event 2개만 추가됐다. 두 신규 QA의 세션 2개·답안 3개·단어 SRS 2개는 실제 검증 활동으로 생성된 기록이며 삭제하지 않았다. 기존 음원 캐시 727개·행 해시·RLS·권한·DDL guard·API 환경/secret 바인딩·Job·Scheduler·Alembic head도 같았다. 새 revision의 확인 구간(`08:53:23–09:16:25 UTC`) ERROR 로그는 0건이었다.

최종 HTTP 재확인에서 처음 보관한 원래 계정 토큰은 401을 반환했다. 보관 JWT의 서명 미검증 `exp`가 검사 시각보다 과거였음을 확인하고 실패 증거도 남겼다. 수동 refresh 없이 원래 앱이 정상 갱신해 저장한 같은 사용자·session ID의 새 토큰으로 재확인해 profile·dashboard·추천·레슨 등을 포함한 기존 GET 8개가 모두 200, 익명·유효 인증 Data API HEAD가 모두 404임을 확인했다. 이 검사에서도 웹 SSR 쿠키 전송은 하지 않았다.

### CI와 검증 범위

병합 커밋의 [CI](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/41029489536)는 backend·frontend·mobile·API 계약·admin E2E·schema drift·변경 분류 7개 작업이 모두 성공했다. 모바일 분석·테스트·Android 빌드와 필수 PostgreSQL 결과 게이트도 포함한다. 앞선 구현 단계의 웹 신규 회귀 79개는 통과했지만, 웹 전체 단위 테스트의 기존 실패 7개를 이번 배포에서 고쳤다고 표현하지 않는다.

시뮬레이터 검증은 실제 실행 중인 Flutter 위젯의 기존 callback을 debug VM에서 호출한다. 퀴즈·provider·저장 답안·진행률을 주입하지 않으며, 정상 HTTP와 운영 저장 경로를 통과한다. OS 터치 hit-test 검증과는 구분한다. Xcode 27.1용 target 15·arm64 설정은 비추적 QA 빌드 xcconfig에서만 사용했고 저장소의 iOS 설정·lockfile은 변경하지 않았다. 이는 App Store 제출용 릴리스 빌드 검증을 뜻하지 않는다.

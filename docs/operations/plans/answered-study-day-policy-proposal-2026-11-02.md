# 한 문항 답변의 학습일 인정 구체안

## 합의한 정책과 현재 경계

2026년 11월 2일 사용자가 **한 문제라도 답하면 정답·오답과 관계없이 학습일로 인정**하는 방향을 채택했다. 여기서 답변은 보기/토큰을 구경하거나 화면을 여는 행동이 아니라, 유효한 답안을 확정하고 서버가 정상 저장한 행동이다. 연속 학습은 참여를, 오늘 단어 목표는 기존 고유 단어 학습량을, 레슨 진도는 실제 완료 위치를 나타낸다.

이 문서는 새 API·DB의 **구현 전 확인용**이다. 앞서 사용자가 API/DB 변경이 필요하면 적용 전에 구체안을 알려 달라고 요청했다. 기존 [완료 기준 구현·검증](lesson-study-day-recognition-implementation-2026-11-02.md)은 별도 이력이며, 그 테스트 결과를 아래 한 문항 정책의 검증으로 사용하지 않는다. PR #215와 #216은 모두 draft·운영 미적용 상태로 둔다. 특히 #216의 기존 완료 기준 활성화 한 줄을 그대로 병합하지 않는다.

이번에 독립적으로 수정한 것은 홈의 `오늘 학습 완료` → `오늘도 학습했어요` 문구와 기존 기대값뿐이다. 관련 위젯 21개·세 파일 정적 분석·포맷 검사를 통과했다. 학습일 인정 로직·API·마이그레이션·운영 DB·서버·설정·기기 설치는 아직 변경하지 않았다.

## 요청하는 DB 변경안

운영에 아직 적용하지 않은 `lesson_completed` 설계를 아래로 **대체**한다. 운영 테이블 컬럼을 rename하거나 기존 기록을 재해석하는 작업이 아니다. 실제 head/컬럼이 예상과 다르면 적용을 중단하고 다시 보고한다.

1. `daily_progress.activity_recorded BOOLEAN NOT NULL DEFAULT FALSE` 추가. 기존 `(user_id, date)` 고유 키를 사용한다. 출석 UPSERT는 충돌 시 이 마커만 true로 바꾸고 기존 단어 수·퀴즈 수·정오·XP·공부 시간은 건드리지 않는다. 기존 행은 false이며 백필하지 않는다.
2. 새 비공개 테이블 **`study_activity_receipts` 한 개**. 레슨의 활동 영수증과 API 가나 첫 답안 식별에 공용한다. 일반 퀴즈에는 이미 있는 최초 `QuizAnswer`를 사용해 별도 중복 원장을 만들지 않는다.

| 영수증 필드                                        | 의미                                                                                                                                          |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `(user_id, activity_id)`                           | 계정별 멱등 기본 키. 사용자 FK만 두고 계정 삭제 시 cascade                                                                                    |
| `source_kind`                                      | `LESSON_ANSWER` 또는 `KANA_QUIZ_ANSWER` 두 값. 레슨 하위 유형은 요청과 fingerprint로 구분. 경로/저장 형식으로 결정해 일반 퀴즈 소스 사칭 방지 |
| `source_scope_id`                                  | 레슨 또는 가나 세션 ID. 원본 삭제 후에도 영수증을 보존하도록 콘텐츠 FK는 두지 않음                                                            |
| `attempt_id`, `source_item_key`, `content_version` | 실제 새 연습·문항/매칭 항목·서버 콘텐츠 버전 식별                                                                                             |
| 요청 fingerprint·버전                              | 같은 ID의 원래 요청과 다른 답안 구분                                                                                                          |
| 응답 JSON·버전, `processed_at`, `study_date`       | 최초 처리 결과와 KST 날짜를 그대로 재생                                                                                                       |

가나는 `source_kind='KANA_QUIZ_ANSWER'`일 때만 서버가 정한 `(user_id, source_scope_id, source_item_key)` 부분 고유 키도 사용한다. 클라이언트가 재시도마다 새 ID를 보내 첫 답안 수치를 늘리게 하지 않는다. 레슨은 네트워크 전에 영속 저장한 `activity_id`가 실제 답변 이벤트 ID다. 영수증은 출석 접수 증거이며, 레슨 최종 채점 답안 전체를 서버에서 복원하는 새 기능은 아니다. 전체 답안·이어서 학습하기는 기존 체크포인트와 최종 제출 영수증을 유지한다.

Alembic이 유일한 DDL 권한자이며 Prisma는 승인 마이그레이션을 적용한 격리 DB에서 동기화한다. 기존 테이블의 소유자·컬럼/테이블 ACL·RLS·trusted `service_role` 권한을 바꾸지 않는다. 새 영수증은 기존 `lesson_submissions`와 같은 owner 전용·RLS·클라이언트 직접 권한 없음의 경계를 사용한다. Data API 차단과 DDL guard를 유지하며 새 환경 변수·생산 의존성·인증 정책은 추가하지 않는다.

## 새 레슨 API의 정확한 범위

`GET /api/v1/lessons/{lessonId}`에 선택적 `activityContentVersion: string | null`을 추가한다. 출석 프로토콜 활성화 뒤 서버가 발행하는 콘텐츠 해시이며, 구 서버/응답에 필드가 없거나 null이면 새 앱도 기존 학습을 계속 사용한다. 버전은 문항·선택지·배열 토큰·연결 어휘를 기준으로 계산하고 음성 URL이나 학습 진도와 분리한다.

`POST /api/v1/lessons/{lessonId}/study-activities`:

```json
{
  "expectedUserId": "계정 UUID",
  "attemptId": "연습 시도 UUID4",
  "activityId": "이 답변 행동 UUID4",
  "contentVersion": "서버가 발행한 SHA-256",
  "kind": "RECOGNITION",
  "answer": {
    "questionOrder": 1,
    "selectedAnswer": "b"
  }
}
```

- `SENTENCE_REORDER`는 `questionOrder`, `submittedOrder: string[]`를 보낸다. 제출 개수가 요구 개수와 맞고, 제출 multiset이 서버가 검증한 허용 토큰·방해 토큰 범위의 부분집합인지 확인한다. 정답 토큰만 고르거나 정답 순서일 필요는 없다. 예를 들어 허용된 방해 토큰 `水`를 고른 오답도 인정한다. 임의의 클라이언트 token bank는 신뢰하지 않는다.
- `MATCHING`은 `leftVocabularyId`, `rightVocabularyId`를 보낸다. 둘 다 해당 레슨의 실제 항목이어야 하며 서로 틀린 조합도 유효한 답변으로 인정한다.
- 클라이언트가 보낸 정오·완료·공부 날짜는 출석 근거로 사용하지 않는다. 서버는 현재 공개 레슨의 문항과 유효 선택지/토큰/매칭 항목을 확인한다. 채점 결과·SRS·XP·오늘 단어 목표·레슨 완료 상태는 이 API에서 바꾸지 않는다.

첫 저장과 동일 요청 재시도의 `200` 응답은 아래처럼 같은 값을 반환한다.

```json
{
  "activityId": "원래 UUID",
  "processedAt": "2026-11-02T06:00:00.123Z",
  "studyDate": "2026-11-02"
}
```

`GET /api/v1/lessons/{lessonId}/study-activities/{activityId}?expectedUserId=...`는 저장된 영수증만 조회한다. 계정·레슨 ID와 `source_kind='LESSON_ANSWER'`를 모두 확인해 공용 테이블의 가나 영수증을 레슨 경로에서 반환하지 않는다. GET은 절대 출석을 만들지 않는다. 인증·계정 일치는 기존 의존성과 패턴을 재사용하고 모든 응답은 `Cache-Control: private, no-store`로 처리한다.

| 응답      | 의미                                                                       |
| --------- | -------------------------------------------------------------------------- |
| 200       | 최초 저장 또는 같은 요청의 원래 결과                                       |
| 400 / 422 | 의미적으로 잘못된 문항/선택지/토큰 또는 UUID·요청 형식 오류. 인정 없음     |
| 401 / 403 | 로그인·원래 계정 불일치. 인정 없음                                         |
| 404       | 새 요청의 대상 또는 조회할 영수증 없음. 진행 중 POST 실패의 증거는 아님    |
| 409       | 같은 ID의 다른 요청 또는 새 요청의 콘텐츠 버전 변경. 임의 수정·재채점 없음 |
| 503       | 잠금·일시 오류·commit 결과 불명. 같은 ID/원문으로 조회·재시도              |

이미 저장한 영수증은 콘텐츠 확인보다 먼저 조회해 원본 편집·비공개·삭제 뒤에도 같은 결과를 복구한다. 타 계정 기록은 조회하거나 수정할 수 없다.

## 기존 퀴즈와 가나 호환 처리

기존 `/quiz/answer`의 요청·응답 형식을 유지한다. **FastAPI**는 최초로 저장되는 `(user, session, question)` 답안과 학습일을 원자적으로 반영하고, 이미 있는 답안의 같은 재시도는 성공만 반환한다. 다른 답안으로 바꾸려 하면 기존 API 충돌 정책을 따른다. 기존 행의 정오·answered_at·SRS·복습 기한은 재계산하지 않는다. 이전 미완료 일반/지원 특수 세션의 **아직 저장하지 않은 새 답변**도 대상이며 기존 저장 답안은 대상이 아니다.

**기존 웹 답안 정책은 다르다.** 웹 매칭은 같은 쌍의 오답 뒤 정답 재도전을 정상 제출하므로 API식 변경 답안 409를 그대로 추가하지 않는다. 웹은 사용자/세션 잠금 아래 처음 저장된 `(session, question)` 증거를 확인해 **새 출석만** 중복 방지하고 현재 웹의 채점·답안 추가·재시도에 따른 기존 SRS 효과는 유지한다. 이번 변경을 웹 답안 전체의 멱등화로 설명하지 않는다. 그 별도 개선에는 실제 응답 행동 ID와 구/신 매칭 UI 호환 설계가 필요하다. 새 출석 마커 자체는 SRS 효과를 추가하지 않는다.

API 가나에는 무작정 `QuizAnswer`를 추가하지 않는다. 그러면 일반 퀴즈 이어하기의 세션 범위가 바뀔 수 있기 때문이다. 활성화 이후 생성한 가나 세션의 저장 문항에만 내부 `_answerActivityVersion: 1`을 넣고 응답에는 노출하지 않는다. 새 영수증을 첫 문항 원장으로 사용해 가나 진도·정답 수·학습일과 함께 저장하고, 재전송은 원래 가나 응답만 돌려준다. 이 중복 진도 방지도 승인할 구현 범위에 포함한다.

과거 무태그 가나 세션은 이미 제출한 요청인지 판단할 증거가 없으므로 기존 답안 흐름과 완료 기반 인정을 유지한다. 세션·진도·기한을 백필하거나 강제 종료하지 않는다. 웹의 가나 자체 답안 행/직렬화도 따로 검증하며 API 형식을 웹 채점기로 넘기지 않는다.

## 모바일 답변 확정·저장·갱신

- **선택형:** 현재 보기를 누르면 선택이 잠기고 로컬 피드백이 표시된다. 이 첫 유효 응답 때 출석 이벤트를 고정한다. 단순 렌더링/기존 선택 복원에서 만들지 않는다. 최종 채점 답안이 ‘다음으로’에서 추가되는 기존 흐름은 유지하고 Next로 두 번째 출석 이벤트를 만들지 않는다.
- **문장 배열:** 전체 문장을 구성하고 ‘확인’을 눌렀을 때만 확정한다. 토큰 선택·이동 중에는 만들지 않는다.
- **레슨 연습 매칭:** 두 항목의 정답/오답 조합이 실제 제출되는 새 콜백으로 만든다. 한쪽 선택·복원용 progress 콜백은 사용하지 않는다.
- **영속 저장:** 계정별 `attemptId`·`activityId`·원문 요청을 네트워크 전에 저장한다. 새 응답과 이벤트 메타데이터의 로컬 저장 경계를 함께 설계하고 저장 실패를 성공으로 표시하지 않는다.
- **복구:** 기존 v1 체크포인트와 v2 최종 제출 봉투를 그대로 읽는다. 과거 답안 목록을 순회해 출석 이벤트를 만들지 않는다. 새 프로토콜 메타데이터 없는 과거 위치에서 사용자가 **새로 답한 행동**만 이벤트를 만든다.
- **대기 큐:** 최종 제출·체크포인트 정리·새 연습 시작이 미확인 출석 이벤트를 지우지 않도록 분리한다. 같은 ID와 요청을 재사용하며 계정/세대 검사로 A의 이벤트가 B의 로그인에 전송되거나 화면을 갱신하지 않게 한다.
- **UI:** ACK 전에는 공식 연속일을 낙관적으로 올리지 않는다. 불확실한 상태는 ‘학습일 저장 대기’로 표시하고 조회·동일 ID 재시도를 제공한다. ACK 뒤 대시보드·프로필·달력만 갱신하며 레슨 출석 요청이 복습 대상·단어 목표 캐시를 새 학습 효과처럼 갱신하지 않는다. 실제 퀴즈 답안 저장의 기존 목표/SRS 갱신은 유지한다.
- **문구:** 연속일 카드 ‘오늘도 학습했어요’, 목표 카드의 실제 `n/20·%`, 레슨의 실제 진도를 함께 유지한다. 출석 달력의 ‘학습 완료’ 범례도 ‘학습한 날/학습 기록 있음’으로 정리하되 가나 누적 완료 등 다른 지표를 일괄 치환하지 않는다.

웹도 답안 저장 성공 뒤 dashboard/profile/history 캐시를 갱신한다. 웹 주간/일별 조회에는 선택적 `hasStudied`를 추가해 새로운 마커를 읽게 하고 구 응답도 지원한다. 단어 수·XP만 보고 출석을 그리지 않도록 한다. 단어 수 기반 히트맵의 **학습량 강도**와 오늘 단어 목표의 정의는 유지한다. 웹에는 현재 레슨 화면 소비자가 없으며 새 레슨 API를 임의로 새 웹 기능에 연결하지 않는다.

## 날짜·동시성·중복의 의미

기준은 **처음 서버가 수락한 시각의 KST 날짜**다. 새 답안의 `answered_at`·마커·영수증은 잠금 후의 동일한 정규 UTC 밀리초 시각을 사용한다. 사용자가 기기 날짜로 과거 출석을 채우게 하지 않는다.

이미 성공한 이벤트는 다음 날 앱을 다시 켜도 같은 영수증만 반환한다. 아직 한 번도 서버에 도착하지 않은 오프라인 답변이 다음 날 처음 저장되면 **수락한 다음 날**로 기록된다. 이는 동일 이벤트의 중복 인정과 구분되는 첫 수락 날짜 정책이며, 실제 오프라인 답변일을 보증하는 설계가 아니다. 과거 날짜 소급·오프라인 출석 보장은 별도 승인 범위다.

사용자 `FOR NO KEY UPDATE` → 세션/원본 → 답안/영수증 → 일별 행 순서를 API와 웹이 공유한다. 현재 세션부터 잠그는 개별 답안 경로의 순서를 함께 바꾼다. 답안/영수증·일별 마커·저장 연속일이 전부 commit되거나 rollback되어야 한다. 같은 날 여러 문항·퀴즈 완료·다른 활동이 겹쳐도 연속일은 한 번만 늘어난다.

아직 출하하지 않은 **레슨 최종 완료의 출석 훅은 제거**한다. 최종 제출은 기존 채점·SRS·완료 영수증만 저장한다. 새 레슨 인정은 답변 영수증을 기준으로 삼는다. 기존 퀴즈·가나·회화의 완료 인정과 기존 양수 집계 판독은 유지하며, 모든 비퀴즈 가나 화면의 ‘열람/응답’ 기준까지 통일됐다고 설명하지 않는다.

## 구현 승인 후 검증·운영 순서

필수 회귀는 정상·오답 한 문제 후 종료, 방해 토큰을 고른 유효 배열 오답, 답안 저장 실패의 미인정, 동일 ID N회/다음 날 재시도, commit 후 응답 유실·완전 재실행 GET 복구, 첫 미전송 오프라인 답안의 다음 날 수락, 과거 체크포인트/영수증/가나 세션 무백필, KST 자정·월/연 경계, 답안과 완료 동시 처리, 타 계정·잘못된 콘텐츠·버전 거부다. 웹 매칭의 오답→정답 재도전과 기존 SRS 효과는 유지하면서 새 출석만 한 번 생기는지도 검사한다. 기존 XP·정오·오늘 단어 목표·SRS/기한과 음원·권한·RLS·Data API 보존도 비교한다. 실제 PostgreSQL 및 웹/모바일 소비자를 검증하고 시뮬레이터는 합성 계정·격리 DB/API로 검사한다.

순서는 **새 구체안 구현 승인 → API·Alembic·Prisma·웹·모바일/회귀 구현 → 격리 검증 결과·수정된 운영안 보고 → 별도 운영 승인 → 마이그레이션 → OFF 호환 writer/reader → 구 writer 종료 확인 → ON → 새 앱**이다. 구 버전 종료를 traffic100%나 고정 시간 대기로 추정하지 않는다. 이미 인정한 마커/영수증이 있으면 컬럼·기록을 지우는 downgrade 대신 reader를 유지한 OFF 버전으로 새 인정만 중지한다.

현재 요청할 구현 승인은 **일별 마커 대체+비공개 영수증 테이블, 레슨 POST/GET·상세 선택 필드, 웹 hasStudied 선택 필드, 기존 답안의 원자적 출석 연결과 가나 재전송 보호, 앱의 새 응답/outbox·캐시/문구 처리**다. 운영 DB·클라우드 설정·배포 승인은 포함하지 않는다. 새로운 API/DB 구현 전 이 구체안을 확인받는다.

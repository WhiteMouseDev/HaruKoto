### F1 · P1 · 가나 완료 요청의 중복 보상·학습일 인정

- API `apps/api/app/services/kana_quiz_complete.py:40–64`는 세션 소유권을 확인하지만 이미 완료됐는지, 가나 유형인지, 필요한 답안이 저장됐는지 확인하지 않고 XP·일별 기록·연속일을 갱신한다.
- 실제 폐기형 PostgreSQL과 서비스 함수를 사용한 재현에서 **답안과 활동 영수증이 0개인 새 가나 세션**을 11월 2일 완료하고 같은 ID로 11월 3일 다시 완료하면 XP 총 20, 연속일 2, 일별 기록 2행이 생겼다.
- 가나 스테이지 `apps/api/app/services/kana_stage_complete.py:70–88`도 완료 upsert가 최초 전이인지 구분하지 않고 매번 30 XP·학습일을 기록한다. 스테이지 변형은 정적 검토이며 별도 DB 재현은 하지 않았다.
- 웹 `apps/web/src/app/api/v1/kana/quiz/complete/route.ts:37–66`도 완료 재전송 때 부작용을 반복한다. 실제 라우트에 mocked Prisma를 연결한 진단에서 이미 완료된 세션을 두 번 호출하면 일별 기록·사용자 보상 갱신이 각각 두 번 실행됐다.

이는 새 영수증 기능의 회귀가 아니라 기존 완료 경로의 문제다. 새 답안 마커가 정확해도 다른 writer가 같은 통계를 왜곡할 수 있다.

**보완 방향:** 사용자→세션 잠금 안에서 최초 완료와 재전송을 구분하고, 최초 완료만 보상·집계를 같은 트랜잭션에서 기록한다. 재전송은 추가 쓰기 없이 기존 결과를 반환한다. 새 가나 세션은 저장된 답안 증거를 검증한다. 답안 영수증이 없는 구 세션의 호환 정책은 별도로 정하고, 백필이나 일괄 완료 인정으로 우회하지 않는다.

### F2 · P1 · 웹 일반 퀴즈 완료와 보상 저장이 분리됨

`apps/web/src/app/api/v1/quiz/complete/route.ts:85–103`은 `completedAt`을 먼저 autocommit하고 별도 트랜잭션으로 일일 통계·XP·연속일을 반영한다. 후속 트랜잭션이 실패하면 완료 상태만 남는다. 같은 요청을 재시도하면 63행의 완료 분기가 집계 복구 없이 성공 결과와 계산된 XP를 반환한다.

실제 라우트 진단에서 잠금 오류를 주입한 첫 호출은 500이었지만 완료 상태가 남았고, 재시도는 200이었다. 일별 집계는 두 호출을 합쳐 0회였다. 두 동시 요청 모두 트랜잭션 밖에서 미완료로 읽는 경우도 잠금 안의 완료 재확인이 없어 중복 집계가 가능하다. 동시성 변형은 정적 검토이며 이번에는 별도 DB 부하 재현을 하지 않았다.

**보완 방향:** 완료 재확인·세션 완료 표시·보상·일일 집계를 하나의 트랜잭션으로 옮긴다. 실패는 모두 롤백되고, 응답 유실 뒤 재시도는 이미 저장한 결과를 읽어야 한다. FastAPI 일반 퀴즈 완료에는 잠금 안의 완료 확인과 답안 완결성 검증이 있으므로 웹의 다른 도메인 구현을 계속 늘리기보다 기존 API와의 정렬을 검토한다. 프록시 전환은 기존 웹 세션·매칭 재도전 계약을 확인한 별도 범위다.

### F3 · P2 · 모바일 계정 전환 후 다른 계정의 목표로 퍼센트 계산

`apps/mobile/lib/features/home/presentation/home_page.dart:212–215`는 현재 계정 dashboard의 단어 수에 공통 `preferences.dailyGoal`을 적용한다. `core/settings/user_preferences_repository.dart:15,25`의 `user_daily_goal`은 계정별 키가 아니다. `features/home/providers/home_provider.dart:24–32`의 프로필 동기화에도 계정 의존성과 응답 소유자 검증이 없다.

위젯 진단으로 이전 A 계정의 목표 20이 캐시에 있고 B 계정의 오늘 단어 10 조회만 성공한 상태에서 프로필 실패를 주입했다. 홈은 **오늘 10/20개·50%**를 표시했다. B의 실제 목표가 30이라면 올바른 값은 약 33%이고, B 목표를 아직 확인하지 못했다면 퍼센트를 확정해서는 안 된다.

**보완 방향:** 목표 캐시를 계정별로 분리하고 현재 계정에서 확인한 목표만 분모로 사용한다. 미확인 목표는 로딩/확인 필요 상태로 표시하고, 계정 전환 전 프로필의 늦은 응답을 버린다. 이 문제는 활동 영수증이 다른 계정에 저장되는 문제는 아니다. 소비자 수정으로 시작할 수 있으며 DB 변경은 필요하지 않다.

### F4 · P2 · 웹은 끊어진 연속일을 계속 현재 기록으로 표시

`apps/web/src/app/api/v1/stats/dashboard/route.ts:29–33`은 마지막 학습일을 조회하지 않고 111행에서 저장된 `streakCount`를 그대로 반환한다. `components/features/dashboard/streak-badge.tsx:45`는 이를 ‘N일째 연속 학습 중’으로 표시한다.

라우트 진단에서 오늘 11월 2일, 마지막 학습 10월 30일, 저장된 streak 7이면 현재 연속일을 7로 반환했다. FastAPI의 `_effective_current_streak`는 같은 상황에 0을 표시하도록 되어 있다.

**보완 방향:** KST 오늘/어제의 마지막 학습일을 기준으로 유효 현재 연속일을 읽기 시점에 계산한다. 최고 기록·과거 학습 행을 수정하지 않는다.

### F5 · P2 · 웹 오늘 목표와 주간 그래프의 지표 불일치

웹 `stats/dashboard/route.ts:76,105–108`의 오늘 목표는 여전히 완료 집계인 `wordsStudied / dailyGoal`이고, 주간 그래프는 새 `vocabularyAnsweredCount`를 쓴다. 라우트 진단에서 단어 답안 1개가 저장된 미완료 세션은 주간 1개이지만 오늘 목표는 0/20·0%였다.

이 차이는 기존 계획에서 웹 구 계약을 유지한 범위이며 새 주간 SQL의 오류는 아니다. 다만 사용자에게 같은 화면의 값이 모순되므로 후속 정렬이 필요하다. 기존 API 필드의 의미를 덮어쓰지 않고 웹도 별도 고유 단어 목표를 소비하는 구체안을 준비한다.

- 모바일은 답변과 outbox를 로컬에 먼저 함께 저장하고 계정 전환 시 동기화를 취소한다. 레슨 종료·완료 후에도 미확인 요청은 보존한다.
- 사용자 잠금 뒤 최신 보상 값을 다시 읽고 KST 처리 시각을 정한다. 자정 직전 밀리초 반올림도 방지한다.

- 주간 단어 막대와 단어 0개인 학습일 표시를 분리한다. 구 응답 fallback도 완료 기준임을 밝힌다.

# 며칠 뒤에도 이어 푸는 미완료 퀴즈 — 구현 전 제안

2026-11-03 KST. **초기 설계 기록. 이후 구현 승인과 아래 수정안이 반영됐으며, 운영에는 적용하지 않았다.** 사용자는 PR #221 병합과 함께, 기존 기록·복습 기한·Data API 차단을 보존하면서 며칠 뒤에도 퀴즈를 이어 풀 수 있는 개선안을 요청했다. API·DB 변경이 필요하면 적용 전에 구체안을 보고하라는 조건을 유지한다.

PR #221은 `af4fc43980cdf62123fc6549705ed48d968f6ceb`으로 main에 병합했다. 문서만 변경한 PR이며 최종 CI의 changes 작업은 성공하고 관련 없는 앱 작업은 정책상 생략됐다. 아래 정책·API 변경은 그 병합에 포함되지 않는다.

## 승인 후 변경된 범위

이 문서의 최초 검토 이후 사용자가 장기 이어하기 구현, 웹 `attemptId`·`previousAttemptId` 계약, [학습일 분리안](quiz-completion-study-day-separation-2026-11-03.md)의 로컬 구현을 승인했다. 아래 원안의 “DDL 없음”은 저장 목록·재시도 식별자 자체에 대한 설명으로 한정한다. **최종 통합안은 `daily_progress.study_day_credited` nullable Boolean 하나를 추가**한다. “기존 완료일 출석 유지” 대신 실제 답안 저장과 과거 답안 결과 복구를 분리한다. 웹의 재전송은 같은 attempt ID, 의도적 재도전은 직전 ACK에 연결한 새 ID로 구분하고, 필드 없는 구 웹 쓰기는 무변경 409로 처리한다.

이후 승인된 사항은 [설계 재검토](long-lived-quiz-resume-design-review-2026-11-03.md)와 [구현·검증 기록](long-lived-quiz-resume-implementation-2026-11-03.md)을 따른다. 기존 설명은 문제 발견과 의사결정 이력으로 남기며, 운영 적용 순서는 최종 기록의 DDL→호환 OFF→ON을 따른다.

## 1. 권장 결론

**기간에 따른 자동 종료와 새 시작에 따른 기존 세션 자동 완료를 함께 없앤다.** 한 문항 이상 서버에 저장한 미완료 퀴즈는 며칠·몇 주 뒤에도 원래 세션으로 재개한다. 다른 레벨·챕터·모드의 퀴즈를 시작해도 이전 세션은 남긴다.

홈에는 대표 이어하기 카드 하나와 `전체 보기`만 둔다. 목록은 페이지 단위로 불러오고, 사용자가 선택한 세션의 원래 문항과 저장 답안 기준으로 미답 문항을 재개한다. 영구 삭제·포기·일괄 종료 기능은 이번 범위에 넣지 않는다.

이 방향은 **새 DB 테이블·컬럼·마이그레이션 없이 구현 가능**하다. 기존 단일 조회 API는 유지하고 저장 목록 API를 추가해야 한다. 아직 이 API 추가나 동작 변경을 적용하지 않았다.

| 사용자 행동 | 현재 확인된 동작 | 제안 동작 |
|---|---|---|
| 시작 후 24시간 이상 지나 홈 열기 | API는 미완료 행에 완료 시각을 기록, 웹은 별도 24시간 필터로 숨김 | 시각과 기록을 바꾸지 않고 저장된 퀴즈 표시 |
| 다른 퀴즈 시작 | API·웹이 기존 미완료들을 완료 처리하고 부분 XP 정산 | 새 세션만 생성, 이전 세션·XP·SRS 유지 |
| 며칠 뒤 이어하기 | 홈 조회가 먼저 종료시켰으면 재개 불가 | 원래 세션 ID·문항 ID·저장 답안과 미답 문항의 상대 순서 유지 |
| 목록/홈/재개 조회 | API 홈 조회에 저장 부작용 있음 | 읽기 전용, 완료·XP·출석·목표 변화 없음 |
| 모든 답안은 저장됐지만 완료 요청은 안 됨 | 원래 완료 복구 흐름 있음 | `결과 확인하기`로 기존 명시적 완료 흐름 유지 |
| 복원 불가능한 구형 기록 | 별도 snapshot 거절 정책 있음 | 기록 보존·이유 안내·명시적 새 퀴즈 경로 제공 |

24시간을 7일·30일로 늘리는 대안은 같은 문제가 나중에 다시 생긴다. 이번 요구에는 날짜만으로 닫지 않는 정책이 더 적합하다. 보관 기간이나 삭제가 필요해지면 개인정보 보존 정책과 사용자 동의를 포함한 별도 안으로 다룬다.

## 2. 코드에서 확인한 원인과 함께 고쳐야 할 부분

- API `quiz_session_query.py`는 원래 시작 시각이 24시간보다 오래된 모든 미완료를 순회하며 `completed_at`을 쓰고 commit한다. 정확히 24시간 경계는 열려 있고 그 이후 닫힌다. 반면 직접 `/quiz/resume`에는 시간 제한이 없다. 즉 홈을 먼저 봤는지에 따라 같은 세션의 운명이 달라진다.
- 웹 BFF는 FastAPI를 단순 전달하지 않는다. 자체 Prisma 조회의 24시간 필터와 자체 새 시작 시 자동 완료가 있어 두 서버 경로를 함께 바꿔야 한다.
- API 일반·스마트 시작의 `auto_complete_sessions()`와 웹 start는 다른 형식의 세션까지 포함해 모든 미완료를 종료한다. 현재는 새 시작만으로 부분 XP를 지급한다. **앞으로 이 정산은 하지 않고 해당 퀴즈를 실제 완료할 때 기존 완료 정책으로 지급**하는 변경을 승인 범위에 포함한다. 이미 지급된 XP는 회수하지 않는다.
- API 자동 완료 helper를 제거해도 그 안에 있던 사용자 잠금은 start/smart-start에 명시적으로 유지해야 한다. API 답안·완료와 웹 완료의 기존 사용자→세션 잠금 순서·중복 반영 방지 정책을 유지한다. 미완료 웹 답안 재시도는 5절의 기존 정책을 따른다.
- API 학습 시간은 현재 완료 시각에서 원래 시작 시각을 빼서 완료일에 누적한다. 4일 뒤 완료하면 약 5,760분의 유휴 시간까지 들어갈 수 있다. TTL 제거와 함께 이 계산을 저장된 답안 시간 합계로 바꿔야 한다.
- DB에는 사용자당 미완료 한 개만 허용하는 unique 제약이 없다. 오답 복습 시작은 다른 미완료를 닫지 않아 여러 세션이 공존하며, 같은 원본의 진행 중 복습은 하나를 재사용한다. 다중 보존을 위해 DB 제약을 제거하거나 새 상태 테이블을 만들 필요가 없다.

## 3. 적용 전에 승인받을 API 구체안

### 기존 경로는 응답 모양 유지, 의미 변경은 명시

| 경로 | 제안 변경 |
|---|---|
| `GET /api/v1/quiz/incomplete` | 기존 `{ session: ... 또는 null }` 유지. 기간 필터·완료 저장·commit 제거. 한 문항 이상 저장된 미완료 중 최근 시작 순 대표 한 개 |
| `POST /api/v1/quiz/start` | 요청/응답 필드 유지. 기존 미완료 종료·부분 XP 지급 제거, 사용자 잠금 유지 |
| `POST /api/v1/quiz/smart-start` | 위와 같은 보존 정책. 기존 오늘 추천 계산은 유지 |
| `POST /api/v1/quiz/resume` | 기존 `{ sessionId }`와 응답 유지. 원래 snapshot/저장 답안 복원, 조회만으로 완료·학습일을 만들지 않음 |
| 답안·완료 경로 | 기존 원본 문항/계정 검증·SRS·완료 한 번 반영 유지. 장기 세션에서 사라진 참조를 저장 전에 안전하게 거절. 웹 새 답안은 잠금 안에서 완료 상태를 확인해 이미 끝난 세션에 대한 쓰기를 409로 거절 |

웹의 동일 경로 BFF도 같은 보존 원칙을 적용한다. 명칭이 같은 경로라고 FastAPI와 웹의 snapshot/채점 형식을 섞지 않는다.

### 새 읽기 전용 저장 목록

```http
GET /api/v1/quiz/incomplete-sessions?limit=20&cursor=<opaque>&quizType=VOCABULARY&jlptLevel=N5
```

`quizType`·`jlptLevel` 필터는 선택 사항이다. 기본 20개, 최소 1개·최대 50개로 제한한다. 대표 카드도 같은 필터·정렬 원칙을 사용한다. `userId` 요청 파라미터는 만들지 않으며 인증된 계정으로 모든 쿼리를 제한한다.

```json
{
  "sessions": [
    {
      "id": "00000000-0000-4000-8000-000000000001",
      "quizType": "VOCABULARY",
      "jlptLevel": "N5",
      "mode": "normal",
      "totalQuestions": 20,
      "answeredCount": 7,
      "remainingCount": 13,
      "startedAt": "2026-10-30T09:00:00Z",
      "resumeStatus": "available",
      "resumeReason": null
    }
  ],
  "nextCursor": null
}
```

- 첫 버전은 **최근 시작 순** `started_at DESC, id DESC`의 안정적인 keyset cursor를 사용한다. `startedAt`을 최근 학습 시각으로 표시하지 않는다. 마지막 답안 시각 정렬·새 timestamp 컬럼은 이번 범위에서 제외한다.
- 새 목록의 `startedAt`과 cursor는 UTC offset이 있는 시각으로 표현한다. 과거 naive UTC 값은 읽을 때만 UTC로 해석하며 DB 시각을 고치지 않는다. 클라이언트는 표시할 때 KST로 변환하고 날짜가 지났다는 이유로 종료하지 않는다.
- cursor는 정렬 위치/필터 버전을 나타낼 뿐 인증 수단이 아니다. 조작·다른 계정 cursor를 받아도 다른 계정 행을 반환하면 안 된다. 잘못된 cursor/범위는 기존 API 검증 오류 방식으로 거절한다. 새 비밀키나 환경 변수는 필요 없다.
- 일반 목록은 한 문항 이상 서버 저장된 미완료를 보여준다. 0답안 세션은 지우거나 종료하지 않고 숨긴다. 이미 아는 ID의 직접 재개는 계속 가능하다. 시작 응답 유실 후 ID도 모르는 0답안의 자동 복구/시작 idempotency는 별도 과제이며, 모든 시작 탭이 오프라인 저장된다고 약속하지 않는다.
- `answeredCount`는 중복 원본 행을 수정하지 않고 구한 저장 문항의 고유 개수다. `available`에서는 원래 snapshot과 대조해 `remainingCount = totalQuestions - answeredCount`를 계산한다. 이미 답한 문항을 재전송하지 않는다.
- 구형/무효 snapshot은 기존 `legacy_unavailable`·`invalid_snapshot` 의미를 유지한다. 이 경우 `remainingCount`는 `null`, 진행률은 표시하지 않고 원래 기록이 보존된다는 안내를 한다. 원래 분모를 줄이거나 잘못된 답안을 정리해 복원 가능한 것처럼 보이지 않는다.
- `resumeReason`은 새 목록 응답의 선택적 안전한 사유 코드다. 제안 값은 `UNSUPPORTED_CLIENT`, `UNSUPPORTED_LEGACY`, `SNAPSHOT_INVALID`, `CONTENT_UNAVAILABLE`이며 알 수 없는 값은 안전한 안내로 처리한다. 기존 API의 enum에 새 값을 몰래 끼워 넣지 않는다. 원인을 확정할 수 없으면 다른 클라이언트에서 반드시 된다고 단정하지 않는다.
- 완료/조회 사이 경쟁에서는 선택 후 `/resume`에서 소유권·완료·snapshot을 다시 확인하고 기존 400/404/409 계약으로 거절한다. 사용자는 목록 새로고침이나 명시적 새 시작을 선택하며 자동으로 새 퀴즈를 만들지 않는다.
- 응답에는 문제/정답/답안 원문·SRS·전체 JSON을 담지 않는다. 후보를 페이지 크기+1로 제한하고 한 묶음의 답안 집계로 N+1을 피한다. 내부 snapshot 분류가 필요해도 bounded chunk로 처리한다. `limit`이 작다는 사실만으로 DB scan 비용까지 작다고 주장하지 않는다.
- 기존 user/session 인덱스로 먼저 폐기형 데이터의 실행 계획·쿼리 수를 확인한다. 추가 복합/부분 인덱스가 필요하다고 확인되면 **실행 계획·DDL·lock/복구안을 별도 보고한 뒤** 승인받는다. 현재안에는 인덱스 DDL이 없다.

대표가 복원 불가 상태라도 전체 목록의 다른 세션 선택을 막지 않는다. 대표는 목록의 첫 항목과 같은 최근 시작 순이고, 그 항목이 미지원이면 `저장된 퀴즈 확인하기`로 전체 보기와 이유를 안내한다. 데이터 일부가 미지원이라는 이유로 저장 목록 전체를 빈 상태로 바꾸지 않는다.

## 4. 모바일·웹 UX와 snapshot 경계

- 홈 대표 카드 하나 + `전체 보기`; 목록은 레벨·카테고리·모드·시작일·`7/20문제 저장됨`을 표시한다. 선택하면 기존 resume를 호출해 원래 세션을 연다. 선택 시점까지 목록 요약만으로 문제를 재구성하지 않는다.
- 새 퀴즈 버튼은 `이전 퀴즈는 저장한 채 새로 시작해요`라는 의미가 되며, 과거 세션을 포기해야 오늘 추천에 접근하는 구조를 없앤다. 진행 중 요청에는 반복 시작 버튼을 잠근다.
- 날짜가 지난 스마트 퀴즈는 `10월 30일 시작한 저장 퀴즈`다. 오늘 추천은 현재 목표·복습 상황으로 새로 계산하고, 저장 퀴즈를 오늘 문항으로 재추출하지 않는다.
- 원래 문항/선택지/정답/매칭 pair/배열 token의 데이터와 저장 답안을 유지한다. 매칭 타일의 화면 배치나 아직 제출하지 않은 드래그·선택까지 영구 저장하는 안은 아니며, 현재 미답 문항의 상대 순서/보드 재배치 동작은 구분한다. 콘텐츠 문구가 바뀌어도 원래 snapshot을 사용한다. 필요한 어휘/문법 참조가 삭제돼 새 SRS 저장이 불가능하면 재개와 새 답안 처리에서 기존 409 계열의 보존 안내로 거절하며 원문을 재생성하지 않는다.
- API/mobile의 유효 일반·스마트·오답 복습·매칭·문장 배열을 현재 decoder 범위에서 지원한다. KANA는 별도 세션/receipt 흐름이므로 이번 일반 저장 목록에서 제외하고 가나 이어하기를 새로 약속하지 않는다.
- 웹 native snapshot과 FastAPI snapshot은 현재 서로 다른 채점/복원 형식이다. 각각의 정식 reader/writer에서만 재개하고 미지원 형식은 보존 안내한다. 모든 기기 간 범용 이어하기/변환은 별도 작업이다.
- 특히 과거 웹 매칭은 모드를 저장하지 않은 일반 배열이라 원래 매칭 의도를 안전하게 추정할 수 없다. 기존 일반 문제 호환은 유지하되 모드를 추정 백필하지 않는다. 향후 웹 매칭의 mode 저장·reader 추가도 별도 범위로 분리한다.
- 모바일의 목록·이어하기 요청 결과를 현재 계정/요청 세대와 대조한다. 로그아웃·계정 전환 중 돌아온 이전 응답을 새 계정 화면에 적용하지 않는다. 인증 방식은 바꾸지 않는다.
- 목록 API가 아직 없는 서버의 명확한 404에는 구 단일 카드 조회로 호환한다. 5xx/인증 실패를 빈 목록으로 처리하거나 새 퀴즈를 자동 시작하지 않는다. 실패 시 기존 목록과 재시도 UI를 유지한다.

## 5. 기록·목표·복습 기한·학습 시간

1. 과거에 `completed_at`이 생긴 행은 자동 종료/교체/정상 완료를 안전하게 구별할 수 없다. **이미 종료된 행은 다시 열지 않고** 원문·답안·성적·XP·기한·집계를 그대로 둔다. 아직 미완료인 오래된 행은 시각 변경이나 백필 없이 새 정책의 대상이 된다.
2. 조회·재개·목록·새 시작만으로 기존 답안, XP, SRS, 복습 기한, 과거 출석을 재반영하지 않는다. 새 시작은 자기 새 세션만 만든다. 기존 오답 복습의 원본/복습 연결과 같은 원본에 대한 진행 중 복습 재사용을 유지한다.
3. 실제 새 답안은 실제 저장된 KST 날짜의 기존 고유 단어 목표·학습일 정책에 반영한다. 예전 답안을 오늘 목표에 다시 더하지 않고, 비어 있던 며칠의 출석을 채우지 않는다. 새 답안의 SRS는 과거 snapshot이 아니라 **현재 진행 상태와 현재 처리 시각**에 기존 함수를 적용한다. 이미 저장된 기한은 조회만으로 바뀌지 않는다.
4. 웹은 현재 완료 상태의 새 답안/SRS 쓰기 거절이 충분하지 않으므로, 사용자→세션 잠금 안에서 완료 여부를 확인하는 안전장치를 이번 구현 범위에 포함한다. 이미 끝난 웹 세션의 새 답안은 409와 새로고침 안내로 거절하고 기존 API의 종료 거절 규약은 유지한다. 아직 미완료인 웹 세션의 기존 답안 재시도/채점 방식을 과거 재채점이나 전체 SRS 정책 통합으로 바꾸는 안은 아니다.
5. 실제 완료의 XP/완료일 일별 집계/스테이지 정책은 유지한다. 답안 전부 저장 후 아직 완료 요청이 안 된 세션은 명시적 완료를 한 번 수행할 수 있다. 이미 끝난 결과를 다시 읽거나 완료를 재시도해 보상을 중복 지급하지 않는다. API와 native web의 기존 채점/답안 재시도 차이를 이번 변경에서 과거 재채점·SRS 통합으로 확대하지 않는다.
6. API 완료의 학습 시간은 canonical 첫 저장 답안의 음수가 아닌 `timeSpentSeconds` 합계를 분으로 변환해 기존 단위에 저장한다. 예를 들어 4일 된 퀴즈의 저장 답안 시간이 90초라면 5,760분 대신 1분이다. 웹은 기존 초 단위를 유지하며 중복 답안으로 시간을 부풀리지 않는 읽기 집계를 검토한다. 특수 모드/구형 답안의 시간이 0 또는 없으면 0으로 남기고 시작~완료 간격으로 보충하지 않는다.
7. 웹·모바일 문항 타이머는 앞으로 화면이 활성인 동안만 증가하도록 검증·보완한다. 기존 답안 시간 원문이나 과거 일별 시간은 다시 계산하지 않는다. 임의의 5분/10분 문항 상한이나 SRS 속도별 등급 규칙 변경은 이번 안에 포함하지 않는다. 과거 기록 자체에 유휴 시간이 들어 있다면 이번 안이 그것을 정확히 추정 복구한다고 주장하지 않는다.

현재 DB에는 이미 세션 JSON·답안·시간·완료 필드가 있고 미완료를 닫아도 원래 데이터는 삭제되지 않는다. 이를 열어두는 것 자체가 중복 snapshot을 생성하지 않는다. 늘어나는 것은 미완료 조회 후보이므로 pagination과 측정으로 관리한다. 무제한 전체 조회/무한 스크롤의 전체 선적재는 하지 않는다.

## 6. 변경하지 않는 DB·운영 범위

새 테이블/컬럼/enum/인덱스, migration, Prisma schema 수정, 과거 기록 백필·완료시각 초기화, 기존 XP 회수, 복습 기한 재계산, 음원 재생성·캐시 교체, 환경 변수/비밀키, 역할·권한·RLS·Data API 설정 변경은 제안 범위에 없다.

영구 포기/보관함 정리와 `abandoned_at` 또는 `closure_reason`은 후속 설계다. 기존 `completed_at`을 포기 버튼의 편법으로 사용하지 않는다. 정확한 과거 종료 사유를 복구할 수 있다고 가정하지 않는다.

## 7. 구현 승인 후 검증과 적용 순서

1. 먼저 위 API 추가, start 의미/미래 XP 정산 시점, 시간 계산·클라이언트 표시를 승인받는다. backend가 OpenAPI 계약을 확정하고 web/mobile이 소비한다. shared generated types는 기존 생성 절차로 갱신하며 운영 DDL은 실행하지 않는다.
2. 기존 회귀의 `새 시작이 기존 퀴즈를 완료한다`는 기대를 새 정책으로 명시적으로 바꾼다. 그 외 완료 한 번 반영·SRS·계정·snapshot 보호 테스트는 유지한다.
3. 폐기형 PostgreSQL·웹·시뮬레이터에서 24시간 직전/직후, 3일·7일·30일, KST 자정, 같은 시작시각 cursor, 오래된 다중 세션, 0답안/무효/다른 형식, 전부 답안 저장 상태를 검증한다. 운영 시각이나 기록을 고쳐 테스트하지 않는다.
4. A를 일부 푼 뒤 B 시작→A/B 모두 남음→같은 snapshot을 지원하는 다른 기기/새 프로세스에서 A의 같은 다음 문항→B 상태 유지→각각 정상 완료를 검증한다. GET/list/resume/new-start 전후 기존 답안·SRS·XP·기한 지문을 비교한다.
5. 실제 동시 DB 세션으로 조회/답안/완료/새 시작 경쟁, 동일 답안·완료 재시도, 외부 계정 ID·계정 전환 응답 지연, 목록 404/5xx, 콘텐츠 삭제 사이 race를 검증한다. 모바일은 현재 계정 세대와 요청 세대를 함께 확인한다.
6. backend lint/format/mypy/영향 회귀·필수 PostgreSQL, web lint/typecheck/관련 테스트·build, 모바일 format/analyze/test와 cold restart UI, OpenAPI/TS 생성·모바일 계약 검증을 수행한다. 제안 문서 작성 단계에서는 구현 테스트 성공을 주장하지 않는다.
7. 운영 적용은 별도 결과/적용안 보고 후 진행한다. 알려진 내부 테스터의 짧은 사용 중지와 기존 배포 URL 사용 중단을 확인한 뒤 **보존 정책을 지키는 웹 BFF → API → 새 목록을 쓰는 웹·모바일 클라이언트** 순으로 맞춘다. 구 모바일도 새 API의 start를 쓰면 기존 세션은 보존된다. 구 웹 배포 주소의 Prisma writer는 별도이므로 현재 canonical 전환만으로 차단됐다고 주장하지 않는다.
8. 새 WAF/Preview 인프라를 선행조건으로 강제하지 않는다. 현재 내부 테스트 범위의 알려진 경로를 전환하고, 구 writer 재접속을 통제할 수 없으면 활성화를 미룬다. DB 스키마 변경이 없으므로 이전 p6용 migration/STOP 전환을 다시 실행하는 안이 아니다. 새 설정이 필요하다고 확인되면 먼저 구체안을 추가 보고한다.

## 8. 롤백

목록 UI에 문제가 생기면 단일 대표 카드로 되돌릴 수 있지만, 서버의 **날짜 자동 종료 제거·새 시작의 기존 세션 보존·p6 호환성**은 유지한 호환 빌드를 롤백 기준으로 준비한다. 24시간 자동 완료나 start 자동 정산이 있는 구 버전으로 복귀하면 보존하던 세션을 다시 닫으므로 일반 롤백으로 사용하지 않는다.

DB downgrade·행 삭제·완료 초기화·과거 XP/복습/출석 재계산은 하지 않는다. 새 보존 호환 버전을 유지하며 수정하거나 앞으로 고친다. Data API를 열거나 권한을 완화하는 복구안은 없다.

## 현재 상태

초기 설계 PR #222 이후 사용자가 구현과 로컬 검증을 승인했다. 현재 제품 코드·계약·로컬 마이그레이션은 후속 구현 브랜치에서 검증한다. 운영 데이터·설정·배포와 기존 학습 기록은 변경하지 않았다. 최신 상태는 상단 후속 문서를 따른다.

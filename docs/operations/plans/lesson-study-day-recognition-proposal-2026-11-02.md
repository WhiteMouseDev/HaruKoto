# 레슨 완료의 학습일 인정 제안

## 상태와 승인 경계

**11월 2일 후속:** 사용자가 A안 구현·PR #214 병합·격리 회귀/시뮬레이터 검증을 승인했다. 구현 결과와 호환 OFF → 구 writer 종료 확인 → ON 운영안은 [구현·검증 기록](lesson-study-day-recognition-implementation-2026-11-02.md)에 분리했다. 아래는 승인 전 설계 당시 기록이며, **운영 적용은 여전히 별도 승인 대기**다.

**설계안이며 서버·API·DB에 적용하지 않았다.** 사용자는 레슨 학습일 인정의 설계와 모바일 복습 카드 개선을 요청했고, API·DB 변경은 적용 전에 구체안을 먼저 확인하도록 했다. 현재 구현 기준은 PR #213까지 병합된 main `1986649e`다. 이 문서는 운영 조회 결과가 아닌 현재 코드·기존 테스트·[직전 운영 적용 기록](lesson-submit-idempotency-rollout-2026-11-02.md)에 근거한다.

권장 범위는 **승인 후 신규 멱등 레슨 제출에서 처음 성공 처리한 완료를 KST 학습일로 인정**하는 것이다. 과거 기록·기한의 백필이나 XP 지급·오늘 단어 목표의 정의 변경은 포함하지 않는다.

## 확인된 연결 누락

`apps/api/app/services/lesson_command.py:apply_lesson_attempt`는 레슨 진도·정오·SRS와 복습 이벤트를 갱신하지만 사용자의 연속일과 `DailyProgress` 활동은 기록하지 않는다. 반면 퀴즈 완료는 별도로 XP·KST 연속일·일별 집계를 갱신한다.

대시보드는 `DailyProgress` 또는 `users.last_study_date`로 오늘 학습 여부를 판단하고, 주간·월간 달력은 `DailyProgress`의 활동을 본다. 모바일 레슨 서비스는 이미 성공 후 대시보드·달력을 갱신하므로 단순 화면 새로고침 추가로 해결되지 않는다. 직전 운영 QA에서도 레슨 두 개 완료 후 연속일·일별 집계가 0이었다.

`DailyProgress`의 `quizzes_completed`, `words_studied`, `xp_earned` 등에 임의의 양수를 넣으면 오늘 단어 수·퀴즈 수·XP의 뜻이 바뀐다. 레슨 완료를 표현하는 별도 마커가 필요하다.

## 선택지와 권장안

B의 기존 영수증은 사용자별로 `processed_at AT TIME ZONE 'Asia/Seoul'` 날짜를 추출하고 지원하는 응답 버전의 `response_body.result.status = 'COMPLETED'`만 사용하면 된다. 하지만 현재 인덱스는 `(user_id, lesson_id, processed_at)`이고, 기존 영수증을 모두 포함하면 과거 표시가 바뀐다. 보존할 기존 `users.streak_count`·`longest_streak`와 불완전한 과거 일별 집계의 관계도 정의해야 한다. 따라서 전체 제품의 학습일 인정에 A를 우선 권한다.

## A안의 구체적인 DB 변경

승인 후 작성할 Alembic 마이그레이션의 핵심은 다음 한 컬럼이다. 아래 SQL은 **설명용이며 실행하지 않았다.**

```sql
ALTER TABLE public.daily_progress
  ADD COLUMN lesson_completed BOOLEAN NOT NULL DEFAULT FALSE;
```

- 기존 `(user_id, date)` 고유 제약을 그대로 사용한다. 카운터가 아니라 해당 KST 날짜에 레슨을 하나 이상 완료했는지를 나타낸다.
- 기존 행은 모두 `false`로 시작한다. 과거 레슨 진도·영수증에서 `true`를 채우지 않는다. 기존 컬럼 값·복습 기한·XP를 재계산하지 않는다.
- SQLAlchemy 모델을 추가하고 shared-packages-agent가 Alembic을 기준으로 Prisma를 동기화한다. Prisma가 DDL 권한자가 되지 않는다.
- 마이그레이션 전 owner·head·컬럼 부재·권한/RLS·DDL guard를 검사한다. 기존 테이블의 클라이언트 권한·RLS 정책은 바꾸지 않고 새 컬럼의 유효 권한도 검사한다. Data API는 계속 차단한다.
- 기록 보존은 **기존 컬럼만 투영한 기본 키/행 해시 동일 + 기존 행의 새 컬럼 false**로 증명한다. 컬럼 추가 뒤 전체 `to_jsonb(row)`에는 새 키가 생기므로 전체 행 해시가 이전과 같다고 주장하지 않는다.

## API와 화면에 나타나는 변화

**모바일이 쓰는 FastAPI에는 새 엔드포인트·요청 필드·응답 필드가 필요하지 않은 안**이다. 기존 필드가 레슨 완료도 학습으로 인정하도록 동작 의미가 확장되므로 이 부분도 사전 승인 범위다. 웹 자체 stats BFF에는 해당 bool이 없는 경로도 있어 웹 달력까지 같은 표시를 보장하려면 BFF 응답 필드 추가안을 별도로 확인해야 한다. 아래의 웹 writer 잠금 참여와 웹 조회 계약 확장은 구분한다.

| 경로/자료                                                                          | 승인 후 달라질 동작                                                                                    | 유지할 동작                                   |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| `POST /api/v1/lessons/{lessonId}/submissions`                                      | 새 제출의 정상 완료와 같은 트랜잭션에서 학습일·연속일 기록                                             | 기존 요청/응답·채점·SRS·영수증 형식 유지      |
| `GET /api/v1/lessons/{lessonId}/submissions/{submissionId}` 및 같은 ID POST 재전송 | 없음. 원래 결과 반환만 수행                                                                            | 오늘 출석 추가·연속일 증가·기한 갱신 0        |
| `GET /api/v1/stats/dashboard`                                                      | 기존 `today.hasStudied`, `streak.studiedToday/current/longest`, `weeklyStats[].hasStudied`에 마커 반영 | 단어 수·XP·퀴즈 수·`vocabularyGoal` 계산 유지 |
| `GET /api/v1/stats/history`                                                        | 레슨만 끝낸 날도 기존 `hasStudied: true`로 반환                                                        | 실제 활동 수치가 없는 집계는 0 유지           |
| `GET /api/v1/user/profile` 등 기존 프로필/완료 응답                                | 새 정상 활동으로 갱신한 저장 연속일·최장 연속일을 사용                                                 | 응답 형식·계정/권한·기존 수치 이력 유지       |

현재 프로필의 `totalStudyDays`는 활동 조건 없이 모든 `DailyProgress` 행 수를 센다. 이 안은 그 기존 집계 의미를 바꾸거나 과거 0집계 행을 재분류하지 않는다. 레슨으로 새 일별 행이 생기면 기존 정의대로 수에 포함된다. 과거의 모든 학습일 수·달력·연속일이 이미 완전히 정합하다고 주장하지 않는다.

복습 카드는 이 서버 변경에 의존하지 않는다. 현재 review summary와 퀴즈 시작 계약만으로 먼저 개선할 수 있다.

## 학습일 인정 규칙

1. 승인된 코드가 활성화된 뒤 **새 제출 ID의 첫 정상 `COMPLETED` 처리**만 대상이다. 점수와 무관하게 유효한 답안을 정상 제출해 완료했으면 인정한다. 시작·카드 이동·중단·실패·타인 요청·손상된 제출은 대상이 아니다.
2. 기준은 기기 날짜나 레슨 시작 시각이 아니라 **서버가 완료를 처리한 시각**이다. 사용자/도메인 잠금을 얻은 뒤 완료 처리에서 단일 UTC 시각을 확정하고, 새 영수증 `processedAt`·KST 날짜·`last_study_date`가 같은 시각을 사용하게 한다. 실제 commit 시각과 처리 시각이 완전히 같다는 보장은 하지 않는다.
3. 일별 행은 기존 고유 키로 UPSERT한다. 신규 INSERT에는 기존 필수 카운터의 0/default와 필수 키를 명시하고, 충돌 시에는 `lesson_completed = true`만 UPDATE한다. 다른 활동의 단어·문법·XP·퀴즈 집계를 0으로 덮어쓰지 않는다. 실제 server default·NOT NULL과 ORM 동작도 마이그레이션 회귀에서 확인한다.
4. 같은 날 여러 레슨 또는 퀴즈·가나·회화를 해도 연속일 증가는 한 번이다. 전날에서 이어지면 +1, 학습일이 끊겼으면 1로 시작하고 최장 연속일은 줄이지 않는다. 같은 날 재학습의 별도 새 제출은 정상 진도/SRS 정책을 유지하되 학습일은 추가 증가시키지 않는다.
5. 같은 ID 재전송·GET 결과 복구가 다음 날 일어나도 원래 영수증만 반환한다. 다음 날 학습일로 새로 인정하지 않는다. 다음 날 사용자가 실제 새 학습을 완료하면 새 날짜를 인정한다.
6. 학습 효과·일별 마커·사용자 연속일·새 영수증이 한 트랜잭션에서 성공하거나 전부 rollback해야 한다. 실패한 요청으로 마커만 남기지 않는다.
7. 기존 영수증·과거 레슨·과거 연속일은 백필하지 않는다. 적용 전 처리한 영수증을 적용 후 조회해도 출석을 새로 만들지 않는다.
8. 1차 대상은 신규 멱등 프로토콜이다. ID 없는 구 `/submit`은 자정을 넘긴 재전송을 새 학습과 구별할 수 없으므로 현재 동작을 유지한다. 구 세션에 ID를 붙이거나 구 경로를 차단하지 않는다. 레거시 사용자까지 같은 인정 정책으로 확장하는 것은 별도 이행안이다.

## 동시성: 레슨 경로만 고쳐서는 충분하지 않다

현재 레슨의 `lock_lesson_user`는 사용자 행에 `NO KEY UPDATE` 잠금을 잡지만 ID만 SELECT한다. 인증 시 읽은 User의 연속일 값은 잠금을 얻기 전 값일 수 있다. 잠금 뒤 **연속일 관련 필드만 최신 값으로 재조회**해야 하며 User 전체 refresh로 이미 계산한 XP 등을 잃지 않아야 한다.

다른 경로도 같은 사용자 연속일을 쓴다. API 퀴즈는 세션부터 잠그고, 웹 퀴즈는 일별 행을 갱신한 뒤 사용자를 갱신한다. 레슨에만 사용자 잠금을 추가하면 오래된 값으로 덮어쓰거나 `사용자→일별`/`일별→사용자` 잠금 순서가 역전될 수 있다.

따라서 구현 승인은 다음을 포함해야 한다.

- 퀴즈·가나·회화 등 실제 연속일 writer를 목록화하고 사용자 활동의 공통 직렬화 경계를 사용한다. 백엔드뿐 아니라 같은 테이블을 쓰는 웹 BFF도 검토한다.
- 사용자 행 `NO KEY UPDATE` → 필요한 도메인/세션 잠금 → 일별 UPSERT의 순서를 일관되게 적용하고, 모든 경로에서 잠금 후 최신 연속일을 읽는다. FK의 `KEY SHARE`와 충돌하는 강한 사용자 `FOR UPDATE`로 바꾸지 않는다.
- 현재 각 경로의 XP/SRS/미션/실패 정책은 유지한다. 겉으로 함수만 묶어 동작 변경을 감추지 않는다.
- 여러 도메인의 실제 PostgreSQL 동시 실행 회귀가 통과하기 전에는 운영에 적용하지 않는다. 웹을 제외한 채 전체 제품의 동시성을 해결했다고 표현하지 않는다.

현재 확인한 writer는 API의 `quiz_complete.py`, `kana_stage_complete.py`, `kana_quiz_complete.py`, `conversation_rewards.py`와, 웹 `apps/web/src/app/api/v1/` 아래 `quiz/complete`, `kana/stage-complete`, `kana/quiz/complete`, `chat/end`, `chat/live-feedback`이다. 이들은 새 레슨 기록 writer와 같은 사용자 갱신에 참여한다. 구현 전에는 각 호출자까지 다시 추적하고 테스트 순서·잠금 획득 위치를 확정해야 한다. 단순히 `streakCount`를 반환하는 profile/mission reader를 writer로 오인하지 않는다.

## 구현 승인 후 완료 기준

| 영역           | 필수 회귀                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 최초 정상 완료 | 레슨만 완료해도 당일 마커·홈·달력·연속일·프로필 일치. 정답률 0%의 정상 완료도 인정                                       |

| 기존 기록      | 기존 컬럼 값/행 키·기한·음원 캐시 보존, 기존 행 새 마커 false, 과거 영수증 재해석 없음                                   |

이 회귀는 **앞으로 구현해야 하는 완료 기준**이다. 이번 설계 단계에서 실행했다고 표현하지 않는다.

## 배포와 롤백 경계

승인 후 마이그레이션·기존 컬럼 보존 감사 → 호환 서버/웹 writer·reader 검증과 배포 → 시뮬레이터의 정상 완료/응답 유실/다음 날 복구 검증 순으로 진행한다. 기존 서버는 추가 컬럼을 무시할 수 있지만, 이것만으로 혼합 버전 writer의 동시성 보장을 주장하지 않는다. 전환 중 트래픽/구 revision의 실제 호환 전략을 별도 배포 계획에 확정한다.

승인된 학습일이 생긴 뒤에는 컬럼을 삭제하거나 이미 인정한 연속일을 되감지 않는다. 마커·영수증 reader를 보존한 forward fix를 우선하고 새 인정 기능을 중지하더라도 기존 기록은 남긴다. 구 reader로 돌아가면 레슨만 학습한 날의 표시가 사라질 수 있다는 한계도 함께 알려야 한다. 학습 기록 삭제·DB downgrade·Data API 재개방은 롤백 수단이 아니다.

**요청하는 별도 승인 범위:** A안의 불리언 컬럼 추가와 위 API 동작 의미·공통 동시성 처리 구현/회귀. 실제 운영 마이그레이션·배포는 구현 검증 후 구체적인 변경 대상·보존 감사·롤백안을 제시해 별도 확인한다. 현재는 어떠한 서버·DB 변경도 적용하지 않았다.

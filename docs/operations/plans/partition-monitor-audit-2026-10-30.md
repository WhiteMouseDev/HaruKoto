# 파티션 자동 점검 확인과 2027년 2월 보완 제안

## 범위와 결론

이 문서는 14:34~14:35 KST의 읽기 전용 감사다. 이후 사용자가 보완을 승인해 2월 파티션을 추가했으며, 적용 후 12개 파티션과 exclusive `2027-03-01` 커버리지를 확인했다. 현재 상태는 [별도 실제 적용 기록](review-event-february-partition-rollout-2026-10-30.md)을 따른다. 아래의 “2월 없음/승인 전”은 감사 당시 상태를 보존한 것이다.

2026년 10월 30일 사용자 요청에 따라 PR #203·#205를 병합하고, 운영 파티션 자동 점검과 2027년 2월 커버리지를 **읽기 전용**으로 확인했다. 아래 보완안은 미적용이며 DB 쓰기·DDL·권한·운영 설정 변경은 별도 승인 후 진행한다.

- [PR #203](https://github.com/WhiteMouseDev/HaruKoto/pull/203): `de60b0db`, 14:33:37 KST 병합. [main CI](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/41009107930) 성공.
- [PR #205](https://github.com/WhiteMouseDev/HaruKoto/pull/205): `18ce5df7`, 14:34:03 KST 병합. [main CI](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/41009147274) 성공.

- 자동 점검은 10월 22~30일 **9일 연속 실제 검사 성공과 Sentry 전달 수락**까지 확인했다.

`accepted`는 자연 실행의 wrapper가 체크인 전송 수락을 확인했다는 증거다. **현재 Sentry UI의 상태나 새 경고 이메일 수신을 재검증했다는 뜻은 아니다.** 실패·미실행·복구 이메일의 실제 수신 확인은 [10월 21일 운영 적용 기록](partition-monitor-deployment-2026-10-21.md)의 별도 증거다. 읽기 전용 요청을 지키기 위해 이번에는 장애를 만들거나 알림을 재발송하지 않았다.

## 실제 커버리지와 정책 기한

전용 `partition_monitor_catalog` 계정과 공식 CA/호스트 이름 검증 TLS로 현재 카탈로그를 조회했다. 트랜잭션은 read-only, repeatable read, UTC다. 학습 행·답안·계정 식별자는 조회하지 않았다.

| 평가                                | 현재 실제 카탈로그를 검사한 결과                                            |
| ----------------------------------- | --------------------------------------------------------------------------- |
| 2026-10-30 현재 시각                | `OK`, 누락 없음, 요구 끝 `2027-02-01T00:00:00Z`                             |
| 2026-11-01T00:00:00Z 기준 사전 평가 | `ADVISORY`, `FUTURE_MONTH_MISSING: 2027-02`, 요구 끝 `2027-03-01T00:00:00Z` |
| 실제 연속 커버리지 끝               | **exclusive `2027-02-01T00:00:00Z`** — 2월분을 포함하지 않음                |

사전 평가는 지금의 카탈로그에 미래 기준일을 대입한 결과이며 미래 DB 상태 예측이나 변경이 아니다. 정책은 UTC의 현재 월과 다음 3개월을 요구한다. 따라서 2월분이 정책상 필요한 시점은 **2026년 11월 1일 00:00 UTC = 09:00 KST**다. 그날 첫 일일 점검과 겹치므로 **10월 31일까지 보완하는 편을 권장**한다. 현재 10월 학습 기록을 저장할 수 없는 즉시 장애로 해석해서는 안 된다.

## 보안과 보존 확인

- 전용 역할은 관리자·BYPASSRLS·역할/DB 생성·복제 권한과 역할 멤버십이 없었다. `INHERIT`도 꺼져 있다.
- public 스키마의 애플리케이션 테이블·열·시퀀스·루틴 권한, 소유 객체, public 스키마 CREATE 권한은 0이다. 기본 read-only 설정도 유지한다.
- 파티션 검사에서 구조·인덱스·RLS·클라이언트 권한·DDL guard·빈 PostgREST 스키마 검사를 통과했다. 플랫폼의 Data API 토글 자체는 SQL 검사로 확인할 수 없다는 `not_verified` 경계를 유지한다.
- 별도의 본문 없는 익명 Data API HEAD 요청은 **404**였다. 이번에 열람한 경로가 차단된 실제 HTTP 증거이며 모든 인증 조합을 전수 검사했다고 주장하지 않는다.
- DB 쓰기 0, 학습 행 조회 0, 클라우드 변경 0, 수동 Job 실행 0, 이번 감사가 보낸 Sentry 체크인 0이다. 로그인·학습·음원·이어하기 런타임을 변경하거나 다시 테스트하지 않았다.

## 적용 전 제안: 2월 파티션 하나 추가

**상태: 제안만 준비했으며 적용하지 않았다.** 승인 후 backend-agent가 새 Alembic 마이그레이션과 격리 PostgreSQL 회귀 테스트를 구현한다. 현재 최소 권한 역할로는 Alembic version 테이블을 읽지 않았으므로 실제 운영 head는 별도의 승인된 사전 조회에서 확인해야 한다.

1. 적용된 `m3n4o5p6q7r8` 파일을 수정하지 않고, 확인한 최신 head 뒤에 새 마이그레이션을 추가한다.
2. 대상은 `public.review_events_2027_02` **하나**다. `PARTITION OF public.review_events`로 만들며 경계는 **`[2027-02-01 00:00:00+00, 2027-03-01 00:00:00+00)`**로 고정한다.
3. 부모의 기존 PK와 보조 인덱스 2개의 상속·attachment를 검증한다. 기존 guard를 유지하고 새 자식의 postgres 소유·RLS 활성·예상 밖 정책 없음·PUBLIC/anon/authenticated의 테이블/열 유효 권한 없음을 검증한다. 새 자식에 대한 RLS/권한 정리는 이 승인 대상에 포함하며 기존 부모·11개 자식의 권한은 바꾸지 않는다.
4. 같은 이름의 예상 밖 객체·다른 경계·소유자·보안·인덱스 상태가 있으면 중단한다. 반복 적용에서는 이미 정확히 붙은 파티션만 검증 후 허용한다. 기존처럼 lock timeout 2초·statement timeout 15초를 사용하고, 실패하면 전체 트랜잭션을 롤백한다. 짧은 부모 DDL 잠금이 필요하므로 부하가 낮을 때 수행한다.
5. 기존 학습 행을 옮기거나 수정하지 않는다. 복습 기한·답안·XP·로그인·음원 캐시·Data API 설정·점검 계정 권한·스케줄·클라우드 설정은 변경하지 않는다. 테이블 구조 추가의 Prisma 미러 영향은 shared-packages-agent가 확인하고 기존 모델을 불필요하게 재작성하지 않는다.
6. 격리 PostgreSQL에서 UTC 경계·비 UTC 연결·기존 데이터 보존·보안·동시/반복 적용·실패 원자성을 검증한다. 2월말은 정상 라우팅되며, 3월 시작은 이번 2월 파티션에 포함되지 않는지도 확인한다. `as-of 2026-11-01` 검사는 `OK`여야 한다.
7. 리뷰·승인된 적용 후 최소 권한 검사로 12개 파티션과 exclusive `2027-03-01` 커버리지, 익명 Data API 차단을 재확인한다. 로그인·학습·이어하기 검증은 지정 QA 계정과 시뮬레이터를 사용하고, 신규 학습 시작에 따른 기존 미완료 퀴즈 자동 종료 영향을 미리 분리한다.

### 롤백과 이후 운영

기본 롤백은 **애플리케이션만 이전 버전으로 돌리고 추가 파티션은 유지**하는 것이다. 데이터가 들어갈 수 있으므로 자동 `DROP`, `DETACH`, `CASCADE`나 downgrade 삭제를 제공하지 않는다. 제거가 꼭 필요하면 비어 있음·의존성 없음·실행 중 쓰기 없음이 확인된 별도 보존 절차와 승인을 먼저 제시한다.

이 한 달 추가로 영구 자동 생성이 구현되는 것은 아니다. 기존 점검은 권한이 없는 검사기이며 자동 복구기가 아니다. 매달 다음 정책 월에 필요한 커버리지를 검토해 승인된 마이그레이션으로 준비한다. 이후 월 전환 전 경고 강화가 필요하면 검사 정책·테스트 변경안을 따로 제시하며 이번에 스케줄이나 권한을 바꾸지 않는다.

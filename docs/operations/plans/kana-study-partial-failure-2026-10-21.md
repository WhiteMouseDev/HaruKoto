# 가나 학습 탭의 부분 실패 격리

## 목표와 승인 범위

가나 표시 사용자의 대시보드 조회가 지연되거나 실패해도, 별도로 정상 조회된 레슨·챕터·복습을 사용할 수 있게 한다. 사용자는 이 화면 수정과 회귀 테스트를 승인했으며 API·DB 변경이 필요하면 구체안을 먼저 확인하도록 요청했다. 이번 안은 기존 조회 계약 안에서 모바일 표시·재시도만 바꾸며, 로그인·저장된 학습 기록·Data API 차단을 유지한다.

## 승인 후 출시 상태

사용자가 PR 병합·아이폰 반영과 실제 가나 실패 재시도·다른 레슨 진입 확인을 별도로 승인했다. [PR #190](https://github.com/WhiteMouseDev/HaruKoto/pull/190)은 2026-10-21 **19:01:26 KST**에 `957a092c2313ad061c508e812084eee99dcf8347`로 병합했다. 아래 최초 구현·로컬 검증과 이후 기기·운영 감사를 구분한다.

원본 통합본의 720개 테스트 결과와 모바일 파일 650개의 스냅샷을 기준으로 physical release 빌드·서명·entitlements·프로필 및 소스·환경 해시 보존, AOT 가나 안내 포함을 확인했다. 연결을 기다린 뒤 **19:50–19:51 KST에 같은 앱을 아이폰에 업데이트하고 실제 기존 로그인 홈을 확인했다.** 앱 삭제·초기화는 하지 않았다.

전용 Simulator에서는 대시보드만 실패한 실제 오류 화면, 다른 레슨 진입과 대시보드 한정 재시도·정상 복구를 확인했다. [병합 후 main CI](https://github.com/WhiteMouseDev/HaruKoto/actions/runs/39581479471)도 성공했다. 기기 잠금으로 설치를 기다린 뒤 실제 업데이트·실행을 완료했다. 운영 감사는 15개 범위의 행 수와 다른 14개 해시를 보존했고, daily_missions 차이는 19:36:11 KST 추가 검사에서 일일 미션 한 행의 집계 current_count 한 필드로 설명됨을 확인했다. Simulator의 실제 오류·재시도 검증과 아이폰의 설치·로그인 홈 확인, 감사 기준선을 각각 구분한다.

## 원인과 설계

수정 전 StudyPage는 대시보드가 최초 로딩 중이면 전체 화면을 반환해 독립된 챕터·복습 provider의 구독을 늦춘다. 대시보드 조회 실패로 값이 없을 때에도 가나 미완료처럼 계산한 뒤 dashboard!를 참조해 예외가 날 수 있다.

대시보드에 의존하는 가나 영역만 로딩·실패·정상으로 나눈다. 챕터·추천 레슨·복습 영역은 각자의 조회 상태로 표시하고 이동할 수 있어야 한다. 조회 실패는 미학습 또는 진도 0%를 뜻하지 않는다. 이전 성공 데이터를 남기는 경우에는 마지막 확인 정보임을 분명히 표시하고, 새 조회를 실패한 상태를 숨기지 않는다. 가나 표시 설정이 꺼진 경우와 정상적으로 가나를 완료한 사용자의 기존 표시 규칙은 보존한다.

가나 영역의 명시적 재시도는 대시보드 조회만 갱신한다. 다른 레슨·복습의 재조회나 학습 시작·답안 저장을 유발하지 않는다. 기존 전체 화면 당겨 새로고침의 의미는 유지한다. 재시도 중 중복 입력과 재실패, 캐시가 있는 갱신 실패도 확인한다.

## 검증 계획

1. 기존 코드에서 대시보드 실패·가나 표시 조건의 회귀 테스트가 실제 실패하는지 먼저 확인한다.
2. 대시보드가 대기·실패 중이어도 별도 챕터와 추천 레슨을 표시하고 실제 레슨 경로로 이동하는지 확인한다.
3. 가나 표시 on/off, 정상 미완료/완료, 초기 로딩/실패, 재시도 성공/재실패, 이전 데이터가 있는 갱신 실패를 확인한다.
4. 재시도가 대시보드 GET만 늘리고 다른 조회·저장 동작을 건드리지 않는지 검증한다.
5. 좁은 회귀부터 실행한 뒤 모바일 전체 테스트·정적 분석·포맷과 독립 코드 리뷰를 수행한다. 원래 작업 폴더에는 이전 승인 UI 변경이 있으므로 원본 해시와 3way 차이를 확인하며 이번 범위만 통합한다.

## 운영·데이터 경계

서버·API 모델·인증·DB 스키마·권한·RLS·Data API·환경 계약·의존성·플랫폼 설정은 변경 범위가 아니다. 새 학습 시작·답안 제출·기존 기록 교정·직접 SQL 쓰기는 이 검증 범위가 아니다. 최초 회귀는 합성 provider/저장소로 수행했고 이후 실제 Simulator 조회는 아래에 구분한다. 개인 계정 정보나 토큰을 문서에 기록하지 않는다. 최초 구현에서는 PR 병합·아이폰 반영을 별도 후속 단계로 두었고, 이후 승인을 받은 현재 상태는 위 출시 기록에 구분한다.

## 결과

모바일 표시 계층의 두 파일과 신규 회귀 테스트 한 파일로 구현했다. 전체 대시보드 로딩에서 조기 반환하던 흐름을 제거하고, 가나 영역이 로딩·오류·정보 없음·정상 진도를 소유한다. 갱신 대기·실패에는 과거 진도를 현재 값처럼 표시하지 않고, 정상 응답에서 확인한 0/92와 미확인 상태를 구분한다. 완료 시 숨김과 로컬 가나 표시 설정은 유지한다. 재시도는 대시보드 조회만 갱신하며 대기 중 중복 입력을 막는다.

수정 전 회귀 두 개에서 null 확인 예외와 대시보드 대기 중 챕터 조회 0회를 재현했다. 수정 후 신규 20개는 실제 HomeRepository의 합성 Dio GET과 실제 GoRouter·LessonPage 경로를 사용해 추천 배너 및 챕터 레슨 이동, 가나 열기, 재시도 성공·재실패·중복 입력, 캐시 갱신 상태, 표시 설정, 진도 누락과 총수 0, 320px·200% 글자·두 테마·48px 버튼을 검증한다. 별도 달력 타이머는 이 화면 상태 테스트에서 격리했다. 테스트의 인증 provider는 접근 시 실패하고, GET 외 요청·학습 쓰기·SharedPreferences 변경도 검사해 표시 재시도의 경계를 확인한다.

원본의 기존 모바일 파일 648개 중 이번 대상 study_page.dart 외 647개의 해시를 보존했다. 기존 StudyPage 테스트·환경 파일·이전에 설치한 PR #188 릴리스 번들도 그대로이며, 신규 두 파일은 PR 체크아웃과 일치한다. API·DB 모델·인증·저장 로직·의존성·플랫폼·운영 설정의 코드 변경은 없다. 최초 구현 검증에서는 운영 DB에 접근하거나 새 학습을 실행하지 않았다. 이후 실제 조회 QA와 운영 감사는 별도 기록한다. 2026-10-21 17:54:20 KST의 기존 공개 키를 사용한 Data API HEAD 응답은 404였다. 행 데이터를 요청하거나 설정을 바꾸지 않았다.

위 표는 최초 위젯·저장소·라우터 회귀와 소스 보존 검사 결과다. 이후 PR #190 병합, 실제 Simulator 검증, 아이폰 업데이트와 기존 로그인 홈 확인을 완료했다. 아래에 기기별 검증 결과와 운영 감사 차이의 범위를 기록한다. 서버 변경이 없어 별도 서버 배포도 필요하지 않다. 변경을 되돌릴 때는 모바일 수정 커밋을 revert하고 해당 앱 버전을 다시 빌드하면 되며 데이터 보정·DB 롤백은 필요하지 않다.

## 실제 Simulator 실패·복구 확인

기존 승인된 테스트 계정과 로그인 상태가 유지됨을 확인했다. 가나 표시는 메모리에서만 임시로 켰고 저장 설정은 바꾸지 않았다. GET `/stats/dashboard` 경로만 닫힌 loopback 대상으로 보내 실패시킨 뒤 실제 가나 오류 화면을 확인했다. 다른 레슨 ‘공통점이 반가울 때’는 본문을 열었고 실제 상세 GET도 HTTP 200이었다.

이후 해당 fault만 복구하고 UI의 ‘다시 불러오기’를 눌렀다. 로딩 중 버튼이 비활성화됐고 실제 dashboard HTTP 200 응답의 **0/208**로 복구됐다. 회귀의 합성 정상 진도 0/92·12/92와 이 실제 조회값은 다른 검증 데이터다.

| 관찰 항목      | 재시도 전후 결과                    |
| -------------- | ----------------------------------- |
| 대시보드 요청  | 11 → 12, 명시적 재시도에 한 번 증가 |
| 다른 GET       | 3 → 3, 같은 재시도에서 추가 없음    |
| 실제 레슨 상세 | HTTP 200 한 번과 본문 확인          |
| GET 외 요청    | 0                                   |

앞선 대시보드 실패 11회에는 기본 자동 재시도가 포함된다. 수동으로 열한 번 눌렀다는 뜻이 아니다. 공식 API 주소와 원래 인터셉터 다섯 개의 identity, 메모리 가나 표시와 저장 bool을 원래 상태로 복구했다. 이후 같은 계정과 정상 홈을 다시 확인하고 Flutter 검증 연결을 종료 코드 0으로 해제했다. 모바일 소스 650개와 physical release 산출물 전체 manifest는 검증 전후 동일했다.

## 운영 감사 차이의 최종 범위

최초 SELECT 감사의 15개 범위는 행 수가 모두 같았고 14개 범위는 전체 행 해시도 같았다. daily_missions는 561행으로 수는 같지만 전체 해시가 달랐다. 이 결과만으로 모든 기록이 불변이라고 보고하지 않고 차이를 추가 확인했다.

19:36:11 KST 읽기 전용 검사에서 현재 daily_missions 전체 지문은 Simulator 직후와 같았다. 승인된 테스트 계정의 당일 correct_20 미션 한 행의 current_count 필드만 가상 교체한 20개 후보 중 정확히 하나가 변경 전 전체 561행 SHA와 일치했다. 실제 DB UPDATE·원복은 하지 않았고 이전 값·계정 식별자·개인 행은 출력·저장하지 않았다.

해시 기준으로 차이는 그 한 행의 집계 current_count 한 필드였으며 나머지 미션 행과 다른 필드는 같았다. 다른 14개 범위도 같아 원본 퀴즈·답안·레슨·복습·XP는 보존됐다. 일일 미션 집계 한 필드 갱신은 있었으므로 앱 서버 쓰기 0회나 15개 전체 해시 불변으로 표현하지 않는다.

기존 GET /missions/today의 DailyProgress 집계 동기화와 부합하지만 어떤 HTTP 요청이 변경을 일으켰는지는 특정하지 않았다. Non-GET 요청 0회는 서버 내부 쓰기 부재를 뜻하지 않는다. 감사 도구 쓰기·DB 권한·설정 변경과 기록 보정·롤백은 없었고 Data API HEAD 404·health 200은 유지됐다.

## 아이폰 업데이트와 실제 로그인 홈 확인

기기 잠금 해제를 기다린 뒤 19:50–19:51 KST경 아이폰에 같은 앱을 덮어 설치했다. 설치 도구는 success·installed true를 반환했다. 같은 앱 ID·서명·entitlements·프로필의 검증한 release를 사용했고 앱 삭제·로그아웃·초기화는 하지 않았다.

실행 직후에는 스플래시가 보였고, 로딩 뒤 새로 캡처한 실제 폰 화면에서 기존 계정의 홈 인사·연속 학습 카드·N5 숙련도 2%가 표시됐다. 로그인 요구나 시작 오류 없이 기존 홈이 유지된 것을 확인했다. 빌드나 설치 성공 메시지만으로 실행을 대신 판단하지 않았다.

19:51:02 KST의 기기 반영 후 SELECT 전용 감사는 Simulator 이후 스냅샷과 비교해 15개 범위의 행 수와 전체 행 SHA가 모두 같았다. 기기 반영으로 생긴 새 변경은 없었다. 최초 Simulator 이전 기준선과 비교하면 14개 SHA가 같고, 나머지는 앞서 전체 테이블 해시로 확인한 일일 미션 집계 한 필드 차이만 유지된다. 비교 기준을 섞어 최초 기준선과도 15개가 모두 같다고 쓰지 않는다. 두 비교에서 보안 카탈로그 지문도 같았고 Data API HEAD 404·health 200을 유지했다. 감사는 TLS를 검증한 읽기 전용 연결이었으며 도구의 DB 쓰기는 없었다.

가나 실패 화면·다른 레슨 진입·대시보드 한정 재시도 복구는 실제 Simulator에서 확인했다. 아이폰에서는 이번 앱 설치와 로딩 뒤 기존 로그인 홈을 확인했으며 터치로 오류를 강제 재현하거나 재시도 수용 검사를 반복하지 않았다. 소스·환경·권한·Data API·클라우드 설정과 기존 학습 기록의 직접 교정은 하지 않았다.

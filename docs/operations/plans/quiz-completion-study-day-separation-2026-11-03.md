# 지연된 퀴즈 결과 복구와 학습일 분리 — 승인된 로컬 구현안

2026-11-03 KST. 사용자가 ‘분리안 채택·로컬 구현과 검증’을 승인했다. nullable 컬럼과 API·웹 판정을 로컬에 구현하고 폐기형 DB·회귀·시뮬레이터로 검증한다. 운영 DB·설정·배포 승인은 포함하지 않으며 운영에는 적용하지 않았다. 최종 근거와 적용 순서는 [구현·검증 기록](long-lived-quiz-resume-implementation-2026-11-03.md)에 정리한다.

## 사용자에게 보일 결과

| 상황                                                | 결과·XP·완료 통계                                    | 오늘 학습일·연속일                                  |
| --------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------- |
| 오늘 새 퀴즈 답안 한 문항 저장, 정오 무관           | 기존 답안 정책, 완료 전 XP 지급 안 함                | 인정                                                |
| 월요일에 전 문항 저장, 목요일에 최초 완료 요청 복구 | 목요일에 기존 완료 보상 한 번, 기존 완료일 통계 유지 | 목요일에 다른 실제 학습이 없으면 새로 인정하지 않음 |
| 같은 완료 요청 다시 전송·앱 재실행 후 결과 조회     | 이미 처리된 결과 복구, 추가 보상 없음                | 추가 인정 없음                                      |
| 목요일에 다른 문제/가나/레슨/회화로 이미 학습 인정  | 기존 정책 유지                                       | 이미 인정된 목요일 유지                             |
| 완료 복구만 한 뒤 같은 날 실제 새 답안 저장         | 기존 보상 유지                                       | 미인정에서 인정으로 전환                            |

이번 분리는 퀴즈의 ‘서버에 저장된 과거 답안에 대한 지연 완료 복구’에 적용한다. 레슨·가나·회화의 별도 완료/학습일 정책을 일괄적으로 새로 정의하지 않는다. 기존 과거 출석을 취소하거나 과거 정답·XP·복습 기한·단어 목표를 다시 계산하지 않는다.

## 기존 Boolean 하나로 해결하기 어려운 이유

현재 `daily_progress.activity_recorded`는 새 답안의 증거다. 그러나 기존 학습일 조회는 이 값이 false여도 완료 횟수·XP·분량 등의 양수 집계로 학습일을 인정한다. 완료 시 연속일 갱신만 생략하면 달력은 다시 출석으로 표시할 수 있다. 반대로 이 집계 보완을 없애고 기존 마커만 믿으면 과거 정상 출석을 잃을 수 있다.

## 제안하는 DB 변경 한 가지

`daily_progress.study_day_credited BOOLEAN NULL` (명시적 default 없음) 컬럼 하나를 추가한다. 새 테이블·인덱스·enum은 없다. 기존 행을 UPDATE하거나 백필하지 않는다.

- `NULL`: 기존 기록 해석을 유지한다. 현재 마커/집계 fallback을 그대로 사용한다.
- `TRUE`: 실제 활동으로 인정된 날이다.
- `FALSE`: 새 정책에서 완료 복구만 발생했고 실제 학습 인정은 없는 날이다. 양수 XP/완료 통계만으로 다시 출석을 만들지 않는다.

기존 `activity_recorded`는 유지한다. 새 컬럼은 서버 내부 판정용이며 클라이언트에 그대로 노출할 필요가 없다. `hasStudied` 등 기존 응답 필드의 타입은 유지한다.

## 트랜잭션과 동시성

1. 기존 사용자→세션→일별 기록 잠금 순서를 유지한다.
2. 완료 집계를 쓰기 전에 오늘 행의 기존 인정 여부를 읽는다. 이미 인정된 TRUE 또는 legacy 인정 상태는 반드시 보존한다.
3. 오늘 실제 저장된 canonical 새 답안/활동 증거가 없고 기존 인정도 없으면 FALSE를 쓴다. 완료 XP·건수·학습 시간은 기존 완료일 기준으로 한 번만 정산하되, 이 복구만으로 `lastStudyDate`·연속일을 갱신하지 않는다.
4. 실제 활동 writer는 TRUE를 쓴다. 같은 날의 완료 복구가 TRUE를 FALSE로 되돌릴 수 없다.
5. 응답 유실 후 동일 완료 재시도는 기존 완료 결과만 반환한다. 최초 완료 이후 기존 일별 집계·학습일 값을 다시 변경하지 않는다.
6. 단어 목표는 기존 KST 답안 고유 단어 집계를 그대로 사용하며 완료 시 재집계하지 않는다. SRS·복습 기한은 새 답안 경로의 기존 정책을 유지한다.

기존 일별 기록이 legacy NULL인 경우에는 **새 완료 집계를 더하기 전**의 인정 여부를 보존해야 한다. 완료 후 XP를 보고 TRUE로 결정하면 분리 목적을 달성하지 못한다.

## 함께 정렬해야 할 코드 경로

- API: `study_day_recording`, `quiz_complete`, 가나 답안·완료·진도 일별 writer, `conversation_rewards`.
- 웹: `answered-study-day`, 퀴즈/가나 완료·진도, `chat/end`, `chat/live-feedback`의 일별 집계와 연속일 writer.
- 조회: API `study_activity`·dashboard·history·user 누적 학습일, 웹 dashboard/history/profile 판정. 누적 학습일의 기존 legacy 행 처리까지 불필요하게 재해석하지 않고 명시적 FALSE 행을 제외하는 경계를 테스트한다.
- 모바일: 서버의 `hasStudied: false`를 XP 양수 등의 클라이언트 추정으로 덮어쓰지 않는지 확인한다. 분량/XP 차트와 출석 표시를 구분한다.
- 공유: Alembic은 backend 소유, Prisma/공유 타입은 정해진 동기화 절차로 맞춘다. 새 응답 필드가 필요하다고 확인되면 따로 계약을 제시한다.

## 로컬 검증과 운영 적용 분리

구현 승인 후에는 폐기형 PostgreSQL에서만 마이그레이션 upgrade/downgrade/upgrade, legacy NULL 해석, 완료 복구 FALSE, 이후 실제 답안 TRUE, 동시 완료/답안, KST 자정, 응답 유실·재시작을 검증한다. 운영 마이그레이션·서버 배포는 별도 승인 전 수행하지 않는다.

운영안은 검증 결과와 함께 다시 보고한다. 기본 순서는 다음과 같다.

1. 기존 코드가 무시할 수 있는 nullable 컬럼을 먼저 추가한다. 기존 행 UPDATE 없음, 짧은 메타데이터 DDL 잠금 영향과 timeout/재시도는 적용 전에 확인한다.
2. 모든 읽기/쓰기 경로에 새 판정과 호환되는 OFF 빌드를 배포한다. 컬럼을 모르는 시점에 새 ORM이 이를 SELECT하지 않도록 한다.
3. 알려진 구 웹 writer와 내부 테스트 경로의 전환을 확인한 뒤 활성화한다. old writer가 FALSE를 TRUE로 올리지 못하거나 old reader가 FALSE를 집계로 다시 인정할 수 있으므로 자동 배포/구 배포 주소도 적용안에 포함한다. 새 WAF·Preview 인프라를 임의로 만들지 않는다.
4. 실제 로그인·학습·지연 완료·달력·목표·이어하기를 시뮬레이터로 확인한다. Data API 차단·RLS·역할 권한은 유지한다.

## 롤백

FALSE 값이 생긴 뒤에는 이를 존중하지 않는 옛 reader/writer로 롤백하지 않는다. 새 컬럼과 판정을 이해하는 호환 빌드에서 신규 분리 동작만 끄거나 앞으로 수정한다. 컬럼 삭제·FALSE→NULL 일괄 변경·과거 출석 취소·XP 재계산은 운영 롤백안에 포함하지 않는다. 로컬 migration downgrade 검증이 운영에서 컬럼을 삭제해도 된다는 뜻은 아니다.

## 승인 경계

사용자는 위 컬럼 한 개와 관련 reader/writer 정렬의 **로컬 구현·마이그레이션·검증**을 명시적으로 승인했다. 앞서 웹 답안 재시도 계약도 별도로 승인했다. 이 승인은 운영 DB·설정 변경이나 병합·배포 승인이 아니다. 운영 활성화 전 검증 결과와 DDL→호환 OFF→ON, 구 writer 통제 및 롤백 빌드를 다시 제시한다.

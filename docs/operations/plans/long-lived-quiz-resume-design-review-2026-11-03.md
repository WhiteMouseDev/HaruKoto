# 장기 퀴즈 이어하기 설계 재검토

2026-11-03 KST. 대상은 PR #222의 `c1db8663eb182e10605554e891576ee0c1f5f0a8`와 같은 체크아웃의 실제 API·웹·모바일 코드다. GitHub에서 PR이 open/unmerged이고 변경 파일 세 개가 모두 문서임을 확인했다. 구현·배포 완료 검증이 아니라 **구현 전 설계 검토**다.

## 판정

핵심 방향은 채택할 만하다. 다만 현재 문서 그대로 구현 완료·배포 가능으로 판정하지 않는다. 웹 답안 저장/완료 경쟁과 재전송 중복 반영을 먼저 해결하고, 페이지 탐색 조건 및 늦은 결과 복구의 학습일 의미를 확정해야 한다.

유지할 원칙은 기간에 따른 자동 종료 제거, 새 시작 시 기존 미완료 보존, 조회의 쓰기 제거, 원래 세션·문항·저장 답안 유지, 실제 새 답안만 현재 SRS에 반영, 답안 시간으로 학습 시간 계산, 기존 종료 기록 비복원·비백필이다. 첫 단계에 보존용 테이블이나 종료 사유 컬럼을 신설할 필요는 없다. 운영 권한·Data API 설정을 바꿀 이유도 없다.

## P1 — 웹 답안 저장 확인과 완료 조건을 함께 고쳐야 한다

제안서는 완료된 웹 세션의 새 답안을 409로 거절하는 방어를 추가한다. 그러나 웹 특수 퀴즈는 답안 요청의 성공을 기다리지 않고 완료 요청을 보낼 수 있고, 웹 완료 경로는 원래 모든 문항의 저장 여부를 확인하지 않는다.

- 근거: `apps/web/src/app/(app)/study/quiz/page.tsx:378–409,552–575,601–620`의 답안 `mutate`와 별도 완료 호출.
- 근거: `apps/web/src/app/api/v1/quiz/complete/route.ts:95–107`의 즉시 완료 시각 저장.
- 비교: API는 `apps/api/app/services/quiz_complete.py:220–230`에서 원래 문항 ID의 저장 여부를 확인한다.

마지막 답안보다 완료 요청이 먼저 잠금을 얻으면 세션이 먼저 닫힐 수 있다. 여기에 새 409 방어만 추가하면 늦게 온 마지막 답안이 영구 거절되어 이어하기로 복구할 수 없다. 이는 **제안한 방어를 단독 적용할 때 생기는 위험**이다.

필수 보완:

1. 웹 완료는 원래 snapshot의 모든 문항에 필요한 답안이 실제 저장됐는지 잠금 안에서 확인한다. 부족하면 완료·XP·학습일 쓰기 없이 재시도 가능한 오류를 반환한다.
2. 클라이언트는 완료 전에 필요한 답안 저장 성공을 기다린다. 실패 답안이 있으면 현재 세션을 보존하고 재시도 UI를 표시한다.
3. 저장 확인 뒤 완료 요청, 늦은 답안, 동일 완료 재시도의 순서를 바꿔도 답안 유실·중복 보상이 없는지 실제 동시 요청으로 검증한다.

## P1 — 웹 전송 재시도와 의도적인 재도전을 구별해야 한다

현재 웹 답안 경로는 이전 답안을 조회하지만 같은 요청에도 새 행을 추가하고 정답 수·SRS를 다시 갱신한다. 완료는 누적 정답 수로 XP를 계산한다. 반면 재개 응답은 문항별 첫 답안을 읽는다.

- 근거: `apps/web/src/app/api/v1/quiz/answer/route.ts:100–124,127–228`.
- 근거: `apps/web/src/app/api/v1/quiz/complete/route.ts:107`, `apps/web/src/app/api/v1/quiz/resume/route.ts:49–61`.

서버 저장은 성공했지만 응답을 못 받은 요청을 재전송하거나, 오래된 두 탭이 같은 문항을 제출하면 정답 수·복습 기한이 반복 반영될 수 있다. 기존 문제지만 장기 세션과 여러 기기의 재개에서 무시할 수 없다. 완료 요청의 중복 방지만으로 해결되지 않는다.

제안서 5절의 기존 웹 정책 보존은 학습 정책과 전송 안전성을 구분하도록 보완해야 한다. **동일 논리 제출의 재전송은 한 번만 반영**하고, 매칭의 오답 후 의도적 재도전은 별도 시도로 구별할 구체 계약이 필요하다. 이를 무조건 문항당 첫 답안만 받는 방식으로 바꾸면 기존 매칭 정책을 바꿀 수 있다. 시도 식별 필드 등이 필요하면 API 구체안을 별도로 보고한다. 이 검토에서는 계약·DDL을 추가하거나 과거 성적을 재채점하지 않는다.

## P2 — 목록에서 숨긴 행 뒤의 기록도 반드시 접근 가능해야 한다

제안서의 `limit+1` 후보 조회 후 0답안·KANA를 숨기는 순서는 아직 구체화되지 않았다. 최근 21개가 제외 대상이고 그 뒤에 이어 풀 세션이 있을 때, 빈 목록과 마지막 페이지로 잘못 판정하면 보존만 되고 찾을 수 없게 된다.

자격 조건은 가능한 한 `LIMIT` 전에 적용한다. 내부 후처리가 필요하면 마지막으로 스캔한 행 기준 cursor와 빈 페이지 이후 탐색 규칙을 함께 정의한다. `sessions`가 비었다는 이유만으로 목록 끝이라고 판단하지 않는다. 이것은 구현된 버그가 아니라 구현 전에 닫아야 할 계약 공백이다.

또한 현재 선택한 N4·문법에 미완료가 없어도 `전체 보기`에서 기존 N5·단어 세션에 접근할 수 있어야 한다. 홈 카드의 필터 결과가 비었다고 저장 목록 진입까지 숨기지 않는다. 첫 버전의 최근 시작 순은 허용 가능한 절충이지만 ‘최근 학습순’으로 표시하지 않는다.

## 정책 확인 — 며칠 뒤 결과 복구만 한 날의 학습일

월요일에 모든 답안이 저장됐고 완료 요청만 누락된 뒤 목요일에 `결과 확인하기`로 최초 완료를 처리하면, 현재 API와 웹은 목요일에 완료 통계·XP뿐 아니라 학습일도 반영한다. API의 `quiz_complete.py:244–252`, 웹의 `complete/route.ts:112–151`이 근거다. 제안서 5절은 이를 유지한다고 명시하므로 새 회귀로 분류하지 않는다.

다만 ‘새 답안을 저장한 날이 학습일’이라는 설명과 다를 수 있다. 기존 완료일 인정까지 유지할지, 앞으로의 지연 완료는 결과·보상만 복구하고 학습일과 분리할지 구체적으로 결정해야 한다. 엄격하게 실제 답안 활동일을 보여주려면 후자가 일관적이나, 현재 계약 변경이므로 승인 없이 적용하지 않는다. 변경을 선택하더라도 기존 출석·XP·일별 기록을 취소하거나 백필하지 않는다.

## 검증 기준과 범위

- 3일·7일·30일 뒤 원래 ID/미답 문항으로 재개, A 중단 후 B 시작해도 둘 다 보존.
- 마지막 답안 지연·실패·응답 유실, 완료 먼저 도착, 동일 요청 재전송, 두 탭 경쟁에서 저장 답안·SRS·XP 일관성.
- 제외 대상만 있는 첫 페이지 뒤의 유효 세션, 필터 전환, 계정 전환 중 늦은 응답, 목록 조회 실패.
- 모든 답안이 저장된 오래된 세션의 결과 복구에 대해 합의한 학습일 기준.
- 카탈로그 삭제는 남은 새 답안에 필요한 참조만 확인한다. 모든 답안이 저장된 결과 복구를 불필요한 카탈로그 검사로 막지 않는다.
- 롤백은 자동 종료를 다시 도입하지 않는 보존 호환 빌드로만 수행한다.

이번 검토는 소스·문서·GitHub PR 메타데이터 읽기와 검토 문서 작성으로 한정했다. 제품 코드·API·DB·클라우드·기존 기록·복습 기한·Data API 설정을 변경하지 않았고, 새 회귀 테스트나 시뮬레이터 실행 결과를 주장하지 않는다. 검토 기록은 로컬 문서로 남기며 PR 병합·배포·구현 승인을 대신하지 않는다.

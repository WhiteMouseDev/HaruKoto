# 로컬 학습 UI 누락 점검과 노선도 복구 계획

작성일: 2026-10-28 KST. 최종 정리: 2026-10-30 KST. 사용자는 지하철 UI가 일반 목록으로 돌아온 원인의 블로그용 Markdown 기록, 다른 누락 점검, 복구 작업을 승인했다. 조사 당시 main `fa82a4b855aac6b677529dd0dcf8e82ce7fe2d55` 위에서 원본 미커밋 변경을 보존하며 진행했다. 아래는 조사와 소스 복구 기록이며, 이후 병합·배포·아이폰 확인은 [운영 반영 기록](learning-ui-production-rollout-2026-10-30.md)을 따른다.

## 확인된 원인과 실행 경계

조사 당시 원본 작업 폴더의 노선도는 미커밋 selector 변경과 미추적 station/color/config/test 파일로 남아 있었다. 기본 source flag는 true였지만 당시 main에는 이 파일들이 없어 기존 ChapterCard 목록을 사용했다. PR #199는 이어하기 구역을 변경했으며 챕터 렌더러 세 파일을 바꾸지 않았다. PR #197의 main 기준 모바일 652파일 일치 기록과 2026-10-28 09:46경 아이폰 설치 receipt는 노선도 없는 빌드의 실제 설치를 확인하는 근거다. 최초 회귀 순간을 화면으로 기록했다고 확대하지 않는다.

조사 중 준비한 기존 일반 목록 빌드는 설치하지 않았다. 업데이트 전 실제 아이폰 기준 위치는 ‘물건을 가리킬 때’ 단어 4/6 傘（かさ）·우산이었으며, 답안·완료 제출이나 초기화 없이 화면 증거를 먼저 보존했다.

## 진행 순서

1. 원본 checkout의 추적 변경과 미추적 파일을 모두 목록화한다. 원본 HEAD·실제 디스크·최신 main의 Git blob을 비교해 이미 통합된 변경, 로컬 전용 후보, 최신 main과 의미 비교가 필요한 변경을 구분한다. 오래된 index 때문에 생기는 가짜 삭제 표시나 최신 main의 새 기능을 누락으로 해석하지 않는다. 비밀·환경·생성 산출물은 제외한다.
2. 모바일, API/DB/CI, 웹/공유 패키지·문서를 나눠 후보를 읽기 전용 검토한다. 원본을 통째로 복사하거나 옛 파일로 최신 기능을 덮지 않는다. 확실한 누락과 의미가 같은 구현, 새 main 개선 때문에 다른 부분을 각각 보고한다.
3. 노선도와 주변 학습 화면의 승인된 표시를 최신 이어하기 카드 1개·모두 보기·최근 학습순과 함께 복구한다. 학습 탭과 전체 레슨 목록 모두 동일한 노선도 selector를 사용한다. 열차·정사각형 역·독립 완료 상태·자유 순서 진입과 대체 목록의 복귀 가능성을 검증한다.
4. 최근 전체 듣기·화면 이탈 취소, 저장 위치·답안·계정/레벨 경계·가나 부분 실패 처리를 유지하는 회귀를 수행한다. 관련 테스트부터 시작해 모바일 포맷·분석·전체 테스트를 실행하고 실제 Flutter 화면을 확인한다.
5. 블로그 문서에는 관찰·원인·검증의 빈틈·복구·재발 방지와 아직 불확실한 항목을 구분한다. 실제 원본/최신 빌드의 기능 차이를 확인하는 검증을 남기고 단순 ‘main과 파일 일치’만으로 기존 사용자 경험 보존을 주장하지 않는다.

## 보존과 승인 경계

- 원본 checkout과 별도 음성 작업 트리의 기존 미커밋 파일을 수정·reset·stash·clean하지 않는다.
- API는 구체안에 사용자 승인을 받은 `records[].hasStudied` 한 필드만 추가한다. DB·권한/RLS·Data API·환경 계약·생산 의존성·기존 학습 기록·복습 기한은 변경하지 않는다. 영속 출석 마커·특수 모드 재개 계약은 별도 승인 전 적용하지 않는다.
- 현재 음원 캐시·Kenzo/Shizuka v4 정책·전체 448개 음원 청취 검수의 별도 PENDING 상태를 유지한다.
- 아이폰은 복구된 통합본을 검토·검증하기 전 일반 목록 빌드를 설치하지 않는다. 앱 삭제·로그아웃·키체인/기록 초기화는 하지 않는다.

## 완료 기준

최신 기능과 노선도가 함께 있는 통합 소스, 다른 로컬 변경의 누락 여부·잔여 결정 목록, 새 회귀 및 최종 실행 결과, 블로그용 Markdown과 검토 가능한 PR을 준비한다. 운영 설정·기기 설치를 소스 검증 완료로 대신하지 않고 실제 수행한 단계만 보고한다.

### 1차 모바일 소스와 검증 — 노선·결과·퀴즈 저장

모바일 변경은 **34개 파일**이다. 노선도 selector의 `studyMapEnabledProvider` 기본값은 true이며, false로 바꾸면 최신 main에서 가져온 `LegacyLessonChapterList`로 돌아갈 수 있다. remote config나 환경변수를 신설하지 않았다.

- 학습 탭·전체 레슨에서 열차, 최소 56dp 정사각형 역, 큰 글자와 밝은/어두운 모드를 검사했다. 처음 추천하는 역에도 열차를 표시하고 전부 완료됐을 때는 추천 열차를 표시하지 않는다.

- #199의 대표 이어하기 카드 한 개·전체 보기·최근 학습순, 계정/레벨 경계와 보호된 navigation을 유지했다.
- #197의 순차 대화 재생·정지·화면/앱 상태 변화 취소, 기존 checkpoint·선택·답안 구현을 유지했다.
- 결과의 정답·획득 XP·오답 타일 높이를 맞추고 레벨 진행은 아래 별도 영역에 둔다. 색종이·콤보음·완료음 호출을 제거하고 정답/오답만 사용한다.

### 별도 KST 수정 경계

API는 `date`를 유지하고 aware 시각과 과거 naive UTC 시각을 KST 날짜로 정규화한다. 같은 날·이전 날 요청에서 기존 current/longest 카운터를 보존한다. 새 완료 요청의 날짜 계산만 고치며, 과거 기록이나 카운터의 일괄 재계산은 하지 않는다.

API의 수정 전 경계 사례 4개 실패를 확인한 뒤 관련 98개가 통과했다. 순수 날짜 수정 단계의 전체 API는 **1039 passed / 기존 admin fixture 13 skipped**, 필수 실제 PostgreSQL 검사는 **85/85 skipped 없이 통과**했다. Ruff lint/format, mypy 173개 소스, PostgreSQL guard 자체 테스트 10개도 통과했다. 이 단계의 OpenAPI 103개 경로는 동일하고 최신 wrong-review 계약을 보존했다. 이후 사용자 승인된 additive 필드와 최종 서버 결과는 다음 절에 구분한다.

웹은 새 날짜 회귀 23개가 UTC·서울·LA·뉴욕에서 각각 통과했고 lint/typecheck가 통과했다. 전체 웹 테스트는 **134 passed / 7 failed**다. 같은 7개 실패를 변경 전 main의 `git archive`에서도 재현했으므로 새 수정의 실패와 구분한다. 기존 achievement 두 개와 stats-component 다섯 개 assertion을 후속으로 정비해야 한다. CI frontend 작업은 install/lint/typecheck/build만 실행하고 웹 `pnpm test`를 실행하지 않는다. 단위 테스트를 CI에 편입하는 작업도 필요하다.

독립 코드 검토에서 이번 복원 diff의 신규 결함은 발견하지 못했다. 단, 실제 부분 진행 매칭 resume는 기존 서버가 mode를 저장하지 않고 재개 응답에 표시용 `word`/`meaning`을 보존하지 않는 제한이 있다. 이번 matching 검사는 start→answer→result와 전부 저장된 합성 resume를 검사했으며 실제 부분 매칭 resume 검증으로 확대하지 않는다. API/DB 계약을 먼저 제시할 별도 후속이다.

### 2차 승인 범위 — 연속일·집계 기반 달력·새로고침

사용자가 `hasStudied` API 추가까지 승인한 뒤 모바일의 원본 후보 25개 모두를 최신 소스에 선택 반영했다. 통계의 기간 탭·heatmap·시간 차트에서 남아 있던 휴대폰 현지 날짜 사용도 KST 날짜 key에 맞췄다. 원본의 직렬 답안 큐나 미승인 출석 마커를 옮기지 않았다.

- 모바일은 명시적 bool을 우선한다. `false`를 true로 추정하지 않으며 absent/null 구 서버 응답만 기존 숫자 집계로 fallback한다. 시작만 한 행이나 answer totals만 있는 응답은 출석으로 만들지 않는다.
- KST 자정·월요일·연도 경계에서 홈·달력 조회·통계의 오늘·차트가 같은 날짜를 쓴다. 앱 복귀 후 날짜 갱신과 미래 날짜의 완료 표시 억제를 검사한다.
- 학습일 카드는 브랜드 핑크와 읽기 쉬운 글자색으로 표시한다. 조회·재조회·실패 상태에서는 예전 완료 상태를 재사용하지 않는다.
- quiz·lesson·kana stage·kana quiz·conversation·call 완료가 성공한 뒤에만 dashboard/history 캐시를 갱신한다. 실패→재시도와 provider dispose 이후 응답도 검사한다. 서버 요청의 내용·XP·복습 기한은 바꾸지 않는다.
- 기존 계정 reader를 사용해 계정이 바뀐 뒤 늦게 도착한 응답, 열린 달력과 보관된 retry callback을 보호한다. 로그인/인증 로직이나 저장 위치의 소유권 형식은 바꾸지 않는다.
- 최신 OpenAPI와 직접 비교해 Dio 61개 경로, annotated model 1개, DailyProgressItem 9개 JSON key의 drift 0을 확인했다. `hasStudied`가 required non-null bool인 새 계약과 구 응답 모두를 테스트한다.

승인 필드 포함 서버는 **1056 passed / 기존 admin fixture 13 skipped**, 필수 PG 85개는 skip 없이 통과했다. Ruff 302개 파일·mypy 174개 source가 통과했다. ## 롤백과 적용 전 확인

1. 노선 표시만 철회하려면 소스 기본값을 false로 바꾸어 fallback 회귀 테스트 후 다시 빌드한다. 저장 키·v1 체크포인트·답안·로그인·DB는 그대로다.
2. 이번 모바일 변경 전체를 철회하려면 복구 PR을 revert한다. 데이터 마이그레이션이나 운영 음원 삭제는 필요 없다. KST 수정은 별도 PR이므로 영향을 분리할 수 있다.
3. 기존 main 기준 일반 목록 빌드는 폐기 대상이며 복구본 설치에 재사용하지 않는다. 병합 후 정확한 커밋에서 새로 빌드·서명 검증하고, 앱 삭제 없이 같은 앱 위에 업데이트한다.
4. 아이폰에서 기존 저장 레슨의 이름·위치, 로그인, 전체 듣기/정지/이탈 취소와 재실행 후 이어하기를 실제 확인한다. 소스 검증과 기기 설치·청취·재실행 확인을 같은 단계로 취급하지 않으며, 10월 30일 적용 후 실제 완료한 항목은 [운영 반영 기록](learning-ui-production-rollout-2026-10-30.md)의 체크리스트를 따른다.

## 재발 방지

- 승인 기능의 구현·테스트·자료가 추적 상태인지 확인하고 PR diff에 포함한다. 미추적 파일이 있는 원본의 디스크 상태를 최신 커밋으로 간주하지 않는다.
- 빌드 소스 일치 검사와 승인 기능 보존 검사를 분리한다. 노선도 기본 표시, 첫 열차, 독립 완료, 최신 저장 카드와 음성 취소를 함께 회귀에 둔다.
- 장기 원본 checkout을 새 main 위에 통째로 덮지 않는다. 실제 파일 기준 세 방향 비교 후 이미 반영된 수정과 최신 main의 계약을 보존한다.
- 적용/검수 단계는 PR·CI, 서버 배포, iPhone 설치, 실제 청취처럼 나눠 기록한다. 한 단계 성공을 다른 단계의 성공으로 표현하지 않는다.

# 문자카드 진도의 안전한 재시도: API·영수증 제약 확장 제안

2026-11-04 KST. **미승인·미구현·미적용 제안**이다. 가나 퀴즈 답안·완료의 모바일 재시도 개선과 구분한다. 사용자의 API·DB 변경 전 구체안 확인 조건에 따라 현행 효과·필요한 변경·적용/원복 경계를 먼저 기록한다.

## 기존 경로에 재시도를 추가하지 않은 이유

`POST /api/v1/kana/progress`는 문자 진도를 매번 누적한다. 같은 `kanaId`를 재전송하면 `user_kana_progress.correct_count`·`streak`와 일별 `kana_learned`가 다시 늘며 기존 일별 학습 인정도 처리된다. 요청 본문 계약은 `kanaId`이고, 현재 모바일이 보내는 `learned`는 서버의 의미 있는 식별 키가 아니다.

따라서 timeout 뒤 같은 body를 다시 보낸다고 같은 행동이 한 번만 반영되지 않는다. 집계 GET은 과거·다른 탭·퀴즈 등의 변화가 합산돼 특정 요청의 commit 증거가 될 수 없다. 새 start도 요청마다 세션을 만들므로, 이번 전송 테스트의 재호출을 카드/start 멱등성의 증거로 해석하지 않는다.

현재 모바일 수정은 카드 저장 오류를 알리고 계정 전환·자동 인증 재전송을 방어하되, 기존 문자카드의 이동 정책을 새로 바꾸거나 카드 저장을 수동/자동 재전송하지 않는다. 퀴즈 답안·퀴즈 완료·단계 완료는 기존 재전송 계약으로 별도 안전하게 다룬다.

## 최소 변경안

새 `POST /api/v1/kana/progress/activities` 요청:

```json
{
  "activityId": "<의도적인 한 카드 학습 행동의 UUID>",
  "expectedUserId": "<이 행동을 시작한 로그인 계정 UUID>",
  "kanaId": "<문자 UUID>"
}
```

성공200은 `{ "ok": true, "activityId": "...", "processedAt": "<최초 접수 UTC 시각>" }`로 제안한다. 동일 사용자·ID·내용은 원래 성공 응답을 반환한다. `expectedUserId`와 인증 계정이 다르면403, 같은 ID의 source kind/내용이 다르면409, 문자가 없으면404, 저장된 영수증이 손상됐으면503으로 안전하게 중단한다. 확인할 수 없는 응답을 성공으로 대체하지 않는다.

기존 경로의 선택 필드로만 ID를 추가하면 구 서버가 이를 무시하고 다시 집계할 수 있으므로 새 경로를 사용한다. 새 경로가 없는 서버의404에서 구 경로로 fallback하지 않는다.

## DB와 최초 처리

기존 비공개 `study_activity_receipts`를 재사용한다. **새 테이블·컬럼·인덱스는 추가하지 않고**, 새 Alembic revision 하나에서 `source_kind` CHECK에 `KANA_CARD_PROGRESS`를 추가하는 안이다. 기존 두 종류의 영수증과 PK `(user_id, activity_id)`·scope index는 유지한다. 같은 사용자의 잠금 안에서 영수증을 먼저 확인하고 최초 요청만 기존 진도 효과와 영수증을 한 transaction으로 commit한다. 실패하면 둘 다 rollback한다.

제안 매핑은 `source_scope_id=kanaId`, `attempt_id=activityId`, `source_item_key=kanaId 문자열`이다. `content_version`은 접수 프로토콜 버전과 문자 ID로 만든 값이며, 요청 fingerprint에는 owner/activity/kana를 정규화해 포함한다. 새 동작을 기존 레슨 답안인 것처럼 기록하지 않는다.

효과는 **기존 카드 진도 효과를 한 번만** 반영하는 데 한정한다. XP·SRS·오늘 단어 목표·사용자 연속일 계산을 새로 호출하지 않는다. 기존 퀴즈/레슨 답안의 학습일 함수로 단순 치환하면 카드의 기존 효과까지 바뀌므로, 실제 구현 전에 동등성을 비교해야 한다. 과거 카드 기록과 영수증은 백필·삭제·재계산하지 않는다. 권한·RLS·Data API 차단·음원 캐시는 유지한다.

## 모바일과 저장 실패

인트로의 ‘다음’과 연습의 ‘알아요’처럼 의도한 새 학습 행동마다 UUID를 새로 만든다. 동일 행동의 응답 유실·앱 재실행 후 재시도에는 계정별로 보관한 같은 ID·문자·요청을 사용한다. 로컬 pending 저장을 먼저 확인하고, 해당 계정의 서버 접수 확인 뒤에만 완료로 표시한다. 늦은 응답·계정 변경·삭제 실패도 기존 pending/영수증 경계에 맞춰 검증한다.

버튼을 여러 번 누르는 것과 같은 행동의 재시도를 구분한다. 같은 카드가 인트로와 연습에 다시 나오는 것을 무조건 동일 행동으로 합치지도 않는다. 무엇을 한 번의 학습으로 볼지 구체적으로 고정한 뒤 구현한다.

## 적용·원복과 승인 전 검사

적용 순서는 **제약 확장 → 새 API 서버 → 새 앱**이다. 기존 `/progress`는 구 클라이언트를 위해 유지하고, 새 앱에서만 안전한 경로를 사용한다. 운영 적용 전 API 계약·기존 두 영수증 종류·기존 값/권한 보존과 실제 PostgreSQL 회귀를 확인한다.

필수 회귀는 같은 요청 동시 처리, 다른 내용409, 다른 계정403, commit 전 실패, commit 후 응답 유실, KST 날짜/월 경계 재전송, 로컬 저장 실패·프로세스 재실행·구 서버404, 기존 레슨 영수증 보존이다. 기존 카드 효과와 새 최초 처리의 동등성도 비교한다.

원복은 새 진입을 중단하고 앱·서버를 원복하되 신규 영수증과 확장된 CHECK는 남기는 방식이다. 새 종류의 영수증이 있으면 제약을 축소하는 downgrade는 거절해야 한다. pending을 구 경로로 보내거나 학습 횟수를 수동 차감하는 보정은 원복에 포함하지 않는다.

이 문서는 다음 작업의 구체안이다. 현재 PR에는 endpoint·마이그레이션·새 receipt writer·카드 재시도를 추가하지 않는다. 사용자 확인 뒤 별도 구현·검증·운영 적용 단계로 진행한다.

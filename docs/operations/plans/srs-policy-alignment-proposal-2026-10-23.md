# 레슨·퀴즈 복습 정책 정렬 검토안

## 상태와 적용 경계

이 문서는 2026년 10월 23일의 설계 검토이며 정책 변경 승인이 아니다. PR #192의 실제 함수 비교 회귀 90개와 현재 소스(a408083b 기반)를 다시 확인했다. 이번 후속 구현은 모바일의 저장된 레슨 진입점에 한정한다. 운영 DB 조회·쓰기, 기존 복습 기한의 재계산, API·DB·Data API 설정 변경은 수행하지 않는다.

사용자는 기존 복습 기한에 영향을 주는 변경과 API·DB 변경을 적용하기 전에 구체안을 확인하도록 요청했다. 아래의 실제 정책 통합과 제출 멱등성은 해당 확인 뒤 별도 작업으로 진행해야 한다.

## 현재 차이와 확인된 세 경로

모바일 레슨은 `apps/api/app/services/srs.py`와 `srs_transition.py`, 모바일 퀴즈는 `quiz_answer_progress.py`와 `quiz_policy.py`를 사용한다. 저장소의 웹 `apps/web/src/app/api/v1/quiz/answer/route.ts`는 `apps/web/src/lib/spaced-repetition.ts`의 `calculateSM2`로 같은 progress 테이블을 갱신하는 경로를 갖는다. 웹 훅의 호출도 코드에서 확인했지만 운영 트래픽을 조사한 결과는 아니다. 백엔드 두 함수의 정리만으로 전체 제품이 단일 정책이 됐다고 말하면 안 된다.

아래는 비교 테스트에 고정한 같은 초기 상태와 8초 정답/오답의 관찰값이다. 표의 일·분은 답안 처리 시각부터의 다음 기한이며, 각 행에 고정한 기존 step·interval·streak가 다르다. 표에 따로 적지 않은 값은 step 0·interval 0·streak 0이다. 일반 학습자 전체의 일정이나 최적 간격을 뜻하지 않는다.

레슨은 `fsrs_last_rating`·`fsrs_reps`·`fsrs_lapses`, 방향별 정오와 `last_presented_on`도 갱신한다. 이 경로가 FSRS stability·difficulty나 shadow 계산 결과를 갱신한다는 뜻은 아니다. 해당 퀴즈 경로는 이 필드를 갱신하지 않는다. 레슨과 퀴즈의 rating 계산·이벤트 기록도 다르다. 레슨의 이벤트 기록 실패는 제출 실패로 이어지고 퀴즈는 savepoint 안에서 이벤트 실패를 허용해 답안을 보존한다. 단순히 퀴즈를 레슨의 `process_answer` 호출로 바꾸면 일정뿐 아니라 재노출·집계·장애 시 동작까지 달라질 수 있다.

먼저 A로 계산 경계를 정리할 수 있으나, 현재 두 정책을 유지하는 코드 정리가 교육적 문제를 해결했다고 설명하지 않는다. B/C는 새 답안에 어떤 정책을 적용할지 결정한 뒤 별도 변경으로 진행한다. 이번 모바일 발견성 개선에 이 리팩터링이나 정책 변경을 묶지 않는다.

## 기존 기한 보존의 정확한 의미

1. 배포·마이그레이션 때 기존 `next_review_at`, interval, ease, 단계·횟수와 이벤트를 재계산·정정·삭제하지 않는다.
2. 새 답안이 없는 항목은 기존 기한을 유지한다.
3. B/C를 적용하면 새 답안을 낸 항목의 다음 기한·단계는 새 정책으로 달라진다. 이를 기존 일정에 영향이 전혀 없다고 표현하지 않는다.
4. 새 항목에만 새 정책을 적용하려면 영속적인 항목별 정책 구분이 필요하다. 현재 `scheduler_version=1`은 두 기존 정책을 구분하지 못하고 2는 FSRS 의미이므로 새 정책 번호로 임의 재해석하지 않는다. `introduced_by`도 정책 버전이 아니다.
5. B/C 적용 후의 코드 롤백은 이미 새 답안으로 계산한 기한을 자동 원복하지 않는다. 과거 기록의 되감기는 별도 승인·증거가 필요하다.

## 반복 문항과 제출 재전송은 별도 결정

현재 레슨은 같은 어휘·문법을 평가하는 여러 문항에도 문항마다 SRS를 갱신한다. 같은 초기 LEARNING 항목을 한 제출에서 두 번 맞히면 +3일을 거쳐 +7일로 전진할 수 있다. 한 레슨 시도에서 문항별 채점은 유지하면서 항목별 일정은 한 번만 갱신할지 결정해야 한다. 한 번만 반영한다면 여러 답 중 오답·정답의 집계와 대표 응답 시간을 정의해야 한다. 하나라도 오답이면 오답으로 처리하는 안도 학습적으로 최적이라는 확정안은 아니다.

동일 제출의 재전송은 별도 멱등성 문제다. 현재 레슨 submit에는 원자적인 요청 식별과 저장 결과 재사용이 없다. `attemptId`·요청 지문·결과를 연결하는 API·DB 안이 필요하며 기존 attempts/completedAt을 요청 ID로 대신하지 않는다. PR #192의 로컬 pending 표식은 재전송을 억제하는 보호이며 서버 멱등성을 대체하지 않는다.

문항별 이벤트를 모두 남기되 일정은 한 번만 반영하려면 이벤트의 역할·레슨 시도 식별을 설계해야 한다. 모든 문항을 독립 복습 이벤트로 해석하면 FSRS shadow 재생이나 신규 카드 집계에도 영향을 줄 수 있다. Data API를 다시 열 필요는 없다.

## 정책 적용 전 구체적으로 확정할 항목

- 모바일 백엔드 두 경로만 정렬할지 웹의 별도 계산까지 포함할지.
- 새 답안 전체와 신규 항목만 적용 중 어느 범위인지. 현재 상태 해석·등록·부가 필드·로그 실패 처리의 최종 표.
- 같은 항목의 레슨 내 여러 문항을 어떻게 집계할지와 제출 멱등성의 포함 여부.
- 과거 기한·이벤트는 보존하되 새 답안의 기한이 어떻게 바뀌는지, 정책 버전·API·DB 필요 여부와 롤백 한계.

현재 이 결정들을 임의로 적용하지 않는다. 이번 확인은 소스와 기존 테스트의 읽기 전용 검토이며 운영 데이터나 고객 기록을 조사한 결과로 확대하지 않는다.
